# Модуль directory (ядро)

Пользователи, подразделения (дерево оргструктуры), должности, роли; карточка сотрудника.
Модель — эпик M2 (#18), требования владельца:

- **Руководитель — производное поле** (#923, ADR-0053): `managerId` сотрудника считает сервер — ближайший активный глава (`headId`) вверх по дереву управленческих подразделений (глава своего отдела; если сотрудник сам глава — глава родительского и так выше; себя пропускаем). Клиент ручное значение не присылает: `createUserSchema`/`updateUserSchema` его не содержат. Пересчёт — в тех же транзакциях, что правки (`ManagerDerivationService`): создание/перевод сотрудника, смена главы/родителя/архивация подразделения, деактивация.
- **Двойная структура**: управленческая (`kind=management`) и юридическая (`kind=legal`) пары должность/подразделение — первоклассные справочники (I15), не кастомные поля.
- **Руководитель и заместители** у подразделения (`headId`, `deputyIds` — связь `department_deputies`, #817): заместителей несколько, порядок показа — `sortOrder`; один сотрудник — зам ровно одного подразделения (`UNIQUE user_id`) **в обеих структурах**, роль «одно место»: юридическая карточка сотрудника не переводит, но прежнее место зама снимает. Один человек — **глава только одного** подразделения: `UNIQUE(head_id)` (индекс `departments_head_id_key`) **в обеих структурах** — юридическая карточка тоже занимает единственное место, но сотрудника не переводит; назначение главы в другом узле снимает прежнюю роль, даже когда перевод сотрудника — no-op (он уже состоит в целевом узле).
- **Расширяемость профиля**: ядро карточки стабильно; кастомные поля — модуль custom-fields (M10), геймификация/HR — отдельные модули по `user_id`.

## Контракты (`@nodus/contracts`)

`userCardSchema`, `userListItemSchema`, `listUsersQuerySchema`, `createUserSchema`, `updateUserSchema`, `updateMyProfileSchema`; `departmentNodeSchema`, `createDepartmentSchema`, `updateDepartmentSchema`; `positionSchema`, `createPositionSchema`, `updatePositionSchema`; `roleSchema` (со счётчиками состава и `preview`), `createRoleSchema`, `updateRoleSchema`, `roleMembersSchema`, `SystemRole`.

## События (outbox, I9)

Все имена — из `DIRECTORY_EVENTS` контрактов (литералов в коде нет): `directory.user.created` / `directory.user.updated` (payload: userId, changedFields) / `directory.user.deactivated` (payload: userId — auth отзывает сессии) / `directory.user.activated` (payload: userId — парное деактивации, подписчиков нет: сессии не восстанавливаются, вход заново; AUD-016); `directory.department.created` / `updated` / `archived`; `directory.position.created` / `updated` / `archived`; `directory.role.created` / `updated` (только `name`/`description`) / `deleted`; `directory.role.permissions_changed` `{roleId, permission, granted}` — по событию на реально изменённое право; `directory.role.members_changed` `{roleId, kind, targetId, added}` — при реальном изменении состава; `directory.role.access_changed` `{roleId, reason: 'membership'|'permissions', userIds}` — у этих сотрудников изменился набор действующих прав (аудитория — прямые участники и сотрудники подразделений роли), auth отзывает их access-токены (#866, AUD-002). Должности: `position.updated` на переназначении сотрудников несёт `changedFields: ['holders']`, `targetId`, `reassigned` (счётчик) и `userIds` (кого перевели — по счётчику не восстановить кадровые поля, I7); удаление строки — `position.deleted` (`{ positionId, kind, name }` — название в payload, потому что строка исчезает безвозвратно; `position.archived` осталось в каталоге историей). Gateway эти события пока не маршрутизирует (подписчиков у клиентов нет — #382).

## Правила

- Создание сотрудника — только администратором (self-registration нет); начальный пароль — Argon2id через core `PasswordService`.
- Email уникален **без учёта регистра** (#321): контракт входа (`emailInputSchema`) приводит адрес к `trim + lower`, БД хранит только нормализованную форму (CHECK `users_email_normalized`), поэтому обычный unique `users.email` регистронезависим; предпроверка → `DIRECTORY_EMAIL_TAKEN` (409).
- **Частичная правка — только присланные поля** (#492): `updateDepartmentSchema`/`updatePositionSchema` — явные `optional()`-поля без значений по умолчанию (Zod 4 подставляет `.default()` и в необязательные поля, из-за чего `PATCH { name }` затирал родителя, руководителя, вида и порядка). Пустое тело → `400 VALIDATION_FAILED`; `changedFields` события — реально присланные ключи. Страж — `packages/contracts/src/update-schemas.guard.test.ts` (все схемы правки).
- **Перенос подразделения сериализуется локом дерева** (#544): смена `parentId` и назначение главы/зама идут в одной транзакции под `pg_advisory_xact_lock(hashtext('nodus:departments:tree'))`; построчный `FOR UPDATE` лочит разные строки и не мешает двум встречным переносам образовать цикл. Тот же приём, что в дереве задач (`TasksRepository.lockTree`); `findParentChain` читает через `tx`. Перенос меняет действующие роли сотрудников поддерева — `directory.role.access_changed` отзывает их access-токены (#866).
- **Управленческое подразделение не открепляется в корень** (#982): `PATCH /departments/:id` с `parentId: null` для management-узла, у которого родитель был, → `409 DIRECTORY_DEPARTMENT_ROOT_FORBIDDEN` (`details.id`), база не меняется. Отказ — ранний быстрый путь до `lockTree` (очередь переносов зря не сериализуем) плюс повторная проверка на состоянии после advisory-лока — interleaving «узел переставили между чтением и локом» тоже не проходит. Корень структуры один — главная карточка компании; обычный узел меняет родителя, но не теряет его. Юридическая структура — лес корней, там открепление по-прежнему разрешено. Создание первой карточки (`POST` с `parentId: null`) не затронуто; UI прячет поле у главной карточки и не рисует пункт «Нет вышестоящего подразделения».
- Архивация вместо удаления: пользователи (status), подразделения (isActive), роли — удаляются только несистемные и неназначенные. **Должность удаляется жёстко** (вердикт 17.11.2026, #768): строка исчезает, имя снова свободно, события `position.deleted`. Перед удалением на должности не должно быть сотрудников → `409 DIRECTORY_POSITION_IN_USE` (`details.reason = 'holders'`, `holders`) — сначала `POST /positions/:id/reassign` переводит ВСЕХ сотрудников своей колонки вида, включая уволенных, на другую должность того же вида (цель проверяется: существует, другой вид запрещён), поэтому висячих ссылок не остаётся. `holders` считается по ОБЕИМ колонкам (`position_id` и `legal_position_id`): при аномальной ссылке не того вида удаление упирается в 409 вместо тихого `SetNull` от FK — такие строки разбираются вручную. Миграция снятия `is_active` делает ранее архивные строки обычными видимыми должностями (держатели сохраняются) — перед выкаткой на живую базу их список снимается и решается судьба. Должность больше не источник решающего (#806), предохранитель маршрутов снят. **Дубли имён**: создание и переименование сравнивают название без учёта регистра → `409 DIRECTORY_POSITION_EXISTS` (`details.positionId`); после удаления имя свободно и создаётся новая строка. Удаление и переназначение берут строки `FOR UPDATE` в порядке id — встречные переназначения не дают дедлок.
- **Архивация подразделения**: непустой узел (есть активные дети) → `409 CONFLICT` (`details.reason = 'has_children'`) — сначала архивируются/переносятся дети; иначе активные дети archived-родителя выпали бы из дерева вида (#441). Создание ребёнка и перенос под родителя лочат строку родителя (`FOR UPDATE`) — гонка с архивацией закрыта. Роли, привязанные к узлу, перестают действовать — `directory.role.access_changed` отзывает токены сотрудников поддерева (#866).
- Роли — данные, не код: права из каталога `Permission` контрактов. Права сотрудника считает порт `ROLE_MEMBERSHIP_READER` (прямые роли ∪ роли управленческого подразделения и всех его предков) — единственный источник для входа, refresh и `/auth/me` (#379, ADR-0034).
- **«Администратор» неизменяем**: `PUT/DELETE …/permissions` и `PATCH` с `permissions` → `409 ROLE_LOCKED`; имя и описание менять можно. Состав роли `admin` — только конкретные сотрудники: подразделение → `409 ROLE_LOCKED` (`details.reason = 'departments'`).
- **Защита от эскалации (bind/escalate)**: выдать право или назначить роль (сотруднику, подразделению) можно, только если у актора есть все её права → `403 ROLE_PERMISSION_NOT_HELD` (`details.permissions` — недостающие). Правило покрывает все пути смены ролей сотрудника (#490): `roleIds` в `POST/PATCH /users`, перевод в подразделение с привязанной ролью, перенос подразделения — добавленные роли считает порт `ROLE_MEMBERSHIP_READER` снимком «до/после» внутри транзакции. Отзыв права и удаление из роли по правам не ограничены.
- **Ссылки оргструктуры** (#441): руководитель/зам подразделения и `departmentId`/`positionId`/`legal*` сотрудника — только существующие активные объекты своего вида структуры (management/legal) → `400 DIRECTORY_REFERENCE_INVALID` (`details { field, reason: 'not_found'|'inactive'|'kind_mismatch' }`). `managerId` сотрудника — производное поле (#923, ADR-0053), клиентом не задаётся; циклы невозможны по построению (обход только вверх по дереву, себя пропускаем).
- **Саморедактирование профиля** (#923): `PATCH /users/me` принимает строго поля матрицы владельца — ФИО, телефон, город, кабинет, удалёнка, пол, день рождения, начало дня; схема `.strict()` → подразделение, должность, email, ставка/дата приёма, роли, статус и руководитель дают `400 VALIDATION_FAILED` (серверный allowlist, I8). `displayName` пересчитывается из ФИО; каждое изменение — событие `user.updated` и аудит.
- **Увольнение** (#923): уволенный перестаёт быть главой/замом — `headId`/строки `department_deputies` во всех подразделениях очищаются, `managerId` подчинённых пересчитывается на ближайшего главу выше, события `department.updated` по каждому затронутому узлу. Себя уволить нельзя → `409 DIRECTORY_SELF_DEACTIVATE`; последний администратор защищён (`ROLE_LAST_ADMIN`).
- **Перевод — одно место в управленческой структуре** (#923, вердикт 18.11.2026): глава/зам — роль СВОЕГО подразделения. При смене `departmentId` (другой отдел или `null`) старый узел теряет `headId`/строку заместителя (снимаем только его — остальные узлы не трогаются), подчинённые пересчитываются на ближайшего главу выше, событие `directory.department.updated` несёт `changedFields headId/deputyIds`; собственный `managerId` пересчитывается тем же путём. Повторная установка того же подразделения — no-op. Отдельной кнопки «Перевести» нет: поле «Подразделение» в окне профиля делает и перевод, и удаление из структуры; юридическая структура (`legal*`) — формальные поля и в переводе не участвует.
- **Назначение главы/зама переводит сотрудника** (#946, решение 18.11.2026): `POST/PATCH /departments` с `headId`/`deputyIds` в управленческом узле переводит главу и КАЖДОГО заместителя в это подразделение в той же транзакции — общее ядро `transferUserToDepartment` (снятие роли прежнего узла, `managerId` поддерева, bind #490, `role.access_changed` при изменившихся ролях, `user.updated` с `changedFields ['departmentId']`). Все точки перевода (создание/правка узла, карточка, деактивация) сериализуются advisory-локом дерева. Уже состоящий в узле сотрудник — no-op: без лишних записей и событий. Глава и зам одного узла — разные люди → `400 VALIDATION_FAILED` (`details { field: 'deputyIds', reason: 'same_as_head' }`); назначение в архивный узел → `409 CONFLICT` (`reason: 'archived'`). Юридическая структура (`kind=legal`) формальная — назначение не переводит. Одиночный `departments.deputy_id` переносится в `department_deputies` миграцией `20261202090000_department_deputies` (после нормализации #946): бэкфилл одной строки `sort_order = 0`, затем DROP COLUMN; падающие проверки — глава среди замов, неактивный зам или зам чужого отдела. Дубли `deputyIds` схлопываются (порядок первого вхождения).
- **Последний администратор**: действие, после которого у роли `admin` не остаётся активных прямых участников → `409 ROLE_LAST_ADMIN` (замок строки роли сериализует параллельные правки): удаление из состава (`DELETE /roles/:id/members/users/:userId`), `PATCH /users/:id` с `roleIds` без admin, деактивация последнего участника (#490).
- **Удаление роли**: системная → `409 CONFLICT`. Пользовательская удаляется вместе с составом: назначения сотрудникам и привязки подразделений снимаются каскадом (`ON DELETE CASCADE`), люди просто теряют роль — это и есть смысл удаления (решение владельца 26.10; запрет «сначала уберите всех» убран как лишний шаг). Состав фиксируется ДО удаления, после `role.deleted` уходит `role.access_changed` — выданные ранее токены участников отзываются (#866).
- **Порядок и форма**: `GET /roles` — `isSystem desc, createdAt asc, id asc`, права по алфавиту, счётчики — активные прямые участники и активные подразделения, `preview` — до 4 аватаров. Права вне каталога отфильтровываются: ответ всегда соответствует схеме.
- **Идемпотентность и сериализация**: каждая мутация — `Idempotency-Key` (core-интерсептор); строка роли берётся `SELECT … FOR UPDATE`, поэтому правки прав, состава и удаление одной роли не теряются при параллельных запросах. Аудит — на каждый вызов (`directory.role.permission_grant|permission_revoke|member_add|member_remove`).
- **Подразделения в ролях**: `department_roles` (expand-миграция). Роль, привязанная к управленческому подразделению, действует на его сотрудников и сотрудников всех вложенных; юридическая структура не участвует, архивная привязка прав не даёт. Переключателя «только само подразделение» нет — исключения решаются назначением людей.

## Лимиты

- Список пользователей — курсорная пагинация ≤ 100 (по умолчанию 50), поиск по ФИО/email.
- Дерево подразделений — целиком (десятки узлов; ленивые уровни — при росте > 1000).
- Замещение (временный зам с периодом) и календарь отсутствий — отдельный issue эпика M2; таблица замещений появится там.
