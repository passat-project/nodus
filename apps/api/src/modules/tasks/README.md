# Модуль tasks (API)

Самостоятельные задачи уровня Битрикс24 — ступень 1 модуля «Задачи» (#37, эпик M4 #49; цель — `docs/mvp/archive/tasks-projects-december-vision.md`). **Проект необязателен**: `Task.projectId` nullable, без FK (I3); задача без проекта и без колонки встаёт в начальную стадию маршрута своего типа.

Типы процессов, маршруты, редактор и публикация — модуль **«Процессы»** (`apps/api/src/modules/workflows`, ADR-0024). Задачи подключаются к движку адаптером сущности категории `task` и портами `WORKFLOW_ENGINE` / `PROCESS_CATALOG_READER`; своих таблиц типов и маршрутов у модуля больше нет.

## Модель (ADR-0008, ADR-0020, ADR-0024)

- `Task` хранит `typeId + workflowId + stageId` — **plain UUID без FK** (типы, маршруты и стадии принадлежат «Процессам»; целостность держится архивацией, а не удалением) — и денормализует `systemState`, `spentMinutes`, `checklistDone/Total` в той же транзакции; `commentsCount` — пересчётом по событиям `chat.message_sent|message_deleted` (`events/comments-count.handler.ts`, read-порт чата, #252).
- `Task.nodeId` — узел структуры проекта (#467, ADR-0030 «Дополнение»): plain UUID без FK (дерево — сущность модуля проектов, канон `projectId`, I3); null — «Без узла». Валидация привязки — read-порт `PROJECT_READER.assertNodeAllowed(projectId, nodeId)` (узел этого проекта, иначе 422 без оракула; архивный проект — 400, дерево заморожено); в одном патче со сменой `projectId` узел СБРАСЫВАЕТСЯ (узел старого проекта не переносится — событие несёт `nodeId/previousNodeId`). Меняется из дерева проекта и bulk `set_node`, не в карточке.
- `TaskParticipant` (coexecutor | observer), `TaskPersonalPlacement` (личная доска «Канбан»), `TaskChecklistItem`, `TaskRelation`, `TimeEntry`, `TaskResult`.
- Ключи порядка (`stage_order`, `sort_order`) — fractional-index base62 (`core/lib/fractional-index.ts`; общий для задач и структуры проектов #467), колонки `COLLATE "C"`; keyset `(order, id)`.
- **Личная доска «Канбан» (модель «Мой план», ADR-0008) — явное временное исключение ADR-0024 до #438/#439:** личные маршруты (`workflows.kind = personal`), их стадии и FK размещений живут в таблицах «Процессов», но читает и пишет их только `personal/personal-boards.repository.ts`; шаблон сеет `personal/personal-template.bootstrap.ts` («засев один раз»). Движок «Процессов» такие маршруты не трогает, редактор отдаёт на них 404.

**Фазы системного состояния** (ADR-0020, дополнение 2) — единственная классификация, хелперы `@nodus/contracts` (`taskStatePhase`, `isOpenState` / `isReviewState` / `isFinalState`, `isCompletedState`, `statesOfPhase` для `IN (...)`); локальных множеств «открытых» состояний в коде нет:

| Фаза     | `systemState`           | Правила                                                                                                                                                  |
| -------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`   | backlog, active, paused | работа не сдана; только здесь стартует новая задача и бывает просрочка (сканер, фильтр, счётчики)                                                        |
| `review` | done («Утверждение»)    | работа сдана и ждёт приёмки — **не завершена** и не просрочена; утверждающий вернёт в работу или примет                                                  |
| `final`  | closed + итог           | `completedAt` ставится входом в итог (между итогами сохраняется, выходом снимается); `task.completed` — только вход в итог «выполнена» из незавершённого |

Гейт `no_open_subtasks` строгий по умолчанию (мешают подзадачи в `open` и в `review`); `allowReview: true` — подзадачи на утверждении не мешают.

**Доступ к данным — только репозитории** (patterns.md): сервисы работают с репозиториями + `TransactionRunner` + `EventBus`; Prisma и SQL — только в `*.repository.ts` (методы предметного языка; всё внутри транзакции принимает `tx`).

## Движок маршрутов и типы процессов (модуль «Процессы»)

- **Адаптер** `workflow/task-workflow.adapter.ts` (категория `task`): роли актора и флаги прав задачи, факты гейтов, применение стадии через `StageMover` (события, личная доска «Канбан», `completedAt`), счётчики по стадиям, перенос/пересчёт публикации пачками (своя транзакция на задачу, подготовка личных маршрутов держателей). Регистрируется `DiscoveryService` по `static workflowCategory`.
- **Кнопки маршрута** — тонкий `workflow/task-transitions.service.ts` на `WORKFLOW_ENGINE`: видимость задачи, подготовка личных маршрутов, транзакция; сам порядок «замок → субъект → условия → гейты → обход → смена стадии» ведёт движок.
- **Гидратация DTO** — `PROCESS_CATALOG_READER`: `type` и `stage` строки читаются пачкой (FK между модулями нет), архивация типа не ломает открытие задачи.
- **Создание и смена типа** — `resolveType` с актором (#432): категория (тип письма — 404), архив, **доступ** — невидимый тип 403 `PROCESS_TYPE_FORBIDDEN {reason: 'view'}`, без права создания 403 `{reason: 'not_creatable'}`. Смена типа переезжает стадией через `StageMover` (`cause: type_change`), событие `task.type_changed`.
- **`GET /tasks/stages?typeId=`** — статусы одного типа; без — всех живых типов категории задач с `typeId/typeName` (межтиповой фильтр «Тип · Статус»); стадии и типы — через read-порт, счётчики — свои.

## Создание по типу (#432)

`tasks/task-create.policy.ts` — одна политика на ВСЕ пути создания (`POST /tasks`, подзадачи, «В задачу», будущий ИИ-агент, #436):

1. доступ к типу — каталогом (`resolveType` с актором);
2. недействительный пресет (уволенный сотрудник) — `422 PROCESS_TYPE_PRESET_INVALID`;
3. скрытые значения формы ставятся поверх введённого — значение формы важнее (`applyCreationPresets`);
4. обязательные поля — после умолчаний: `422 PROCESS_TYPE_FIELDS_REQUIRED {reason: 'create'}`; ответственного сервер ставит сам, «не хватает» его не считает.

**Обязательное нельзя очистить** (`reason: 'clear'`): `TaskFieldsWriter` (PATCH карточки и окно перехода) и снятие последнего участника обязательной роли (`ParticipantsService`). **`layout` детали** собирает сервер из типа: `{hiddenBlocks, roleLabels, requiredKeys}` — работает и для типа, невидимого зрителю.

**Единый писатель полей** — `tasks/task-fields.writer.ts` (#380): все правки полей задачи (PATCH карточки, окно перехода, bulk) идут одним кодом — локи, обязательность по форме типа, перепривязка, события; `nodeId` — там же (валидация портом, сброс сменой проекта).

**Замок записи** (#496, Р4) — колонка `tasks.field_locks`: окно создания (`buildCreationLocks` в `TasksService.create`) и нажатая кнопка (`WorkflowEngine` → `TaskFormApplier.applyLocks`, `mergeLocks`: строже побеждает, I-L8) закрепляют поля. Проверка — `task-field-locks.guard.ts` в едином писателе (`assertFieldLocks`: только фактически меняющиеся ключи, карта `lockKeysOfPatch`), у участников — `ParticipantsService`; ручная правка «никто» — 422 `FIELD_LOCKED {keys, reason: 'locked'}`, «постановщик» — `owners_only`/`reason_required` (постановщик или `task.manage_any` с причиной 3..500; форс-мажор — право `task.edit_locked` с причиной). Окно кнопки, которое снова просит поле, пишет его мимо замка (`windowWritableKeys`: настроенный раздел и пустые поля условия «Заполнены поля», В10); права путь замка не снимает. Формульная запись — системный пересчёт, а не ручной ввод: `formulaWrite` замок не проверяет (решение Р4: замок защищает руку, агрегат по формуле меняется от своих источников). Состав под замком читается и пишется только под локом строки (участники — `tasksRepo.lock`, как писатель полей и движок). Формула ячейки закреплённого атрибута — тоже ручная правка: `PUT`/`DELETE /tasks/:id/custom-fields/:fieldId/formula` проверяют замок (`taskFormulaBodySchema.lockReason` / `?lockReason=`, 422 `FIELD_LOCKED`). Деталь отдаёт `fieldLocks` только ключей текущего типа с `canEdit` (Р10); список и канбан замков не несут — отказ 422 тостом. Замок не снимается ни возвратом по маршруту, ни сменой типа.

## Права и видимость

- **Видимость** — единственная функция `access/task-visibility.ts` на все чтения: участники (постановщик, ответственный, соисполнители, наблюдатели), их руководители по оргструктуре (read-порт `ORG_STRUCTURE_READER`, ADR-0012), `task.view_all` (все задачи). Конфиденциальные задачи (#461, `confidential = true`) видят ТОЛЬКО участники: ветки руководителей, видимых проектов и `task.view_all` гейтятся `confidential = false`; поручения из конфиденциального письма ставит #463. Чужая задача = 404. `scope=mine` — только своё участие.
- **Действия** — `access/task-access.ts`: правка и участники — постановщик/ответственный; время — ответственный/соисполнители; чек-лист отмечают и соисполнители; удаление — постановщик; `task.manage_any` — всё. Наблюдатель только читает.
- **Переходы** — условия «кто» из правил перехода (`task.manage_any` проходит всегда); гейты DoR/DoD → `409 WORKFLOW_TRANSITION_BLOCKED` с `details.reasons`; обход — `override` + `reason` и право `task.override_gate` (причина — в событии `task.stage_changed`, история).
- Подзадача и смена родителя — нужен `canEdit` на родителе (иначе наблюдатель заблокировал бы чужую задачу гейтом подзадач). Новая задача создаётся только в открытой стадии (backlog/active/paused; «начальная» на утверждении/итоге — берётся первая открытая), колонка (глобальная или «Канбан») задаёт цель, но переход в неё выполняется в той же транзакции с проверкой условий и гейтов: создание не обходит их; нет перехода или у колонки нет стадии маршрута — `409` с причиной. Перенос в «Завершённые» учитывает итог колонки: «Отмена» не подставляется вместо «Завершить», заблокированный переход возвращает `409 WORKFLOW_TRANSITION_BLOCKED` с причинами этой кнопки.
- «В задачу» и закреп сообщения в результате — только видимые актору сообщения (read-порт `CHAT_MESSAGE_ACCESS` модуля chat через `ChatPortsModule`); дедуп — одна живая задача на сообщение у постановщика (параллельный клик, проигравший unique-индексу, получает задачу победителя, а не 409). Снимок сообщения в задаче не хранится: узел цепочки строится при чтении по правам смотрящего (участник беседы видит название и выдержку, остальные — заглушку «Сообщение чата»).
- Смена родителя: права правки на новом И прежнем родителе; цикл проверяется под advisory-блокировкой транзакции (одна очередь смен родителя на портал — смены редки, а построчные локи не ловят циклы из 4+ узлов).
- Создание — `task.create`. Назначение другому сотруднику отдельного права не требует (канон Битрикса; `task.assign` в каталоге прав пока без потребителя).

## События (`TASK_EVENTS`, каталог api-conventions.md)

`task.created / updated / stage_changed / status_changed / personal_stage_changed / assigned / participants_changed / checklist_changed / completed / overdue / time_logged / timer_started / timer_stopped / result_set / relation_changed / deleted / type_changed`, `task.personal_stage_created / updated / archived`. Payload несёт `audience` — gateway рассылает событие в user-комнаты (`fanout.ts`). `task.relation_changed` уходит по каждой стороне связи (своя аудитория и история у обеих карточек; удалённая вторая сторона — без события). Подписчики: notifications (`events/task-events.handler.ts`: назначение, выполнение, «работа принята», возврат, просрочка, «ждёт утверждения», «отменена» — #378); chat (#252: беседа задачи).

Каталожные события типов и маршрутов — `workflow.*` модуля «Процессы» (там же); прежние `task.type_*` / `task.workflow_*` не эмитятся с #428 (имена зарезервированы, история читает старые записи). `task.stage_changed` несёт `toStageOutcome`, `cause` (`transition` | `workflow_migration` | `type_change`), `coexecutorIds` (адресаты «отменена») и при обходе гейта — `overriddenGates` + `reason` (текст причины); `task.completed` — только вход в итог «выполнена» (фазы выше); `task.type_changed` — задачное, с аудиторией участников.

Автоперемещение «Канбана» — синхронно в транзакции смены состояния (`personal/placements.ts`). Просрочка — `events/overdue.scanner.ts` (BullMQ, каждые 5 минут, однократно, только фаза `open`; смена срока сбрасывает метку).

## Кастомные атрибуты (#431, ADR-0029)

Значения живут в `tasks.custom_fields` (JSONB, ключ — id определения; GIN `jsonb_path_ops`). Читает и пишет их только модуль задач, а валидирует **порт реестра** `CUSTOM_FIELD_REGISTRY` (модуль `custom-fields`): таблицу `field_definitions` задачи не читают (I3).

- **Создание** (`TasksService.create` — единственный путь, включая подзадачи и «В задачу»): `prepareCreate` подставляет умолчания **привязанных к типу** атрибутов (включая снимок «подразделение автора»), ввод важнее умолчания; ошибка — `422 CUSTOM_FIELD_VALUE_INVALID` до записи строки. Значение непривязанного атрибута — `not_in_type`.
- **Правка** (`PATCH /tasks/:id` и окно перехода): `prepareUpdate` с `typeId` под замком строки — параллельные патчи сливаются по ключам, `null` удаляет ключ, проверяются только изменённые значения (архивный сотрудник в старом значении не блокирует соседнее поле); запись непривязанного — `not_in_type`, очистка разрешена.
- **Деталь** несёт `customFieldRefs` (имена/аватары/архивность) — пачками через порты; строка списка несёт только значения.
- **Событие:** `task.updated` получает `fields` с ключами `cf.<id>` и `customFieldChanges[{fieldId, from, to}]` (≤ 50, `long_text` обрезан до 500).
- **Удаление атрибута** чистит значения обработчиком `custom_field.definition_changed` (`change='deleted'`) — `custom-field-values-cleanup.handler.ts`; повторная доставка безвредна.
- **Гейт «Заполнены поля»** видит атрибуты через факты адаптера (`customFields`, `activeCustomFieldIds`); неизвестный ключ переход не блокирует, скрытый — блокирует по значению.
- Права: правка значений — как у полей задачи (`canEdit`); управление реестром — `custom_field.manage` (не здесь).

### Формулы ячеек (#632, ADR-0037 п.3)

- Мутации формулы — `tasks/task-formula.service.ts` (право `canEdit`, как у правки полей): `PUT/GET/DELETE /tasks/:id/custom-fields/:fieldId/formula`; значение материализует штатный `TaskFieldsWriter` (`formulaWrite`), пересчёт по зависимостям — `TaskFormulaRecalcService` + обработчики `events/formula-*.handler.ts`.
- **Формульная ячейка руками не пишется** (решение по #660): значение в атрибут со своей формулой или формулой типа — 422 `FORMULA_CELL_LOCKED` (`task-fields.writer.ts`, проверка `FORMULA_CELLS.lockedFieldIds` только реально изменённых ключей); окно перехода и окно создания такие поля молча пропускают. Снятие формулы (DELETE) очищает вычисленное значение — ячейка пуста или под формулой типа; снятие идемпотентно: без ячейки — no-op, значение и `formula_changed` не трогаются (#658).
- **Пересчёт синхронный в tx PATCH** (`recalcOwnAfterValuesChange`, порог 20 ячеек): ответ мутации несёт свежие формульные значения — асинхронный диспетчер (поллинг outbox) опаздывал на цикл, карточка «отставала на шаг». Чужие хосты пересчитывает диспетчер; каскадная запись чужих задач идёт с `foreignWrite` — актёр-триггер в аудиторию чужих событий не добавляется (конфиденциальность).
- Актёр правки всегда в аудитории `task.updated` своей записи; `formula_changed` (O4) — адресно, при смене наличия ошибки.

## Окно перехода (#380)

`POST /tasks/:id/transitions/:transitionId` принимает `form` (поля, время, итог, причина; значения атрибутов — `form.fields.customFields.<id>`, ключ окна — `cf.<id>`) и выполняет переход **одной транзакцией**: сверка с эффективным окном кнопки, `TaskFormApplier` (права `canEdit`/`canLogTime`/`canCheck`, дифф полей через общий `TaskFieldsWriter`, время через `TimeService.addManualInTx`, итог через `ResultRevisions` с проверкой сообщений беседы задачи), гейты по новым фактам, смена стадии, журнал `transition_records`, события. Чужое/удалённое сообщение итога — одинаковый 404; 422 — состав окна, 409 — гейт. DnD и «Канбан» в кнопку с обязательным окном отвечают 422; перенос в колонку этапа «Итог» фильтрует кандидатов по итогу колонки (#402). `task.stage_changed` несёт `recordId`, `transitionName`, `fromStageName`, `comment`, `commentLabel`, `result { resultId, fileCount, messageCount }` — по ним чат пишет блок перехода.

## Лимиты и границы

- **Файлы задачи — вложения её чата** (#252): отдельного файлового хранилища у задачи нет (одна механика вложений, без дублирования; доступ к файлу = участие в беседе задачи = участие в задаче). Ссылка на файл-результат на сервере — ступень 2.
- Колонок «Канбана» — не больше 30 на сотрудника; правки колонок одной доски сериализуются advisory-локом владельца (лимит и «последняя колонка состояния» не обходятся гонкой). Самоснятие с задачи — только наблюдателю.
- Участники: ответственный — никогда; постановщик — только соисполнителем (так он пишет время), наблюдателем — нет. Смена роли пересчитывает звук (наблюдатель — без звука, соисполнитель — со звуком).
- Чат задачи здесь не живёт: `/tasks/:id/messages` на бэкенде нет (канон #252 — одна беседа мессенджера `type='task'`).
- `project` в DTO — `null` до бэкенда проектов (ступень 3); `projectId` хранится.
- Таймер пишет не больше 1440 минут одной записью; дата записи таймера — UTC-день старта. Идущую запись таймера удалить нельзя (`409 CONFLICT`) — сначала «Стоп» (каноничная остановка с `task.timer_stopped`), затем удаление.
- Подзадачи: глубина не ограничена, циклы — `TASK_PARENT_CYCLE`; удаление родителя поднимает детей к ближайшему живому предку (под той же очередью дерева, что смена родителя). В карточке — первые 200 подзадач по номеру (порядок создания).
- Каскад дат автоматикой не делается: веб предлагает «подвинуть подзадачи» сам (#311).

## Решающие: видимость, пресет, наблюдатель (#433)

- `TaskDeciders` (`access/task-deciders.service.ts`) — единственный сервис,
  который знает, кто держит шаг: факты актора для движка, вакансии, набор
  задач для видимости и адресаты уведомлений. Внутри НЕ вызывается
  `visibleTasksWhere` (иначе цикл).
- Видимость: `Viewer.deciderTaskIds` → ветка `id in (...)` в
  `visibleTasksWhere` под гейтами скрытых проектов и `confidential = false`
  (как у руководителей). Решающий видит карточку и чат read-only, но не
  получает прав участника.
- Пресет «Ждут моего решения» — только список задач: `GET /tasks?role=decider`
  (серверный фильтр, scope принудительно `all`). Канбан и журналы
  проектов/сотрудника пресет не показывают.
- `task.stage_changed` несёт `deciderIds` нового статуса (отфильтрованы
  видимостью), `taskNotices` шлёт им `action.decision` («Ждёт вашего
  решения»); нажавший исключён. Ретро-уведомлений при смене оргструктуры нет.
- После нажатия решающий добавляется наблюдателем без звука
  (`insertObserverIfAbsent`: только вставка, coexecutor не понижается),
  пишется `task.participants_changed`.
- Вложения задачи: `TaskDeciderFileAccess` (маркер контекста `chat`) даёт
  решающему `canView: true, canEdit: false`; чат задачи открывается через
  `TASK_CHAT_READER.isDecider` без добавления в состав беседы.
