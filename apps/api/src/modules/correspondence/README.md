# Модуль `correspondence` (#55, ADR-0027)

Письма компании на движке «Процессы»: очередь «Новые», регистрация с
нумерацией, журналы «Входящие»/«Исходящие», карточка с реквизитами, файлами,
историей и чатом. Заменяет СЭД «Е-дело» и папки Bitrix24.

## Что здесь

| Папка       | Содержимое                                                                                                                                                                                                                                                                                                        |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `letters/`  | Контроллер `/api/v1/letters`, чтения (списки, карточка, адресаты), мутации (ручное создание multipart, правка реквизитов — и незарегистрированного по месту в карточке, спам, присоединение/приглашение в обсуждение, личный признак «просмотрено»), проверка регистрационных полей, маппер DTO, разбор multipart |
| `workflow/` | Адаптер категории `letter` для движка «Процессов», применение окна «Регистрация», смена стадии с событиями, сервис переходов                                                                                                                                                                                      |
| `history/`  | История карточки из event log по агрегату `letter`                                                                                                                                                                                                                                                                |
| `mail/`     | Подсистема приёма почты (#56, ADR-0035): порт `MAIL_CLIENT` (imapflow), событийный парсер mailparser, писатель письма (temp-файл → хранилище → одна транзакция), цикл приёма IDLE/фолбэк, SMTP-транспорт очередью                                                                                                 |
| `ports/`    | `LETTER_CHAT_READER` — порт для моста чата (состав беседы, ссылки, видимость); `LETTER_FIELD_VALUES_READER` — число писем с заполненным атрибутом (#575) для окна удаления определения; `LETTER_VISIBILITY_READER` — видимость писем для счётчика «Писем» карточки CRM (#461)                                     |
| `access/`   | Одна функция видимости и прав карточки (Р7)                                                                                                                                                                                                                                                                       |

## Приём почты (#56, ADR-0035)

Общий ящик канцелярии (Kerio Connect, IMAP 993) — источник входящих.
Подсистема с собственным рубильником `mail-reception` (default false, сид
миграцией), НЕ флагом модуля: armed = флаг И `MAIL_IMAP_*`; флаг
перепроверяется каждый цикл (выключили — suspend и разрыв, включили —
resume). Секреты — только `.env` владельца/песочницы; в контейнер `api` ключи
проводятся явно из `docker-compose.yml` (#577) — иначе compose видит их только
для подстановки и приём молча спит. Включение на проде —
`docs/runbooks/mail-reception.md`. Если подсистема не вооружена, сервис пишет
причину в лог одной строкой на переход (`reportDisarmed`), а не молчит.

- **Мгновенность** (вердикт В4): INBOX выбран постоянно, imapflow сам уходит
  в IDLE и толкает `exists` → дебаунс 2 с → `sync('idle')`. Фолбэк — Job
  Scheduler BullMQ каждые `MAIL_POLL_MINUTES` тем же sync (идемпотентен
  курсором). Реконнект: 5 с → 30 с → 5 мин.
- **Цикл**: status → контроль UIDVALIDITY (смена — полный переобход под
  дедупом) → readonly-lock → UID > lastUid → письмо за письмом. Первый запуск
  ставит курсор на max UID — старое не импортируется (В5). Параллельность:
  in-process мьютекс + `pg_advisory_lock`; горизонтальное масштабирование
  api для приёма запрещено.
- **Письмо** (`mail-letter-writer.ts`): исходник — temp-файл (размер до
  записи в хранилище); разбор событийный — заголовки раньше вложений, дедуп
  Message-ID ДО записи файлов (гейт: 'end' ждёт решения); тело UTF-8
  (`role=body`), .eml (`role=source`), первый PDF — `main`, inline-картинки с
  `contentId`; письмо + вложения + авто-связь + курсор + outbox
  `letter_received` (≤52 файлов) — одной транзакцией, компенсация файлов при
  отказе. Битое письмо — «Новое» с `mailParseIssue`, без файлов, курсор идёт.
  После коммита у письма с телом — фоновая PDF-копия тела («Основной документ
  письма»): очередь `correspondence-body-pdf` (`mail/body-pdf/`, конвертация
  Gotenberg/Chromium через порт `DOCUMENT_CONVERTER`), файл-вложение
  `role=body_pdf` «Текст письма.pdf» — системный кандидат основного документа
  (главный де-факто, пока `main` не выбран); backfill на старте подхватывает
  старые письма, отказ конвертера — флаг `mailBodyPdfIssue` без падения
  письма.
- **Связи «ответ на»** (`letters/letter-threading.service.ts`): авто по
  In-Reply-To/References (JWZ: ближайший предок, кап 100); подсказка по теме
  «Исх-ГГГГ/N» / «на № N от ДД.ММ.ГГГГ» — только зарегистрированные исходящие;
  подтверждение галочкой (`replyToLetterId`) валидирует свежесть подсказки
  (`LETTER_RELATION_INVALID`).
- **Спам-надгробие**: удаление спама сносит файлы и вложения, строка живёт с
  `deleted_at` и Message-ID — повторный импорт (сброс UIDVALIDITY) мусор не
  возвращает; списки и карточка надгробия не видят.
- **SMTP** (`smtp-outbox.transport.ts`): очередь BullMQ для #464 — 587
  STARTTLS, 4xx ×5 повторов, 5xx — провал сразу с `letter_send_failed`.
- **Уведомления** (модуль notifications): `letter.arrived` держателям
  `correspondence.register` (на каждое почтовое письмо), `mail.sync_failed`
  (≥3 неудач, раз в 24 ч), `letter.send_failed`.
- **Egress Gotenberg**: контейнер конвертера — только в `nodus_internal`
  (без выхода наружу), api — в обеих сетях (долг security-ревью #55).

## Как устроено

- **Письмо — сущность движка** (ADR-0024): тип, маршрут и стадия — plain UUID
  без FK; категория типа `letter`. Адаптер регистрируется DiscoveryService по
  `static readonly workflowCategory = 'letter'`.
- **Уборка значений удалённого атрибута** (#582): событие
  `custom_field.definition_changed` (`change='deleted'`; `scope` упразднён
  #631 — каждый владелец чистит свою таблицу безусловно)
  убирает ключ из `letters.custom_fields` пачками и идемпотентно; мягко
  удалённые письма тоже чистит — восстановление не воскрешает значение.
- **Регистрация — переход** `register` маршрута входящего: окно
  `{kind:'registration'}` + пост-действие `assign_number`. Номер выдаёт движок
  в той же транзакции (`NumberSeriesService`), откат перехода не сдвигает
  счётчик — номеров без пропусков. Формат «Вх-2026/118», год — по
  `COMPANY_TIMEZONE` (Минск).
- **Видимость** (`access/letter-access.ts`): зарегистрированное — всем,
  незарегистрированное — держателям `correspondence.register`; невидимое —
  404 без оракула. Той же функцией пользуются мост чата, файлы, дерево связей
  и счётчик CRM. Конфиденциальное письмо (#461) сужает круг до участников
  (регистратор, адресат, участники обсуждения) и держателей
  `correspondence.view_confidential` (по умолчанию ни у кого, даже у
  администратора); списки фильтруются SQL-условием, чужим — 404.
- **Права карточки**: `canEdit` — право регистрации (правка реквизитов, для
  незарегистрированного — заполнение полей по месту в карточке, редизайн #56;
  адресат меняется только до регистрации), `canDeleteSpam` — «Новое» и не
  закрыто, `canJoin` — не участник (канцелярия — любое письмо, остальные —
  только зарегистрированное; у конфиденциального — только регистратор ЭТОГО
  письма или держатель права). `canManageRelations` — право регистрации.
  Сервер — истина (I8), веб прячет недоступное.
- **Связи писем** (#461): `letter_relations` двух видов — `reply_to` («ответ
  на», авто по почтовой цепочке #56 и ручная канцелярией) и `nested_in`
  («вложено в», матрёшка). Частичные unique «одна связь каждого вида»,
  CHECK самосвязи; цикл запрещён — подъём по обоим видам в транзакции с
  `FOR UPDATE` пары писем (порядок по id). Повтор той же цели идемпотентен,
  другая цель — 422 `already_linked` или `replace` (delete+insert), снятие —
  204 идемпотентно. Дерево «ёлочки» (`GET /letters/:id/tree`) — вверх до
  корня (кап 64), вниз DFS (глубина 8, узлов 200, `truncated`); невидимые
  узлы исключаются молча, невидимый промежуточный скрывает поддерево.
- **Приложенные письма** (#461): `letter_attached_refs` — строки «№ +
  организация (контрагент или текст с листа) + дата» конверта-матрёшки;
  ввод при регистрации и PATCH в карточке (набор целиком, история —
  счётчиком), поиск реестров находит по номеру любого приложенного
  (`attachedRefs.some.number contains`). Вложения-файлы сюда не входят.
- **Личный признак «просмотрено»** (редизайн #56): `letter_views` (письмо +
  сотрудник), `POST /letters/:id/view` — 204 без аудита и события; список
  несёт `viewed` для текущего сотрудника, карточка — всегда true.
- **Файлы** — plain UUID модуля files (I3): метаданные через
  `FILE_OBJECT_READER`, запись через `FILE_STORAGE`, отдача — подписанные
  ссылки `SignedUrlService` после проверки видимости. Роли: `main` (документ
  вкладки «Письмо»), `body` (HTML/текст почты — хранится для PDF-конвертации,
  в продукте не показывается), `body_pdf` (PDF-копия тела — единственная
  видимая форма текста, «Основной документ письма» #56, роль неизменна),
  `attachment`, `source` (.eml, #56). Файлы писем неизменяемы
  (`canEdit:false` в реестре доступа файлов).
- **Основной документ** («Основной документ письма» #56): канцелярия выбирает
  звёздочкой файл-кандидат до регистрации — `POST /letters/:id/main-document`
  (идемпотентен; заморозка после регистрации — `LETTER_NOT_EDITABLE`);
  выбранный файл становится `main`, прежний — приложением, PDF-копия тела
  остаётся `body_pdf` и становится главным де-факто. Регистрация требует
  выбор, когда кандидаты есть (422 `mainDocument`), — номер присваивается
  документу. Смена фиксируется историей (`letter_updated`, поле
  `mainDocument`).
- **Чат письма** — модуль chat по событиям `correspondence.*`: состав
  (адресат + участники, регистратор не входит — В2) читается портом
  `LETTER_CHAT_READER`, блок `letter_transition` пишется по
  `letter_stage_changed`. Внутреннее обсуждение незарегистрированного письма
  (редизайн #56): `POST /letters/:id/join` канцелярией «начинает» его,
  `POST /letters/:id/participants` (`correspondence.register`) приглашает
  коллег; владелец до регистрации — создатель (первый участник), состав
  переживает регистрацию — владелец становится адресатом.
- **Спам** удаляется физически только из «Новое» (Р12): письмо, вложения,
  объекты хранилища (после коммита, best-effort); в аудит — только id.

## Запреты

- Не импортировать модули `workflows`, `chat`, `files`, `crm`, `dictionaries`
  напрямую — только порты-модули (`WorkflowsPortsModule`,
  `CorrespondencePortsModule`, …) и события.
- Не менять контракты `@nodus/contracts` ради удобства сервера: они
  заморожены UI-пакетом.
- Не писать в чужие таблицы: `letters`, `letter_attachments`,
  `letter_participants`, `letter_views` — только через `LettersRepository`.
- Тяжёлую работу (PDF-производные) — не в HTTP-запросе: очередь модуля files.
