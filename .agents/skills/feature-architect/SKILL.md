# Архитектор фич — техплан issue → план для исполнителей

План «из головы» оставляет дыры — решения без обоснования, пропущенные края, вопросы,
выстреливающие на исполнении или приёмке. Дорогая модель сильна не усердием, а фазами —
навык задаёт их процедурой.

## Граница с другими инструментами

| Инструмент | Уровень | Вход → Выход |
|---|---|---|
| Прожарка (`grilling`/grill-me, `core-forge`) | Верхний | мысль/концепция → бизнес-решения владельца, глобальный план, нарезка issues |
| **Этот навык** | Нижний | готовый issue (+прошлые решения) → технический план для исполнителей |
| `workflow.md` п. 2 | Каркас | когда какой план пишется и куда кладётся |

Сцепка с прожаркой: глобальная модель уже согласована — не переспрашивать отвеченное, цитировать источник; Ф2 обязателен всегда.

## Порог: когда какой конвейер

- **Полный**: ≥2 модулей, новые сущности/миграция/права, новый поток/экран, событие со слушателями в других модулях.
- **Сокращённый**: один модуль, без новых сущностей — Ф1 → Ф2 → Ф3 → Ф4-минимум (линзы 2, 5, 9, 10, 11) → один критик-субагент (поперёк) → Ф6.
- **Не конвейер**: правка одного файла/дня без новых поверхностей — план по `workflow.md`, навык не нужен.
- Сомневаешься → полный. Ошибка в сторону глубины дешевле переделки на приёмке.

## Конвейер

| Фаза | Выход | Гейт (не пускает дальше) |
|---|---|---|
| Ф0 Калибровка | категория, список поверхностей | категории соответствует фактам issue |
| Ф1 Разведка | таблица «что уже есть» | каждая строка с file:line или ссылкой на документ |
| Ф2 Прогон понимания | таблица ответов владельца | сценарии подтверждены; блокеров нет |
| Ф3 Модель и решения | черновик Р1…РN, инвентарь механизмов, таблица внешней сверки | решения с источниками; 5–10 web-запросов с вердиктами |
| Ф4 Закалка линзами | находки C1…CN внесены | чистый проход; ≥10 находок на полный конвейер |
| Ф5 Критики-субагенты (2 запуска) | вердикты поперёк + вдоль | оба без блокеров |
| Ф6 Финальный план | план в issue, чеклист фаз в тело | чеклист приёмки шаблона пройден; `plan:check` зелёный |
| Ф7 Отчёт владельцу | секция «Владельцу» | простой язык, без жаргона |

### Ф0. Калибровка

Прочитай issue, эпик, строку плана трека и свежие правки канона (git log docs/) — правила среды
движутся быстрее плана. Определи категорию (порог выше) и поверхности: модули, события, контракты,
права, миграции, файлы, WS, флаги, экраны. Дальше — по строкам [references/coverage-map.md](references/coverage-map.md):
каждая поверхность тянет свои обязательные разделы плана и линзы (пропущенная строка = дыра).

### Ф1. Разведка (verify, don't trust)

Чеклист и карта точек интеграции — [references/recon-checklist.md](references/recon-checklist.md).
Разведка — до закрытого фронта: на каждую поверхность из Ф0 — свой целевой субагент
(пачкой; запрос конкретный — «как устроен X», не «изучи модуль»); гейт: факты покрывают
ВСЕ поверхности Ф0, «не нашёл» — только с перечисленными запросами. Чистый поиск — дешёвый
поисковый субагент (Claude Code: `Explore`), многошаговые цепочки — универсальный субагент
(Claude Code: `general-purpose`; в других рантаймах имена свои — бери аналог по роли);
точечное — сам.
Утверждение о коде — с file:line; расхождения спеки и кода — отдельным списком; прошлые
решения — в артефактах, до вопросов владельцу. Отдельные ходы: grep канона (ADR, планы) по
номеру issue — что обещано ЭТОЙ задаче, выполняется или отклоняется строкой, не молча;
конвенционный аудит — 5–10 grep кода (маппинг ошибок/HTTP-статусы, формат курсора, regex
кодов, i18n, канон UI) → секция «Конвенции» с цитатами file:line; числовой HTTP-код в плане —
только после сверки с решающим фильтром. Доступность инструмента — пробой, не предположением
(цепочка issues — `gh issue view` по одному); недоступное — вскрывается голосом, не молча.

### Ф2. Прогон понимания мимо владельца (обязателен всегда)

Владелец — нетехнический и мог не увидеть, как кейс ляжет в работу системы, — архитектор
валидирует понимание всегда, даже когда «всё отвечено». Банк паттернов — [references/business-questions.md](references/business-questions.md).

1. Составь 2–4 сквозных бизнес-сценария по ролям на фейковых, но живых данных («Вика
   регистрирует письмо от ООО „Галур“… опечаталась — что должно произойти?»); вперёд и назад.
2. Каждый сценарий заканчивается вопросом «так ли ты себе это представлял?» —
   подтверждение или поправка: дословно в план и немедленно парой «вопрос → ответ»
   в issue; публикация недоступна — полные тексты в плане, издать первым шагом после.
3. Дыры: **отвечено где-то** (цитата, не спрашивать) / **блокер** (вопрос владельцу) /
   **допущение** (безопасный дефолт с пометкой); допущение, видимое владельцу в интерфейсе
   или схеме (поля, обязательность, кто видит, раскладка), — не допущение, а вопрос: он
   читает его как «уже решили — неправильно».
4. Вопросы — 1–2 батча по ≤4, grilling-формат: рекомендация первым пунктом, варианты,
   бизнес-языком. Технические слова (API, таблица, схема, миграция) — запрещены.
5. Продукт-референс (Битрикс и т. п.) — выписать элементы и сверить модель с ожиданием владельца до плана (урок #379).

### Ф3. Модель и решения

Черновик: сущности/поля; потоки; права; события; состояния; границы модулей и порты (ADR-0012);
фичефлаги; миграции; экраны; MSW-мир. Источник РN — цитата владельца / file:line / ADR / «решение архитектора: почему».

Доводки решений (каждая — гейт с артефактом, не «старание»):

- **Трасса до края — по значению, не по имени**: новое данное и рискованный поток тянут
  цепочку «рождение → хранение → чтение → доставка → рендер»; звено фиксирует, ЧЕМ стало
  данное и ИЗ ЧЕГО оно построено (входы → источник); у каждого потребителя данного (DTO,
  payload, чужой модуль) — носитель: пара «данное × потребитель» без механизма = дыра; край
  закрыт ВЕРДИКТОМ гейта — прочитанная строка + вывод против значения во всех существенных
  измерениях (размер, длина, количество, схема): file:line — адрес, не приговор; край
  называет среду показа (мок/песочница/прод) с предусловиями — линза 10. Существующие
  звенья — file:line; «когда» — момент и порядок (бутстрап, транзакция, очередь); край
  предметен (пиксель, строка, тост). Обрыв — дыра или STOP; норма 3–5 трасс на фичу.
- **Гейты точек входа**: переиспользуемый паттерн И каждая новая точка входа (джоба, тик шедулера,
  системный путь) — таблица «обязательный вход → источник значения» (актор — первый подозреваемый):
  актор → права → все флаги на пути и их сочетания → явная строка «какие существующие проверки НЕ
  применяются и почему» (решающим файлом). Строка без источника — STOP.
- **Матрица инвариантов**: правило доступа/секретности сущности — таблица «инвариант × ВСЕ пути
  записи (create, PATCH, переходы, участники, join/leave, события — включая существующие) × где
  проверяется × какой тест»; перечень точек вместо матрицы — дыра: неперечисленный путь находит ревью.
- **Носитель сигнала и аккумулятор**: ветвящееся правило сопровождается сигналом различения веток
  и полем, где сигнал живёт; правило со временем/счётчиком/порядком — аккумулятором: что копится,
  где живёт, когда сбрасывается. Нет поля — дыра модели, решается сейчас, не «на исполнении».
- **Внешняя сверка (web) — 5–10 запросов до закалки**: рискованные решения — против мировой
  практики; запрос по РЕШЕНИЮ со стеком и ограничением, не по теме; вердикт «подтверждено /
  скорректировано (как) / отклонено (почему)» со ссылкой; артефакт — таблица «решение → запрос →
  источник → вердикт» в §4 плана. «Мир делает иначе» — находка для линз 1/11; расхождение с
  вердиктом владельца — вердикт остаётся, цена записана. Не Context7 (синтаксис, Ф1) и не проба
  своей инфраструктуры — сверка про «лучше ли мы придумали».

Ф3 завершается **инвентарём механизмов** — подвижные части (цикл, очередь, курсор, соединение, счётчик, шедулер) и упорядочивающие/
исключающие утверждения решений; допрос отказами — линза 1, ответы — утверждения плана с гейтом достоверности.

Отклонения от канона — ON с обоснованием, пометкой «Дополнение ADR»; что НЕ делаем — явно, с триггером
возврата. Пакеты — **по цене суждения, не по слою стека** (урок #55): описанное до буквы — рабочей модели,
суждение и вкус — умной. UI: **механика** (рабочая, композиция — из плана) → **вкус** (`ui-writer`, сессия
на весь issue) → **тираж** (рабочая); бэкенд после freeze — рабочей. Детали — шаблон.

### Ф4. Закалка черновика линзами

Одиннадцать линз, каждая — отдельный проход (полный каталог — [references/attack-lenses.md](references/attack-lenses.md)):
3 часа ночи; края данных; права; интеграции; UX-состояния; скоуп; «не так представлял»; соседние задачи;
поздняя правка; среда показа; технические механизмы. Линза находит ≥1 замечание или «не применимо»;
находки правятся сразу, цикл до чистого прохода (максимум 3).

### Ф5. Критики-субагенты (свежий контекст, два запуска)

Два ОТДЕЛЬНЫХ запуска универсального субагента (Claude Code: `general-purpose`; в других
рантаймах — аналог по роли), по одному на режим; объединение режимов в один прогон
запрещено — режимы открывают непересекающиеся классы дыр. Промпты ниже — дословно,
дополняй только файлом плана и номером issue. Рантайм не запускает субагентов без явного
поручения — запроси владельца словом; молча пропустить критиков нельзя.

**Запуск 1 — поперёк:** «Ты — независимый критик техплана Nodus, свежий контекст, автор
плана — не ты. План: <файл>; issue: `gh issue view <N> --json title,body` (комментарии не
читай). Read-only. Найди, где план сломается при исполнении средней моделью: решения РN
без строки "Источник:"; вопросы без ответа; допущения, видимые владельцу (поля,
обязательность, видимость, раскладка); противоречия коду — каждую ссылку file:line
проверь сам (файл существует, строка в пределах, файл говорит именно это); противоречия
канону — AGENTS.md, инварианты I1–I15, ADR области, шаблон плана (разделы отсутствуют без
"не применимо: причина"); дыры фаз — гейт недостижим в границах фазы, критерий приёмки
без команды. Каждая находка: C#, серьёзность (блокер/существенное/механика), раздел,
сценарий сбоя, правка; без сценария сбоя — не находка. Последняя строка: "Вердикт: без
блокеров" или "Вердикт: N блокеров, M существенных".»

**Запуск 2 — вдоль (сухой прогон):** «Ты — исполнитель без контекста сессии планирования.
План: <файл>; issue: заголовок и тело, комментарии не читай. Read-only. Пройди самый
рискованный пакет <имя из §7> файл за файлом; каждый шаг помечай [план отвечает] /
[догадка] / [STOP] — догадка = план не отвечает. Заканчивай полным списком догадок и
STOP-ов. Последняя строка: "Вердикт: без блокеров" или "Вердикт: N блокеров".»

Находки C-номерами → правки → повтор при блокерах (максимум 2).

### Ф6. Финальный план и самопроверка

Шаблон эталонного плана — [references/plan-template.md](references/plan-template.md).
Самопроверка — ЕДИНЫЙ чеклист приёмки шаблона (14 пунктов, по порядку, без пропусков) плюс
механика: `pnpm plan:check <файл плана>` (разделы или «не применимо», источники у РN,
существование file:line ссылок, команды у критериев, длина) — вывод скрипта прикладывается
к плану; «конвейер пройден» без вывода скрипта — ложь. Каркас плана — рабочий файл
`docs/mvp/plans/<N>-<slug>-plan.md` (не в git) с первой фазы, фазы дозаполняют его.
Куда: полный план — комментарием в issue; чеклист фаз и ответы владельца — в тело issue
(с комментарием-следом).

### Ф7. Отчёт владельцу

Секция «Владельцу» в плане + короткое сообщение: что придумали (простым языком), главные
развилки, что НЕ делаем, оценка, порядок урезания, что проверять на приёмке.

## Железные правила

1. Не спрашивай владельца о том, что можно найти в коде, доках, артефактах, — факты добываем сами; владельцу — только выборы.
2. Ответы и поправки владельца — дословно в план; тела issue правятся тем же шагом.
3. Решение без источника — не решение.
4. Исполнители решений не принимают: спорное решено в плане; нехватка факта — STOP.
5. Прогон понимания (Ф2) не пропускается никогда — подтверждение стоит минуты, расхождение стоит переделок.
6. Вопросы владельцу — бизнес-кейсами, с рекомендацией; один-два батча, не капать по одному.
7. Линза без находок обязана объяснить пустоту.
8. Каждая находка закалки либо правит план, либо отклонена с причиной — «пропущено» не бывает.
9. Гейты не сжимаются при нехватке времени — сжимается скоуп; трассы Ф3, линзы 9/10, сухой прогон Ф5, бут-гейт фаз не урезаются никогда.
10. Границы пакетов (freeze) определены в плане до старта исполнения.

## Антипаттерны

- «Изучу при реализации» — план отвечает сейчас или честно пишет STOP-условие.
- Технические вопросы владельцу — схему выбирает архитектор, владельцу — бизнес.
- Прожарка заново вместо цитирования отвеченного; один проход «я всё проверил» вместо линз и критика.
- План-транскрипт: шаги вместо решений; раскатка решений «из головы» мимо внешней сверки.
