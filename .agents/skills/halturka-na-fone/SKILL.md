# Халтурка на фоне

Мелкий баг с видимым результатом, который можно починить без вопросов
владельцу. Навык — для пауз между основной работой: владелец сказал
«займись халтуркой», «пока ждём — почини мелочь», «разбери мелкие баги».

**Не включать самовольно** во время UI-чекпоинта или ожидания вердикта по
другой задаче: там сессия исполнителя остановлена (workflow п. 4). «Фон» —
это пауза с чистым деревом, а не параллельная правка того же дерева.

## Железные правила

1. **Только свободный issue.** Кандидат — `no:assignee`: ни одного
   ответственного, включая владельца. Перед взятием перепроверь
   `gh issue view <N> --json assignees`; кто-то успел назначиться — пропусти,
   не отбирай. Чужой assignee не снимать.
2. **Сразу сообщи номер.** Сразу после назначения и до начала фикса —
   короткое сообщение владельцу: «Беру #N — <одна строка сути>». Без вопросов
   и «можно?». Бросил — так же коротко: «#N бросил — <причина>».
3. **Ответственный — владелец.** `gh issue edit <N> --add-assignee @me` +
   проверка, что в assignees появился логин `gh api user --jq .login`
   (учётка владельца; это не она — STOP). Это осознанное исключение из общего
   правила «assignee — исполнитель»: исполнитель здесь агент, ответственный —
   владелец; фиксируется комментарием. Не назначать сотрудников и не работать
   без assignee.
4. **Два «ок» и две остановки.** До визуального «ок» — ветка локальная:
   запрещены `git push`, PR, мерж, деплой, релиз. Показ — только песочница
   `:4173`. После визуального «ок» — push и PR, затем **СТОП: PR проверяет
   владелец на GitHub**; мерж — только после его «мержи»/аппрува. Оба «ок»
   записываются комментариями в issue.
5. **Только визуальный результат.** Есть кадры «до/после» (обе темы) или
   короткое видео поведения; владелец смотрит живьём. Нет визуального
   «до/после» — баг не кандидат.
6. **Один баг за прогон = один issue = одна ветка = один PR.** Без
   параллельных веток и «заодно»: смежное — комментарий или новый issue.
7. **Бюджет.** Один баг за прогон, ≤ 3 файла, ≤ 150 строк. Не уложился —
   бросай, не растягивай «халтурку» в фичу.
8. **Стоп-кран.** 2 попытки репро / 2–3 итерации фикса без результата —
   бросай: сними assignee, объясни в issue, погаси песочницу. Не чини вслепую.
9. **Никаких продуктовых вопросов.** Размытое ожидание, нужен выбор владельца,
   нет критериев — пропусти. Если в теле есть явная рекомендация — следуй ей.
10. **Риск-поверхность — не халтурка.** Миграции, auth/сессии/токены, RBAC,
    файлы/загрузки, WS/gateway, events/outbox/BullMQ и фан-аут уведомлений,
    новые зависимости/lockfile, API-контракты/новые эндпоинты, infra/CI/Docker,
    секреты/env/конфиги (CORS, rate-limit, debug), пользовательский ввод до
    SQL/shell/файлов/URL/HTML/логов, десктоп, субъективный редизайн. Полная
    карта — DoD; сомнение — STOP и обычный процесс.
11. **Гейты как у всех.** DoD целиком: lint/typecheck/test/build,
    `code-reviewer` до показа, `security-reviewer` только по карте рисков.
    `ui-writer` для точечного визуального фикса **не зовётся** (DoD): кадры
    «до/после» снимает исполнитель, но визуально не судит.
12. **После визуального «ок»** — drift check → push → PR `Closes #N` →
    зелёный CI → **СТОП: проверка PR владельцем на GitHub**. Мерж (squash) —
    только после его «мержи»/аппрува; при PR под учёткой владельца — `--admin`
    по его команде. После мержа — удалить ветку → `git pull --ff-only` →
    отчёт и ретро. Следующий баг — только после закрытия цикла (мерж +
    подтверждение; отказ/бросок — подтверждение закрытия). Релиз на прод —
    отдельной командой «ОБНОВИТЬ ПРОД».

## Выбор бага

```bash
gh issue list --state open --label type:bug --label status:ready \
  --search "no:assignee" --limit 100
```

Дальше по короткому списку:

```bash
gh issue view <N> --json number,title,body,labels,assignees,comments
gh pr list --state open --search "<N>"
git log --oneline origin/main --grep="#<N>"
```

Проверь: нет активного PR/ветки/комментария «беру»; баг воспроизводится на
`origin/main`; в теле есть механизм, ожидаемое поведение и критерии приёмки;
нет продуктового вопроса. `status:draft`/`waiting-trigger` и P0 не брать;
P1 — только если все оси скоринга максимальны.

Скоринг 0–2 по осям (детали и примеры — `references/bug-triage.md`):

| Ось | 0 | 1 | 2 |
|---|---|---|---|
| Визуальность | нет UI-эффекта | косвенный | явное «до/после» |
| Локальность | > 3 файлов / межмодульно | 2–3 файла | 1–2 малых |
| Ясность | нет ожидаемого поведения | механизм без критериев | механизм + решение + критерии |
| Риск | риск-поверхность | shared-компонент/API | чистый UI/текст |

Бери лучший; при равенстве — меньший дифф. Если максимум ниже 7/8 —
«подходящих нет»: покажи 2–3 отклонённых с причиной, не выдумывай баг.

## Процесс

### 0. Preflight

- `git status` — дерево чистое; чужие правки/активная сессия — не стартуй.
- `git fetch origin main`; `pnpm live-stack status` (`:4173` не занят чужой
  песочницей). Свои серверы/порты не плодить — канон `nodus-dev-testing`.

### 1. Взятие

1. Перепроверь assignees; пусто — продолжай.
2. `gh issue edit <N> --add-assignee @me`; проверь, что назначился владелец.
3. Сообщи владельцу номер и одну строку сути.
4. Комментарий в issue: исполнитель — агент, ответственный — владелец,
   ветка `fix/<N>-<имя>`, приёмка на `:4173`, push только после «ок».
5. `git switch -c fix/<N>-<имя> origin/main`.

### 2. Репро и фикс

- `pnpm live-stack up --dev` — **всегда non-mock**; данные — реальным
  конвейером с маркером, за собой чистить (`nodus-dev-testing`).
- Сними «до»: обе темы, нужный экран/состояние; для поведения — короткое
  видео. Не репродьюсится за 2 попытки — бросай по стоп-крану.
- Минимальный дифф + регрессионный unit в том же коммите. UI-строки — i18n,
  цвета — токены темы, без новых зависимостей. `ui-writer` не звать.
- Локальные гейты: lint, typecheck, test, build (что применимо).

### 3. Гейты до показа

```bash
pnpm lint
pnpm typecheck
VITE_API_MOCK=false pnpm test:coverage
pnpm diff-coverage
pnpm build
```

Это каноническая строка DoD для source-диффа («Локальные гейты перед пушем»):
`diff-coverage` — тот же гейт, что в CI; `lint/typecheck/test` его не заменяют.

- `code-reviewer`: задание-минимум «Валидация issue #N: ветка <имя>, база main»;
  вердикт — комментарием в issue. Субагента нет в списке — `general` с ролью
  `.agents/agents/code-reviewer.md` (канон DoD).
- diff неожиданно задел риск-поверхность — остановись: это уже не халтурка,
  вынеси отдельным issue. Если владелец явно оставил фикс здесь — обычный
  процесс и `security-reviewer` по карте.
- Блокеры чини; повторная валидация — только блокеры/security.

### 4. Показ владельцу

- `pnpm live-stack down` → `pnpm live-stack up` (preview) — один раз перед
  вердиктом; держать до ответа.
- Сними «после»: обе темы, те же ракурсы/шаги. Приложи кадры или видео.
- Комментарий в issue + короткое сообщение владельцу: номер, что было/стало,
  URL `:4173`, маршрут, тестовый пользователь (`tests/e2e/e2e-users.json`),
  шаги, обе темы; «ветка локальная, не запушена, жду „ок“».
- **СТОП.** Не пушить, не создавать PR, не мержить. Не писать «выглядит
  хорошо» — только факты; визуальную оценку даёт владелец.

### 5. Вердикт

- **Визуальное «ок»** → записать комментарием в issue → push → PR `Closes #N`
  → дождаться зелёного CI → **СТОП: PR проверяет владелец на GitHub**.
- **«Мержи»/аппрув PR** → squash-мерж, удалить ветку, `git pull --ff-only`,
  финальный отчёт и ретро. Только теперь следующий баг.
- **Замечания на показе** → та же ветка; механические правки — без повторной
  валидации (кроме риск-поверхности), повторный показ. Вкусовой редизайн —
  уже не халтурка: стоп, отдельный issue.
- **Замечания к PR** → та же ветка, fix, push, снова зелёный CI и проверка PR
  владельцем; новый баг не начинать.
- **«Не надо»** → PR закрыть (если создан) с удалением ветки:
  `gh pr close <N> --delete-branch`; локальную — `git branch -D`; песочницу
  погасить, assignee снять, комментарий с причиной; issue остаётся открытым.
- **Владелец недоступен** → ветка/PR и песочница ждут; в issue — состояние и
  как поднять заново; ничего не мержить, следующий баг не брать.

### 6. Финал

Финальный отчёт в issue человеческим языком: что было не так, что стало, как
проверено, где посмотреть; ретроспектива (или «пуста»). На проде исправления
ещё нет — это отдельный релиз. **Следующий баг — только после закрытия
текущего цикла:** мерж PR + закрытый issue + явное подтверждение владельца
(«видела, всё ок»); при отказе/броске — явное подтверждение закрытия (issue
остаётся открытым). Номер снова сообщить. Пока цикл не закрыт — новый issue
не выбирается, даже если он свободен.

## Частые ошибки

- Взял issue с assignee или снял чужого ответственного.
- Забыл сообщить номер владельцу до начала фикса.
- Запушил до визуального «ок» или смержил до проверки PR владельцем — грубое
  нарушение.
- Начал следующий баг, пока текущий PR не смержен и владелец не подтвердил.
- Спросил «какой баг чинить?» — навык выбирает сам.
- Показал без «до/после» или только текстом — владелец не увидел результат.
- Забыл снять assignee после отказа или растянул фикс за бюджет — цикл застрял.
