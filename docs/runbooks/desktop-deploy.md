# Runbook: выпуск и развёртывание десктоп-оболочки Nodus

Аудитория: системный администратор компании (и агент, выпускающий сборки).
Оболочка — тонкий клиент портала (ADR-0019, issue #254): обновление контента
происходит деплоем сервера; этот runbook — про установщики и обновления САМОЙ
оболочки (редко) и про первое развёртывание на машинах сотрудников.

## Модель обновлений (что обновляется как)

| Что | Как обновляется | Участие сисадмина |
|---|---|---|
| Функциональность портала (~99% изменений) | Деплой сервера (`docker compose up`) — все клиенты получают при следующем запуске | деплой сервера |
| Сама оболочка (окно/трей/попапы) | Автообновление с сервера портала: тихо скачивает подписанный установщик из `/desktop/` и ЖДЁТ решения пользователя — зелёная точка на кнопке «Скачать приложение» / пункт трея «Перезапустить» | выложить артефакты в `NODUS_DESKTOP_DIR` |
| Принудительная замена устаревших оболочек | `NODUS_MIN_SHELL_VERSION` на сервере: оболочка ниже минимума показывает экран «обновите приложение» и не пускает к порталу | поднять env при ломающем релизе |

## Ключи подписи (GitHub, однократно)

1. Пара minisign-ключей уже создана: публичный зашит в
   `apps/desktop/src-tauri/tauri.conf.json` (`plugins.updater.pubkey`), приватный
   и его пароль лежат в окружении GitHub **`desktop-signing`**
   (Settings → Environments): секреты `TAURI_SIGNING_PRIVATE_KEY` и
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Окружение требует подтверждения
   владельца (required reviewer) и пускает только ветку `main`.
2. Ключ выдаётся только job'е подписанного выпуска
   (`.github/workflows/desktop-release.yml`) — после кнопки Approve. Сборочный
   гейт `desktop.yml` секретов не читает.
3. Потеря приватного ключа = автообновления мертвы (выпуск новой сборки с новым
   ключом и ручная переустановка на машинах). Резервная копия — в менеджере
   секретов владельца, вне GitHub.
4. id ключа (`773fec9b09efa8a5`) сверяется автоматически при выкладке: подпись
   чужим ключом `desktop-publish.mjs` не пропустит.

## Выпуск сборки

1. Версия оболочки: `apps/desktop/src-tauri/tauri.conf.json` → `version`
   (semver; мажор — ломающие изменения моста, минор — функции, патч — фиксы).
   Отдельный PR, мерж в `main`.
2. Запустить подписанный выпуск:
   `gh workflow run desktop-release.yml --ref main -f notes="<что нового простым языком>"`
   (`notes` видит сотрудник в попапе обновления).
3. Владелец получает уведомление GitHub «Review deployments» → **Approve**.
   Без этого ключ подписи не выдаётся; агент деплой не одобряет.
4. Дождаться успеха: `gh run watch <id>`. В прогоне: сборка NSIS + MSI, подпись
   ключом из окружения (версия в trusted comment ставится автоматически),
   `latest.json` с URL `/desktop/releases/<версия>/…`, самопроверка теми же
   правилами, что применит выкладка.
5. Выложить на сервер портала (забирает артефакт прогона, проверяет подпись,
   id ключа, версию и URL, раскладывает в `releases/<версия>/`, атомарно
   заменяет `latest.json`):
   `node scripts/desktop-publish.mjs --run <id> --dest D:/NodusProd/desktop`
   Версия не перезаписывается: повторный выпуск той же версии отвергается.
6. Проверка: `node scripts/prod-smoke.mjs --desktop-version <версия>` — зелёный
   смок означает, что манифест отдаётся, URL абсолютный, установщик скачивается.
   Затем — живой взгляд: кнопка «Скачать приложение» в шапке, попап с версией и
   примечанием, у запущенной оболочки — зелёная точка «Обновить и перезапустить».
7. **Смена иконки приложения** (в `src-tauri/icons/`): у установленных машин
   ярлык и панель задач могут показывать СТАРУЮ иконку, пока Explorer не
   сбросит кэш (exe уже несёт новую). Действие пользователя: свойства ярлыка
   → «Сменить значок» → выбрать тот же exe; либо `ie4uinit.exe -show`, либо
   перезапуск explorer. Программного гаранта нет (gotchas, «кэш иконок»).

## Аварийный выпуск без CI

Если GitHub недоступен или сборку выпускают с локальной машины (ключ подписи —
в менеджере секретов владельца, вне репо):

1. `pnpm --filter @nodus/desktop exec tauri build` — установщики появятся в
   `apps/desktop/src-tauri/target/release/bundle/{nsis,msi}`.
2. Подписать оба установщика:
   `pnpm --filter @nodus/desktop exec tauri signer sign -f <путь-к-ключу> --app-version <версия> <файл>`.
   **`--app-version` ОБЯЗАТЕЛЕН** (инцидент 16.10: релизы 1.0.7/1.0.8 были
   подписаны без него — обновлятор оболочки отвергает подпись без привязки
   к версии (`requireSignedVersion`, защита от подмены манифеста), ошибка
   видна ТОЛЬКО в логе оболочки, в трее «Проверить обновления» молчит;
   `tauri build` ставит флаг сам, при ручной подписи его забывают).
3. Собрать манифест и каталог выпуска:
   `node scripts/desktop-manifest.mjs --notes "<что нового>" --url-prefix "/desktop/releases/<версия>/" --out <каталог-выпуска>/latest.json`,
   затем положить в этот каталог установщики и их `.sig`.
   **В Git Bash** (в т.ч. на машине агента) аргумент, начинающийся с `/`,
   переписывается в путь Windows — команда падает на проверке формата URL.
   Запускать с `MSYS_NO_PATHCONV=1 node scripts/desktop-manifest.mjs …`.
4. Выложить: `node scripts/desktop-publish.mjs --from <каталог-выпуска> --dest D:/NodusProd/desktop`
   — проверки те же, что в CI (криптографическая проверка подписи, id ключа,
   версия, URL, запрет перезаписи).

## Политика одного канала (анти-дубли версий, #263)

Боль десктоп-Битрикса — по 2–3 версии у одного человека. Правила:

- **NSIS (per-user) — основной канал для людей**: без прав администратора,
  ярлык рабочего стола, автообновление — родной путь. Кнопка «Скачать
  приложение» в шапке портала раздаёт именно его.
- **MSI (perMachine) — только корпоративная раскатка через GPO**; обычным
  пользователям MSI не давать. Никогда не раздавать одному человеку оба
  формата руками.
- Автообновление НЕ прыгает между каналами: манифест несёт отдельные
  target-ключи `windows-x86_64-nsis` и `windows-x86_64-msi`, апдейтер
  выбирает ключ по типу СВОЕЙ установки (NSIS-машина качает NSIS,
  MSI-машина — MSI).
- MSI-машины обновляются раскаткой новой MSI через GPO (тот же
  `upgradeCode` — фиксируется в `tauri.conf.json`
  `bundle.windows.wix.upgradeCode`, смена сломала бы обновляемость на
  «второе приложение»).
- HTTP-портал (ЛВС без TLS): автообновление недоступно (апдейтер принимает
  только https-манифест) — обновление вручную кнопкой скачивания либо
  после настройки внутреннего CA.

## Настройка сервера портала

`.env` (или переменные окружения compose):

```env
# Имя сервера на экране подключения оболочки
NODUS_SERVER_NAME=Название компании
# Минимальная версия оболочки (semver); 0.0.0 — без ограничения
NODUS_MIN_SHELL_VERSION=0.0.0
# Каталог артефактов оболочки: АБСОЛЮТНЫЙ путь на хосте, ВНЕ git-деревьев
NODUS_DESKTOP_DIR=D:/NodusProd/desktop
```

**Путь только абсолютный и только вне git-деревьев.** Относительный
(`./infra/desktop-dist`) резолвится от каталога compose-проекта: при запуске
прода из другого worktree он указал на пустую папку — `/desktop/latest.json`
стал отдавать 404, кнопка «Скачать приложение» молча исчезла, оболочки перестали
видеть обновления (инцидент 02.11, #560). Сегодня обязательность процедурная:
в `.env` прода путь задаётся явно, дефолт compose оставлен для разработки.
С переходом на `compose.prod.yaml` (отдельный issue, прод из готовых образов)
переменная станет обязательной на уровне compose — прод без неё не поднимется.

Раскладка каталога: `latest.json` в корне (стабильный адрес) и
`releases/<версия>/` с установщиками и `.sig` (версии неизменяемы, кладёт их
только `scripts/desktop-publish.mjs`).

nginx web-контейнера отдаёт каталог как `/desktop/`: `latest.json` — `no-cache`,
`releases/*` — `immutable` (версии не перезаписываются). Изменение env требует
`docker compose up -d web api` (api отдаёт `/api/v1/desktop/config`).

## Установка сотрудникам

- **Самостоятельно:** кнопка «Скачать приложение» в шапке портала (видна в
  браузере и в оболочке; попап при наведении — версия и примечание релиза) —
  качает NSIS `Nodus_<версия>_x64-setup.exe` (per-user, без прав
  администратора). Первый запуск: экран «Адрес портала» → ввести адрес →
  вход. Далее — автозапуск опционально (трей → «Запускать при входе в
  Windows»). Повторный запуск установщика поверх — штатное ручное обновление.
- **Корпоративная раскатка (адрес не вводят):** MSI из релиза — в GPO-папку
  (perMachine, тихая установка `msiexec /i Nodus.msi /quiet`), адрес портала
  зашивается build-аргументом при сборке: env `NODUS_PORTAL_URL` на шаге
  `tauri build` (например `https://portal.company.local`). Для зашитой сборки
  закажите её у агента с этим аргументом.
- Windows 10 без WebView2: установщик докачивает bootstrapper сам; для
  изолированной сети положите offline-распространяемый пакет WebView2 рядом
  (докатка вручную).

## Прод-адрес — только HTTPS

Экран подключения принимает и `http://` (разработка/локальная сеть), но для
продуктива используйте `https://` (домен + туннель или внутренний CA): http
открывает окно для перехвата, а страница логина портала соберёт креды в
открытом виде (security-аудит #254). Корпоративная раскатка — зашивайте
`NODUS_PORTAL_URL=https://…` в установщик, сотрудники адрес не вводят.

## Поддержка

- Логи оболочки: `%APPDATA%\by.nodus.desktop\logs\nodus-desktop.log`
  (ротация 8 МБ). Адрес портала: `%APPDATA%\by.nodus.desktop\portal.json`.
- «Нет связи с сервером» на экране подключения — проверьте адрес/сеть;
  кнопка «Повторить» ходит в `GET /api/v1/desktop/config`.
- Смена сервера: трей → «Сменить сервер…» (перезапуск оболочки на экран
  подключения; для зашитых сборок адрес фиксирован политикой сборки).
- Антивирус на рабочих станциях может эвристически ругаться на неподписанный
  установщик: добавьте исключение/дождитесь подписи внутренним CA (ТЗ §13).
