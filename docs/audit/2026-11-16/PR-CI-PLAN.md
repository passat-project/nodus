> **Обновление 2026-11-16 (решения владельца).** Владелец выбрал один PR со многими коммитами и одним прогоном CI; вариант «гейт вперёд» (§3) снят. Правила защиты веток, сводный job и `images.yml` (§4–§6) в ночную работу не входят — остаются планом на отдельную задачу; в #866 из CI входит только отмена прогонов (§4.4). Действующая входная задача для исполнителя — issue #866 (копия тела — `NIGHT-RUN.md`); при расхождении с этим файлом верен #866.

Черновик. Ничего не создано и не изменено: ни ветка, ни PR, ни настройки GitHub, ни workflow.

## 0. Что уже есть — три поправки к исходным посылкам

Перед проектированием сверил текущее состояние (`.github/workflows/ci.yml`, `gh api …/branches/main/protection`, PR #853/#832/#831). Три посылки задания не совпадают с фактом, и это меняет план.

1. **Интеграционные тесты уже в гейте CI.** Job `quality` («lint → typecheck → test → build») поднимает PostgreSQL и Redis и запускает `pnpm --filter @nodus/api test:integration:coverage` и то же для gateway. Там же — `pnpm audit --audit-level high` и покрытие изменённых строк ≥ 80 %. Вне гейта они только **локально** (AUD-033). Значит, «добавить интеграционные тесты в гейт» — не задача; задача — сделать гейт необходимым.
2. **Все три слияния с красным гейтом упали на одном шаге — «Покрытие изменённых строк (diff coverage)».** Это не случайная небрежность: проверка покрытия регулярно красная на изменениях интерфейса, и её обходят. Запретить обход, не решив этот вопрос, — значит остановить работу над экранами.
3. **Админский обход — не нарушение, а записанный канон.** `docs/process/workflow.md:105`: PR агента создаётся под учётной записью владельца, GitHub не даёт автору одобрить собственный PR, поэтому агент сливает через `--admin`. Требование задания «`enforce_admins=true` + обязательное одобрение» в лоб **заблокирует все PR агента**. Нужна конструкция, которая разделяет «обойти одобрение» (можно) и «обойти проверки» (нельзя).

## 1. Ветка

`fix/audit-cutoff-2026-11-16` от актуального `origin/main`. Одна.

По канону ветка называется `fix/<N>-<имя>`, где N — номер issue. Здесь issues группа, поэтому после создания эпика в GitHub ветку стоит назвать по его номеру: `fix/<N эпика>-audit-cutoff`. Имя из задания — рабочее до этого момента.

Канон ограничивает жизнь ветки («дольше 2 дней — режь на фазы»). Эта ветка заведомо длиннее обычной; мера — перебазирование на `origin/main` перед каждым push и коммиты, которые можно вынести в отдельный PR без переделки (см. §3).

## 2. PR

**Причина изменения одна:** «отсечка аудита 2026-11-16». Это допустимо каноном («группа багфиксов / issues одной темы», `CONTRIBUTING.md`, «Группировка issues в один PR»).

**Заголовок:** `fix: отсечка аудита 2026-11-16 — отказоустойчивость, доступ, целостность данных (#<эпик>)`

**Тело:**

**Коммиты:** один коммит на issue, формат канона — `fix(<scope>): <описание> (#N)`. Порядок в ветке:

**Порядок проверки:**

2. `code-reviewer` — весь дифф против `ISSUES.yaml` и определения готовности.
3. Владелец — живьём только то, что видно: AUD-005, 009, 014, 016, 027, 028, 030, 032. Остальное — отчётом.

## 3. Один PR или несколько — моя оценка

По умолчанию — один, как задано. Но честно: **один PR на 32 изменения — рискованная конструкция**, и два условия должны разделить его без обсуждения.

**За один PR:** одна причина; один прогон гейта; владелец получает одну приёмку; изменения в основном не пересекаются по файлам.

**Против:**

- Squash превращает 32 исправления в один коммит `main`. Если после выкатки сломается одно — откатывать придётся все 32 либо чинить вперёд.
- Гейт проверяет PR правилами, которые сам PR меняет (AUD-026). Исправления и изменение правил проверки в одном диффе — плохая практика: красный гейт непонятно чем вызван.
- Проверка покрытия изменённых строк на таком диффе почти наверняка покраснеет на интерфейсной части — ровно тот случай, из-за которого гейт обходили.
- `main` движется параллельной сессией; длинная ветка — постоянные перебазирования.

**Рекомендация — два PR последовательно, а не один:**

| PR | Состав | Зачем отдельно |
|---|---|---|
| **A. Гейт** | AUD-026 (workflow, правила защиты), AUD-033 (локальный гейт) | Маленький, без продуктового кода. После него исправления проверяются уже новым, необходимым гейтом |
| **B. Отсечка** | Остальные 30 issues, одна ветка | Основной PR; одна причина изменения |

Это не «stacked PR» в полном смысле — просто гейт идёт вперёд. Если владелец настаивает на одном PR, план выполним: AUD-026 остаётся последним коммитом, а правила защиты в GitHub включаются **после** слияния.

**Условия, при которых PR B делится дальше** (по фазам, тот же порядок):

- гейт красный дольше двух итераций подряд по причинам, не связанным между собой;
- `security-reviewer` вернул замечания более чем по трём issues Ф1;
- живой репро Ф0 показал, что AUD-020 или AUD-024 требуют изменения схемы или порядка выкатки;
- перебазирование на `main` дало конфликты более чем в пяти файлах.

Разделение дёшево, потому что коммиты уже по одному на issue.

## 4. Единый гейт CI

### 4.1. Конструкция

Сейчас обязательных контекстов три, и ещё два job («E2E формул», «Страж данных») необязательны. Предлагаю **один сводный job `gate`**, который зависит от всех остальных и является единственным обязательным контекстом.

```yaml
gate:
  name: Гейт
  if: always()
  needs: [changes, secrets, quality, migrations, e2e, e2e-formulas, data, compose, docs]
  runs-on: ubuntu-latest
  steps:
    - name: Все проверки прошли
      env:
        RESULTS: ${{ toJSON(needs) }}
      run: |
        # success и skipped допустимы; failure и cancelled — нет
        echo "$RESULTS" | jq -e 'to_entries | all(.value.result == "success" or .value.result == "skipped")'
```

Почему так: `skipped` у job с условием `needs.changes.outputs.code == 'true'` на docs-only изменении остаётся допустимым (сегодняшнее поведение сохраняется), а `cancelled` и `failure` валят гейт. Добавление новой проверки — одна строка в `needs`, без правки настроек защиты ветки.

### 4.2. Состав

| Проверка | Сейчас | В едином гейте | Изменение |
|---|---|---|---|
| `pnpm format:check` | есть | да | — |
| `pnpm lint` (храповик `--max-warnings`) | есть | да | Добавить стража: число в `--max-warnings` не может вырасти относительно `main` |
| `pnpm typecheck` | есть | да | — |
| `pnpm test:coverage` (unit) | есть | да | `VITE_API_MOCK=false` принудительно в тестовом режиме (AUD-033) |
| Интеграционные api + gateway | **есть** | да | — |

| `pnpm build` | есть | да | — |
| `pnpm test:scripts` | есть | да | — |
| gitleaks | есть | да | — |
| `pnpm audit --audit-level high` | есть | да | — |
| E2E критичных путей | есть | да | Сверить набор со списком ниже |

**E2E критичных путей** — сверить фактические спеки с перечнем: вход, письма, чат двух сессий, задачи, формулы, уведомления, файлы, автоматизация. По отчёту аудита (F-20-04) спека создания задачи существует, но в CI не запускается, а пути «письмо → поручение → закрытие» нет вовсе — он появится вместе с #463, не раньше. Добавляемые этим эпиком e2e: смена пользователя (AUD-005), структура > 100 задач (AUD-014), активация сотрудника (AUD-016), подтверждение массового удаления (AUD-027).

### 4.3. Что **не** включаю из запрошенного и почему

| Запрошено | Решение | Причина |
|---|---|---|
| Проверка миграций «обновлением с дампа прод-базы» | **Не в CI** | Дамп прода содержит персональные данные и переписку; класть его в CI (даже в секреты) — утечка. Замена: проверка обновления со **схемы предыдущего выпуска** (`migrate deploy` до тега прошлого выпуска → синтетический сид → `migrate deploy` до HEAD). Обновление на копии прода — ручной шаг runbook перед выкаткой (AUD-024) |
| Проверка заголовков и CSP | Частично | Заголовки ответа проверяются одним шагом в e2e (curl к поднятому стеку). CSP живьём в браузере — отдельная заготовка: сейчас политика не описана как требование, проверять нечего |
| `enforce_admins=true` | **Заменено** | См. §5 |
| Сборка и автообновление оболочки в общем гейте | Условно | Сборка Rust — десятки минут; гонять её на каждом PR бессмысленно. Только при изменении `apps/desktop/**` |

**Покрытие изменённых строк — что делать с причиной обходов.** Проверка остаётся блокирующей на 80 %. Обход заменяется **явным, проверяемым списком исключений** в конфигурации `scripts/diff-coverage.mjs`: чисто презентационные файлы (например, декоративные компоненты без логики), с комментарием-обоснованием у каждой записи. Список меняется только через PR, его видит `code-reviewer`. Это честнее обхода: исключение записано и обсуждаемо, а не сделано молча флагом `--admin`. Порог не снижается.

### 4.4. Отмена прогонов

```yaml
concurrency:
  group: ci-${{ github.event_name == 'pull_request' && github.ref || github.sha }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

PR: новый push отменяет предыдущий прогон той же ветки. `main` и расписание: группа по SHA — каждый коммит получает завершённый прогон.

## 5. Защита ветки

Классическая защита ветки не умеет «обход одобрения — да, обход проверок — нет»: `--admin` снимает всё сразу, а `enforce_admins=true` не оставляет агенту способа слить собственный PR. Поэтому — **наборы правил (rulesets)** вместо классической защиты: у каждого набора свой список обхода.

| Набор правил | Правила | Кто может обойти |
|---|---|---|
| **main — проверки** | Обязательный контекст `Гейт`; ветка актуальна относительно `main`; линейная история; запрет force-push и удаления | **Никто** |
| **main — одобрение** | PR обязателен; 1 одобрение от владельца кода (`CODEOWNERS`); сброс одобрения при новом коммите | Администратор репозитория (в режиме «только для PR») |
| **Теги выпусков** `v*` | Создание, изменение и удаление тега | Только администратор |

Что это даёт:

- PR агента: гейт зелёный → слияние без одобрения проходит, как сейчас. Гейт красный → слияние невозможно никому, включая владельца.
- PR сотрудника: одобрение владельца обязательно, как сейчас.
- Прямые docs-коммиты в `main` (разрешены каноном) — отдельным исключением по путям **не делаются**: наборы правил этого не умеют надёжно. Варианты — в вопросе владельцу 7; технически предпочтительно оставить администратору обход набора «одобрение» и требовать для docs зелёный лёгкий гейт через PR с автослиянием.

**Отдельно решить в AUD-026:** `workflow.md:107` разрешает сливать подъём версии оболочки «без ожидания CI». При наборе «проверки» без обхода это перестанет работать. Решение: для PR, меняющего только `version` в `tauri.conf.json`, детектор `changes` отправляет его в лёгкую полосу (как сейчас «данные-only»), гейт проходит за минуты.

**Перед изменением** сохранить текущую конфигурацию: `gh api repos/passat-project/nodus/branches/main/protection > protection-before.json` — это и есть откат.

## 6. Выпуск образов

`images.yml` уже проверяет форму тега `vX.Y.Z` и что коммит — предок `origin/main`, и запрещает перезапись версии. Остаточный риск — ручной запуск с ветки исполняет файл workflow этой ветки. Меры:

1. Набор правил «Теги выпусков» (§5) — тег `v*` создаёт только администратор.
2. Окружение `release` с ограничением «только ветка `main` и теги `v*`» для job, которому доступен `packages: write`: запуск из произвольной ветки не получит право публикации.
3. `workflow_dispatch` оставить (нужен для пересборки по существующему тегу), но job публикации привязать к окружению из п. 2.

То же для `desktop-release.yml`: ключ подписи — только в окружении `release`.

## 7. Откат

| Что сломалось | Действие |
|---|---|
| До слияния — отдельное исправление | `git revert <коммит>` в ветке либо вынос коммита в отдельный PR |
| После слияния, прод не обновлялся | `git revert` squash-коммита через PR (гейт обязателен и для него) |
| После выкатки на прод | `node scripts/prod-deploy.mjs --version <предыдущая>` — переключение образов без пересборки |
| Миграция | В этой ветке одна (AUD-017), только добавляет строки: старому коду не мешает, восстановления базы не требует. Если в ходе работ появится изменение схемы — expand/contract по навыку `prisma-migrations` и отдельная выкатка |
| Данные испорчены | Восстановление из дампа, снятого перед выкаткой (сейчас вручную по `prod-update.md:25-29`; автоматически — после AUD-024 и #472) |
| Правила GitHub заблокировали слияния | Вернуть `protection-before.json` через `gh api`; наборы правил выключаются переводом в режим «disabled» без удаления |

## 8. Критерий «гейт зелёный»

Гейт зелёный, когда job `Гейт` завершился успешно, то есть **каждая** проверка из §4.2 либо прошла, либо законно пропущена детектором изменений. Не считается зелёным:

- прогон отменён;
- красная проверка «не обязательная, поэтому не страшно» — таких больше нет;
- слияние выполнено в обход;
- интеграционные тесты завершились с нулём выполненных (страж: число тестов в отчёте больше нуля);
- e2e прошли с повторами больше установленного предела (флак — это красный, а не жёлтый).
