# ADR-0038. Модель внимания пользователя: окно на виду, активность и видимая поверхность

- **Статус:** Принят
- **Дата:** 2026-11-11
- **Контекст:** issue #770 (P1, ложное «прочитано» в групповом чате), обсуждение и внешняя сверка с владельцем 11.11.2026; смежные задачи #771 (мультидевайс) и #772 (статус «отошёл»).

## Контекст

Единственным источником «прочитано» были клиентские квитанции видимости
(`use-viewport-read.ts` → `viewport-read-scheduler.ts`), а тот проверял только
`document.visibilityState`. WebView2 в оболочке при скрытии в трей и
сворачивании может оставлять вкладку «видимой» и сохранять
`document.hasFocus()`; к тому же планировщик копил наблюдения в фоне и
отправлял их при возврате. Итог: сообщения мгновенно становились
«просмотрено» у людей, ушедших домой с Nodus в трее или свёрнутым, а та же
ложная квитанция гасила журнал уведомлений и останавливала срочные повторы.

Отдельная проблема сервера: `stopRepeats` по беседе гасил повторы ВСЕХ важных
уведомлений, включая более новое непрочитанное, — прочтение старого сообщения
останавливало срочные повторы того, что пользователь ещё не видел.

Каждый гейт («читать», «гасить попап», «догонять ленту») собирал свой признак:
`document.hidden`, `document.hasFocus()`, `shell-visibility`. Модели
«пользователь действительно смотрит» не было.

## Решение

### 1. Единый источник внимания — `shared/attention/attention-store.ts`

Три уровня (внешняя сверка — Telegram, Element/Matrix, Cinny/Mattermost,
TalkJS/Odoo/Atrium, Nextcloud Talk; подробности — тело #770):

- `windowAttentive` = вкладка видима + окно в фокусе + оболочка видима и в
  фокусе (свёрнута ≠ фокус);
- `userActive` = `windowAttentive` + ввод (клик, клавиша, колесо, касание,
  движение мыши с троттлом 1 с) за последние **30 с** — только это даёт право
  ставить «прочитано» и решает, что «смотрю в чат» для попапов/тостов;
- `presenceActive` = приложение видимо (вкладка + не трей) + ввод за **5 мин**,
  фокус не обязателен — для статуса «отошёл» (#772).

Возврат фокуса считается активностью («вернулся и смотрю» — дочитываем
видимое). Активность истекает по таймеру без событий. Стор без React:
события — passive-слушатели, подписки — обычные колбэки на переходы
`windowAttentive`/`userActive` (не на каждый ввод).

### 2. Видимость поверхности — отдельная ось

Вкладка может быть видимой, а чат — накрытым: карточка под верхней (dormant,
issue #63) или страница под непустым стеком карточек (ADR-0009). Контекст
`shared/lib/surface-visibility.tsx`: `SurfaceVisibilityProvider` (вложенный:
`parent && visible`) — `SliderPanel` ставит `!dormant`, `AppShell` —
`stack.length === 0` вокруг раздела. `useFeedViewportRead` читает
`userActive && surfaceVisible`; накрытый чат не читает и не «открыт» для
гейта попапов (`useConversationHost` снимает регистрацию, `getOpenConversation`
возвращает только видимый хост).

### 3. Поведение источников

- `viewport-read-scheduler.ts`: `canRead()` вместо `isHidden`;
  `observe()` в фоне **не копит** (сообщения, приехавшие в трей, не становятся
  прочитанными), `flush()` отправляет только накопленное при внимании — уход
  фиксирует реально увиденное. `shell-hidden.ts` удалён: сокрытие оболочки —
  часть модели внимания.
- `use-incoming-follow.ts`: лента не догоняет и не компенсирует рост под
  ушедшим пользователем.
- `desktop-notify.ts` и `toast-store.ts`: «смотрю» = `isUserActive()`
  (а не «видимо и в фокусе»); `useReadEntityNotifications` гасит уведомления
  карточки только когда она видима и пользователь активен.
- Сервер: `stopRepeats` по беседе ограничен `source_seq <= upToSeq`
  (как `markReadBySource`): квитанция о старых видимых не гасит повторы более
  нового важного.

### 4. Оболочка сообщает фокус

Контракт `shell-focus { focused }` (+ `DESKTOP_BRIDGE_EVENTS.shellFocus`):
Rust шлёт событие на `WindowEvent::Focused` и `Resized`, где
`focused = focused && !is_minimized()`; повторы дедуплицируются в
`ShellState.shell_focused`. `shell-visibility` (трей) остаётся отдельным
сигналом.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Оставить `document.visibilityState` + `hasFocus()` | В WebView2 minimize/трей не отражаются надёжно (подтверждено кодом bridge/WebView2 и приёмкой); не покрывает «окно на виду, но человек отошёл» | Если Microsoft починит сигналы WebView2 — модель останется, источники упростятся |
| Серверная presence-модель (heartbeat «онлайн» определяет прочтение) | Прочтение — действие клиента; presence не различает «открыто, но не смотрю»; лишняя нагрузка и приватность | Мультидевайсная синхронизация (#771) — как дополнение, не замена |
| Отдельные гейты в каждом потребителе (как раньше) | Именно это дало рассинхрон: три разных ответа на один вопрос | — |
| Требовать ввод для любого «видимо» (без 30-секундного окна) | Невозможно «просто читать»: каждое сообщение требовало бы движения мышью | Если владелец решит ужесточить/ослабить порог — константа в сторе |
| Считать поверхность видимой всегда (без контекста) | Накрытый чат читал и глушил попапы (критерий 4) | — |

## Последствия

- Ложные «прочитано» и гашение уведомлений у ушедших пользователей исчезают;
  «прочитано» появляется после реального возврата внимания (30 с без ввода —
  пауза чтения, критерий владельца 3).
- Попапы и тосты приходят, если человек отошёл от открытого чата: это
  осознанное следствие модели (иначе уведомление не заметят).
- Новый релиз оболочки нужен для `shell-focus` (сборка только CI
  `desktop-release` + Approve владельца); веб-часть работает и без него,
  но сворачивание без события оболочки опирается на focus/blur WebView2.
- Пороги 30 с/5 мин и список событий ввода — константы одного файла; менять
  только вместе с тестами.

## Обоснование (research)

Внешняя сверка в теле #770 (Exa, 11.11.2026): Telegram («marked if visible and
not overlapped and the computer is used»; tdesktop #16188/#4664 — idle не
читает), Element/Matrix (квитанции при active, inactive on blur или 2 мин без
ввода), Cinny/Mattermost (не читать в неактивном окне, дочитывать при возврате
фокуса), TalkJS/Odoo/Atrium (уведомление не гаснет, если открытый чат не в
фокусе), Nextcloud Talk (Page Visibility + dead-man switch 180 с). Модель
повторяет консенсус зрелых мессенджеров; порог 30 с — консервативнее
Nextcloud, но внутри обсуждённого с владельцем.
