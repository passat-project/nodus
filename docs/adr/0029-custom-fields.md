# ADR-0029. Кастомные поля: реестр определений, JSONB-значения, участие в процессах

- **Статус:** Принят; частично отменён ADR-0037 (одна область — атрибут на весь портал, формулы, удаление с перечнем последствий)
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 23.10 (ответы 29, 33, 62, 63, 66: «как в ClickUp, не как в Битриксе — поля должны участвовать в процессах, фильтрах, реестрах, отчётах»), запись инкубатора 24.09, #427. Актуализирует задел `FieldDefinition` в `data-model.md` и модуль `custom-fields` из `modules.md`.

## Контекст

Без полей не собрать ни письма (корреспондент, подписант, их №/дата), ни заявки (дата, часы, проект), ни комплекты («№ накладной», «дата передачи»). В Битриксе пользовательские поля только отображаются — владелец назвал это «полной чушью».

## Решение

1. **Модуль `custom-fields`** (ядро): реестр определений по областям `task | letter | project | counterparty`; область `node` зарезервирована (узел — папка без полей, вердикт 24.10). Вкладка раздела «Автоматизация» (в интерфейсе — «Атрибуты», см. дополнение #431); тип процесса выбирает поля из реестра или создаёт на месте (ADR-0024).
2. **Типы полей:** текст, длинный текст, число (точность), деньги (сумма + валюта из справочника), дата, дата-время, продолжительность (минуты, «ч:мм»), флаг, словарь (один / несколько — по id элементов `dictionaries`, I15), сотрудник (один / несколько), проект, контрагент, ссылка/путь (URL или путь `\\сервер\…`: в десктопе — «Открыть в проводнике», в вебе — «Скопировать путь»). Тип «файл» — V2 (файлы задач живут в чате).
3. **Хранение:** значения — JSONB `custom_fields` сущности, ключ — id определения (переименование поля безопасно). Валидация на границе API — zod, собранная из определений. Индекс GIN `jsonb_path_ops`; для полей с флагом «индексировать для отчётов» — функциональные индексы / генерируемые типизированные колонки. Удаление — архивация; смена типа — только совместимая.
4. **Участие в процессах:** формы создания и карточки (ADR-0024); раздел «Дозаполнить поля» окна перехода и гейт `fields_required` (ссылки на системные и кастомные поля); фильтры списков, реестры, выгрузка; источник решающих «поле „Сотрудник“» (ADR-0025); значения по умолчанию, включая снимок на момент создания («подразделение автора» — для аналитики по подразделениям при переводах сотрудников).
5. **События:** `custom_field.definition_changed`; изменение значения — в событии изменения сущности (`task.updated` и аналоги) с кодом поля и старым/новым значением.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| EAV (строка на значение) | Каждое поле — соединение; значения текстом | — |
| Колонка на поле (миграция на каждое поле) | Новое поле = релиз; противоречит I15 | Горячие поля продвигаются генерируемыми колонками |
| Поля «для отображения» (Битрикс) | Не участвуют в процессах — владелец против | — |

## Последствия

**Проще:** новое поле — данные, без релиза; поля сразу работают в формах, окнах, фильтрах и реестрах. **Сложнее:** динамическая валидация и рендер; сортировки по полям без индекса медленнее (флаг «индексировать для отчётов»); BI-представления по типам — позже.

## Обоснование (research)

- AWS Database Blog «PostgreSQL as a JSON database: advanced patterns» (2025): выражения и частичные индексы для частых ключей.
- «JSONB without regret» (2025): GIN — для вхождения, B-tree — для сортировок и диапазонов, продвижение горячих полей.
- ClickUp custom fields; Яндекс Трекер — типы «продолжительность» и «деньги» (06.2026).

**Замена архива скрытием (вердикт владельца 25.10.2026).** `archivedAt` у определения убран: вместо него `hidden`. Скрытый атрибут живёт для процессов, автоматики и отчётов, но не виден никому в карточках, фильтрах и окнах переходов. Удаление — физическое (`DELETE …/:id`, 204), значения стираются: запрещено, пока атрибут стоит в окне или условии «Заполнены поля» опубликованного маршрута (409 `CUSTOM_FIELD_IN_USE` со списком процессов). Причина: владелец не приемлет «архив вместо удаления» — тестовый мусор должен исчезать. Лимит 100 и уникальность имени считаются по ВСЕМ атрибутам области, поэтому уникальность — выраженный индекс `(scope, lower(btrim(name)))`, а не partial.

**Термин.** В интерфейсе — «Атрибуты» (вкладка «Автоматизации», блок карточки, группа фильтра, подгруппа редактора маршрута). В коде и контрактах остаётся `custom field` / `customFields`: ключи API и таблиц не переименовываются.

**Где живёт валидация.** Одна точка на сервере — порт `CUSTOM_FIELD_REGISTRY` (`definitions`, `prepareCreate`, `prepareUpdate`, `refs`). Модули-владельцы сущностей не читают `field_definitions` и не проверяют значения сами (I3/I7). Грамматика типов — общая в `packages/contracts/src/custom-fields/custom-field-values.ts` (исключение «общая грамматика» из `patterns.md`).

**События и ключи.** `custom_field.definition_changed {definitionId, change: created|updated|deleted|reordered, fields?}` — каталожное (gateway рассылает всем); `task.updated` несёт `customFieldChanges[{fieldId, from, to}]` и ключи `cf.<id>` в `fields`. Ключ `cf.<uuid>` — общий для окна перехода и гейта `fields_required`; неизвестный (удалённый) ключ переход не блокирует, публикация даёт ошибку `custom_field_unknown`, существующий, но не привязанный к типу процесса — `custom_field_not_in_type` (глобального `hidden` нет — О2 #631).

## Дополнение (#432)

**Атрибут принадлежит типам процессов** (вердикт владельца 26.10, В2): тип видит только свои атрибуты — в карточке, окне создания, окнах переходов и условиях. До этого привязки не было, и все атрибуты области были видны везде.

| # | Отклонение | Почему | Последствия |
|---|---|---|---|
| О3 | **Привязка `field_definition_types` (атрибут × тип)**: показ, выбор, умолчания и запись — по привязке | В2; «набор полей по типу» из #431 не был реализован | Новая таблица; `customFieldDefinitionSchema.typeIds`; 422 `not_in_type`; фильтр `GET /definitions?typeId` |
| О3а | **Умолчания применяются только у привязанных атрибутов** | Иначе умолчание «протекало» бы в тип, которому атрибут не принадлежит | `prepareCreate({ typeId })` считает умолчания по привязанным определениям |
| О3б | **Снятие привязки блокируется, пока атрибут работает в опубликованном маршруте типа** (окно, условие, форма создания) — 409 `CUSTOM_FIELD_IN_USE` | Иначе уже работающий маршрут стал бы невалидным без ведома администратора | `workflowsUsingField(scope, fieldId, { typeId })` |
| О3в | **Копия типа копирует привязки основы** | Окна скопированного маршрута ссылаются на те же атрибуты; без привязок публикация копии падала `custom_field_not_in_type` (нашла живая проба) | `copyTypeBindings` при создании типа «копией» |
| О3г | **Очистка (`null`) значения непривязанного атрибута разрешена всегда**, запись — 422 | Снятие привязки не должно блокировать уборку старого значения в карточке | `prepareUpdate`: `null` проходит, значение — `not_in_type` |
| О3д | **Неизвестный ключ — `unknown`, существующий но непривязанный — `not_in_type`** | Клиент различает опечатку в id от «атрибут есть, но не для этого типа» | Причины `CustomFieldIssueReason`; тексты в i18n веба |

**Бэкфилл при миграции** (`20261030120000_type_forms_card`): привязки восстанавливаются по уже заполненным значениям задач и по использованию в опубликованных маршрутах (форма создания, окна переходов, условия «Заполнены поля»). Без бэкфилла введение привязок спрятало бы заполненные атрибуты.

**Событие и аудит:** привязка/снятие — `custom_field.definition_changed { change: 'updated', fields: ['typeIds'] }` + аудит `custom_field.bind` / `custom_field.unbind`; обе операции идемпотентны (повтор не ошибка).

## Дополнение (02.11): область «Папка» и путь к файлу

- **Резерв области `node` активируется** (ADR-0030 «Дополнение (02.11)», #556): атрибуты привязываются к видам папок структуры так же, как к типам задач (#432), с формой создания вида (скрыто / по желанию / обязательно); значения — JSONB узла по id определения, валидация — порт `CUSTOM_FIELD_REGISTRY`. Вердикт 24.10 «узел без полей» уточнён: поля есть только у видов, которым их назначили; аналитика по-прежнему собирается с работ.
- **Тип «Ссылка или путь» (Р11)**: в десктоп-приложении для UNC-путей разрешённых серверов — «Открыть» и «Показать в папке» (исполняемые и ярлыки не запускаются); в браузере — по-прежнему «Скопировать путь» (#558). Путь к файлу комплекта — временная замена файлового модуля: при его появлении значения путей станут версиями документов.

## Реализация (#556, 03.11.2026)

- **Скоупинг реестра `fieldIds`.** Порт `CUSTOM_FIELD_REGISTRY` принимает `{typeId}` (типы процессов, #432) ИЛИ `{fieldIds}` (форма вида папки, #556): оба сразу — ошибка программиста. При `fieldIds` умолчания и валидация — только атрибутов формы вида, порядок — реестра; значение существующего, но не входящего в форму атрибута — 422 `not_in_type` (текст нейтральный: «не входит в форму этого типа или вида папки»), очистка `null` разрешена всегда.
- **`refsMany`** — ссылки пачкой по списку карт значений: срез структуры проекта отдаёт значения всех папок одним набором ссылок (дедуп `kind:id`, одна пачка запросов на вид ссылки). `refs` делегирует `refsMany([values])`.
- **Область `node` активна**: CHECK `field_definitions_scope_check` включает `node`, `SCOPE_ORDER` — «задачи, письма, проекты, папки, контрагенты», в окне атрибута — подсказка области.
- **`usage.nodeKinds`**: окно удаления атрибута показывает виды папок, держащие атрибут в форме (архивные тоже). Использование видами удаление НЕ блокирует (вердикт 25.10 — удаление стирает значения).
- **Уборка значений удалённого атрибута** — обработчик `ProjectFieldValuesCleanupHandler` в модуле projects (без проверки фичефлага, идемпотентен): `custom_fields - key` в `project_nodes` (область `node`) и `projects` (область `project`, закрывает F1), плюс удаление слота из форм всех видов с событием `project.node_kind_changed` на каждый переписанный вид. Имя класса уникально: диспетчер различает обработчики по имени класса.
- **Мёртвый `DefinitionsRepository.countValues` удалён**: читатель значений выбирается по области — задачи через `CUSTOM_FIELD_VALUES_READER`, проекты и папки через новый порт `PROJECT_FIELD_USAGE_READER` (счёт и `nodeKindsUsing`).

## Дополнение (05.11, ADR-0037) — атрибут на весь портал и формулы

- Вместо одной области на определение — **один атрибут на портал** с привязками «Где используется»: типы задач и писем, типы проектов, виды папок, виды реестров, «Компания». Название уникально без учёта регистра; внутренний номер — ключ значений и формул.
- Новые типы данных: **ссылка на любую запись** (задача, письмо, папка, проект, строка реестра); варианты списков получают цвета.
- **Формулы** в ячейках: значение или «=формула», формула по умолчанию у типа, подстановки в окнах (ADR-0037 п.3).
- **Удаление** разрешено всегда — с перечнем последствий и подтверждением вводом названия; запрет удалять атрибут, стоящий в опубликованном маршруте, снимается.
- Системные поля сокращаются до минимума ядра (ADR-0037 п.1): шифр проекта, код папки, заказчик становятся атрибутами; перенос данных — expand/contract.

## Дополнение (06.11, #631) — реализация «атрибут на весь портал»

Зафиксированные отклонения от буквы предыдущих решений (утверждены техпланом #631):

- **О1 — ключ значений остаётся UUID.** Внутренний номер `number` (sequence, уникален, не переиспользуется) — адрес атрибутов в формулах #632; ключи значений в JSONB сущностей и `cf.<id>` в маршрутах НЕ переписываются на номера: UUID уже стабилен, перепись прод-данных риска без пользы. Реестр отдаёт карту номер→id.
- **О2 — глобального `hidden` нет.** Видимость — у формы места: слоты `hidden/optional/required` в формах видов папок и типов проектов, форма создания маршрута — у типов задач/писем. «Спрятать отовсюду» = снять все привязки (значения живут). Определения с `hidden=true` мигрировались снятием привязок и вычищением слотов из форм видов.
- **О3 — снят 409 `CUSTOM_FIELD_IN_USE`** и с удаления, и с отвязки: удаление разрешено всегда (окно последствий + ввод названия), отвязка тем более. Опубликованные маршруты с ключом удалённого атрибута продолжают работать (толерантность unknown), повторная публикация — `custom_field_unknown`.
- **О4 — лимита 100/область больше нет** (областей нет): продуктового лимита нет, технический потолок портала 1000 (`CUSTOM_FIELD_LIMITS.portal`, страховка зацикленных скриптов; в UI не светится).
- **Привязки** — единая таблица `field_bindings(definition, target_kind, target_id)` вместо `field_definition_types` и неявной привязки формой вида: слот формы места и запись в пикере «Где используется» пишут одну таблицу; добавленный слот привязывает, снятый — снимает, но привязка без слота законна (посев системных полей на все места, точечная привязка диалога) и записью формы не сносится. Целостность цели (существует/не архивный тип процесса) проверяет сервис, FK полиморфной цели не заводится.
- **Глобальные переменные** (`isCompany`): привязок нет, значений у записей нет; значение — одна строка `company_values` на компанию, правится `custom_field.manage` из реестра; чтение — всем аутентифицированным (настройки компании, не секрет). «Переменная vs константа» — до #634 всё константы.
- **Системные поля — атрибуты**: посев миграцией под детерминированными uuidv5 (`SYSTEM_FIELD_IDS` в contracts) с поглощением одноимённых того же типа и переносом значений из колонок `projects.code/client_id`, `project_nodes.code`; формы типов проектов получили слоты из `code_field`; уникальность шифров/кодов снята (дубли разрешены, В2); колонки заморожены до отдельного chore.
- **Ссылки на записи** (типы `task`/`letter`/`node`): проверка видимости актёра портами владельцев (`TASK_REF_READER`, `LETTER_REF_READER`, `NODE_REF_READER`); читатель без доступа видит `name: null`, удалённая цель — `name: null` + `archived: true` («Запись удалена»). Слоты-«реестры» добавит #636: CHECK `field_bindings.target_kind` в миграции #631 допускает только `process_type|project_type|node_kind`, член `registry_kind` расширяется отдельной миграцией #636.
- **usage-агрегат** (окно удаления): значения по пяти видам сущностей (задачи, письма, контрагенты, проекты, папки; счётчики включают мягко удалённые записи — уборка стирает и их), формы (создания типов процессов, включая непубликуемые черновики; типы проектов; виды папок), опубликованные маршруты (окна, валидаторы, условия решающих `decider_in`), привязки с именами целей, факт глобального значения. Места поиска маршрутов — четыре (ранее три, добавлен `decider_in`). Контрагенты добавлены дополнением #646: колонка `counterparties.custom_fields` переписывается миграцией #631, поэтому счётчик и уборка подключены до появления путей записи (Н2 CRM).

## Дополнение (06.11, #632) — формулы в ячейках атрибутов

- **Формула — способ заполнить ячейку, не тип атрибута.** Приоритет: своя формула > своё значение (вписанное руками) > формула типа/вида > пусто. Собственная формула материализует результат обычным значением атрибута (`custom_fields`), поэтому фильтры, ссылки, события и виды читают его без специальных веток; формула типа/вида вычисляется на чтении (Р6 плана #632).
- **Новый пакет `packages/formula-engine`** (зеро зависимостей, зависит только от `@nodus/contracts`): одна реализация вычисления для API, MSW-моков и редактора — parity моков по построению. Внешние движки отклонены: HyperFormula — GPLv3/коммерческая, несовместима с Elastic-2.0; строковый Excel-парсер не нужен — вход конструктор плашек.
- **Язык — типизированный AST из плашек, хранение JSON.** Адресация атрибутов по внутреннему `number` (переименование ничего не ломает); `field_bindings.default_formula` — формула по умолчанию у типа/вида; слоты окон создания/перехода получают `formula`. Матрица «носитель → допустимые источники» и каталог функций — в contracts, одна для редактора, моков и сервера.
- **Безопасность структурная.** Формула видит только своё дерево проекта и общие данные (компания); конфиденциальные записи исключены из выборок ДЛЯ ВСЕХ (вердикт В1 06.11), секретные проекты недоступны по построению. Фильтрация — в резолверах портов владельцев, движок не умеет читать мимо них.
- **Значения списков в формулах — подписи вариантов** (резолвер разворачивает id → имя); при материализации в поле-список сервер сопоставляет подписи с id словаря. Ссылки на записи остаются id.
- **Ошибки как в Excel, работа не блокируется:** каталог runtime-кодов ячейки (`attribute_deleted`, `type_mismatch`, `cycle`, `division_by_zero`, `selection_limit`, …) хранится в `formula_cells.error` и приезжает в DTO `customFieldFormulas`; статические отказы сохранения — 422 `FORMULA_*`.
- **Событие `custom_field.formula_changed`** — адресное (аудитория хоста), не каталожное: broadcast раскрывал бы hostId конфиденциальных записей (О4 плана).
