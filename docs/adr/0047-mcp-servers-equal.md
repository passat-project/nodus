# ADR-0047. MCP-серверы равнозначны: один реестр, все инструменты, без «по умолчанию»

- **Статус:** Принят
- **Дата:** 2026-11-18
- **Контекст:** вердикт владельца 18.11.2026 на живой приёмке #902/#901; I11 (исключения — через ADR), ADR-0043 п. 10 (реестр MCP), ADR-0046 (Exa как исключение для интернета), #899 (планируемые действия).

## Контекст

В #902/#901 в реестре MCP-серверов появилось поле «По умолчанию для поиска», а агент выбирал один сервер (`resolveForSearch`) и подключал только его инструменты Exa. Это ошибочная модель: MCP — не «точечный поиск», а протокол подключения ЛЮБЫХ внешних инструментов (Blender, GitHub, склад, 1С, поиск). У компании может быть десять поисковых серверов и ещё десять непоисковых; все включённые должны быть равнозначны, а «назначить Blender поиском по умолчанию» — бессмыслица. Владелец прямо отклонил чек-бокс и саму семантику выбора.

## Решение

1. **Признак `default_for_search` удалён** из контрактов, БД (миграция `20261127150000_mcp_servers_equal`), API, DTO и экрана настроек. Нельзя выбрать «главный» сервер, потому что главного нет.
2. **Агент получает инструменты ВСЕХ включённых серверов**: `McpSettingsService.resolveEnabled()` возвращает список, `externalMcpTools()` на старте прогона читает `tools/list` каждого и регистрирует `ext.<slug-сервера>.<инструмент>` (стабильный слаг из имени, уникальность при совпадении, потолки имени/описания). Сломанный сервер пропускается и не валит прогон.
3. **Прогрессивное раскрытие, как у зрелых MCP-клиентов (проверено через Exa)**: Exa и первые 3 инструмента каждого сервера (всего ≤12 внешних) попадают сразу в native `tools` — модель видит имя и вызывает БЕЗ дополнительного шага, ровно как `ext.exa.web_search_exa`. Остальные остаются в полном каталоге и находятся нашим `tools.search` (лексический meta-tool по имени сервера/инструмента); 50+ определений в контексте стоят десятки тысяч токенов и ухудшают выбор инструмента. В системный промпт уходит компактная сводка «сервер → человеческие названия инструментов», чтобы модель знала, что подключено, ещё до поиска. Названия в сводке и строках вызовов — человеческие («Интернет: поиск», «Git MCP: echo»), сырые id вроде `web_search_exa` в ленту и промпт не уходят.
4. **Exa остаётся особым случаем только по качеству схем**: для `mcp.exa.ai` регистрируются `ext.exa.web_search_exa` / `web_fetch_exa` с лимитами запроса ≤ 400 символов, чтения ≤ 8 000 и правилами ссылок (ADR-0046). Это не привилегия «по умолчанию»: сервер подключается наравне со всеми, просто у его инструментов точная валидация. П. 2 ADR-0046 («единственный внешний сервер») заменяется данным ADR.
5. **Аргументы и результат**: generic-инструменты принимают объект аргументов как есть (валидирует сам MCP-сервер), сигнал «Стоп» прокидывается в вызов, результат обрезается `maxToolResultChars`, текст ошибок сервера очищается от ключа (`McpClient.redact`). Внешние результаты приходят модели в блоке `<data tool>` и считаются внешними данными, не данными портала (правила промпта `external`).
6. **Границы действий**: `kind: read` у каталога — это защита от изменений ДАННЫХ ПОРТАЛА без подтверждения (#899). Внешние MCP-инструменты действуют во внешнем сервисе, который администратор сам подключил; подтверждение для них появится вместе с общим механизмом действий (#899), отдельной модели принятия решений не будет.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
| --- | --- | --- |
| Один «поисковый» сервер по умолчанию | MCP ≠ поиск; владелец отклонил на приёмке | Никогда |
| Жёстко зашитые инструменты только Exa | Реестр тогда декоративный; нельзя подключить Blender/другой поиск | Никогда |
| Все инструменты на горячей полке | Промпт раздувается до тысяч инструментов | Появится отдельный шелф с явным выбором админом |
| Отдельный ADR на каждый сервер | Настройка, а не архитектурное решение (ADR-0043 п. 10) | Никогда |

## Последствия

**Проще:** администратор добавляет любой MCP-сервер — агент сразу видит его инструменты; нет гонки за «главный», нет миграции настроек при добавлении второго сервера.

**Сложнее:** на старте прогона читается `tools/list` каждого включённого сервера (таймауты уже есть); для generic-инструментов нет zod-схем по полям (валидирует сервер); редкие инструменты требуют одного шага `tools.search`.

**Риски и меры:** сломанный/медленный сервер — пропуск и лог, прогон живёт; слишком много инструментов — не горячая полка + `tools.search`; внешние тексты — `<data tool>`, redact, лимит; приватность — правила промпта и аудит `assistant_tool_calls.args` (как в ADR-0046).

## Обоснование (research)

- Model Context Protocol, спецификация 2025-06-18: `tools/list` — штатный способ обнаружения инструментов сервера, `tools/call` — вызов; сервер сам владеет схемой инструмента. Клиент не должен знать заранее, поисковый сервер или нет.
- MCP «Client Best Practices» (modelcontextprotocol.io): при десятках серверов и сотнях инструментов грузить все определения в контекст нельзя — рекомендован порог 1–5% контекста и прогрессивное раскрытие; для небольшого набора грузить всё сразу нормально; группировать инструменты по серверу и давать модели сводку категорий в системном промпте.
- Anthropic «Advanced tool use» (2025-11-24): 50+ MCP-инструментов ≈ 72K токенов до начала диалога; Tool Search Tool снижает до ~8,7K (−85%) и повышает точность выбора (Opus 4: 49% → 74%); рекомендация — «держать 3–5 часто используемых инструментов всегда загруженными, остальные отложить»; включать при >10 инструментах.
- Claude Agent SDK «Scale to many tools with tool search»: точность выбора падает при >30–50 инструментов, до ~10 инструментов выгоднее грузить всё сразу; поиск сопоставляет имена и описания — описательные имена важны.
- ADR-0043 п. 10: реестр MCP — настройка, а не код; ADR-0046: hosted Exa — исключение I11, но не монополия на внешние инструменты.
