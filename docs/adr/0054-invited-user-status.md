# ADR-0054 — Приглашённый сотрудник — пользователь со статусом `invited`

**Статус:** принято (23.11.2026, #101)
**Контекст:** до этого учётку создавал prisma-сид: для пилота хватало, для перевода отделов нужна штатная выдача доступа без разработчика. Отправка письма отложена (#991), поэтому приглашение — ссылка, которую админ передаёт вручную.

## Решение

1. **Приглашённый — реальная строка `users` со статусом `invited`**, а не отдельная invitation-сущность. В общем списке «Сотрудники» строка видна с чипом «Приглашён»; в структуре, пикерах, поиске, ролях и назначениях — нет (те же фильтры `status = active`, что у уволенных). Отдельного раздела «Приглашённые» нет.
2. **Пароля до активации нет:** `users.password_hash` допускает NULL. Вход по email приглашённого отвечает `403 AUTH_ACCOUNT_NOT_ACTIVATED` до проверки пароля (анти-enumeration осознанно ослаблен — корпоративный портал; троттлинг входа сохраняется).
3. **Токены — `user_tokens`:** в БД только SHA-256, сырой токен отдаётся один раз. `kind: invite | reset` (CHECK), `expires_at`, `used_at`, `revoked_at`, `created_by` (голый UUID без FK, как audit). Приглашение — 7 дней, сброс — 24 часа. Одноразовость — CAS одним `UPDATE … WHERE used_at IS NULL`, отзыв — `revoked_at` при перевыпуске/отмене.
4. **Активация = принятие приглашения:** сверка рабочей почты (без учёта регистра), пароль по общей политике, `status = active`, `activated_at = now`, базовая роль `employee`, если прямых ролей нет. Сессию модуль directory не создаёт: фронт входит обычным `/auth/login` (I3/I6).
5. **Истечение:** строка, которую никогда не активировали (`activated_at IS NULL`), удаляется; у бывшего сотрудника возвращается статус `deactivated` — история цела. То же правило — у ручной отмены, сразу. Job раз в час, `FOR UPDATE SKIP LOCKED`, событие `directory.invitation.expired` + аудит.
6. **Сброс пароля:** только `active`; себе — запрещено (`DIRECTORY_SELF_RESET`), уволенного сначала возвращают в работу («Вернуть в работу»), затем выпускают ссылку. Админ не придумывает пароль и не знает его. Выпуск ссылки гасит сессии сотрудника и действующие access-токены (стоп-лист #333) событием `directory.user.password_reset_issued`; установка нового пароля повторно гасит сессии, созданные до события.
7. **Запреты сервера:** приглашённому нельзя выдать роль (`PATCH /users/:id` с `roleIds` → 409), сделать главой/замом (`ReferenceGuard` требует `active`), назначить исполнителем/участником/решающим (`filterActiveUserIds` уже отсекает не-активных), вызвать старые `activate`/`deactivate` (409).
8. **Токен не попадает в логи, аудит и Redis-идемпотентность:** сегмент пути после `/invitations/` и `/password-resets/` маскируется (`maskTokenPath`), публичные префиксы исключены из `IdempotencyInterceptor`, а админские маршруты, возвращающие СЫРОЙ токен (`POST /directory/invitations`, `…/reissue`, `POST /directory/users/:id/password-reset`), не кэшируются механизмом идемпотентности вовсе — иначе действующий токен лежал бы в Redis открытым текстом 24 часа. nginx не пишет access-log для SPA-путей `^/(invite|reset)/` и отдаёт их с `Referrer-Policy: no-referrer`.
9. **Сверка почты — UX-подтверждение, а не защита:** держатель ссылки видит email в `GET /invitations/:token` (bearer-токен, осознанно — префилл формы). Реальной защитой станет доставка ссылки на рабочую почту (#991), а не ввод того же email на странице.
10. **Сброс пароля — право `user.manage`** вместе с `directory.manage`: каталог прав отводит сброс паролей именно `user.manage` («Блокировать вход и сбрасывать пароли»); это защищает от будущего делегирования `directory.manage` (HR, #816) без права на захват учёток. Самому себе сброс запрещён на сервере (`DIRECTORY_SELF_RESET`): это действие над другим сотрудником. Сессии гасятся событием на момент выпуска ссылки, там же ставится стоп-лист access-токенов — доступ пропадает сразу; авто-вход после установки нового пароля выпускается позже маркера.
11. **Границы, зафиксированные осознанно:**
    - держатель `user.manage` сегодня — только администратор; при делегировании этого права (HR) нужен гейт иерархии «права цели ⊆ права актора», иначе он сможет выпустить ссылку себе и войти в любую учётку. Сейчас эскалации нет: у admin все права;
    - базовая роль `employee` (`directory.read`, `task.create`) выдаётся при активации без bind — системная роль-минимум, осознанное исключение из правила #490;
    - ссылка сброса не блокирует вход старым паролем до её принятия; «заморозить учётку» — отдельный сценарий, не в этом ADR;
    - сверка почты на странице принятия — UX-подтверждение (email виден держателю ссылки), а не защита: защитой станет доставка на рабочую почту (#991).

## Осознанные отклонения

- **O1.** Вход по email до активации отвечает отдельным кодом — анти-enumeration ослаблен (корпоративный портал, адрес коллегам известен); троттлинг входа сохранён.
- **O2.** Авто-вход после установки пароля (OWASP рекомендует обычный вход): фронт делает `logout` прежней сессии (если была) → `accept` → `login`. MFA в продукте нет.
- **O3.** Приглашённый = строка `users`: мёртвые строки до истечения закрываются job’ом.
- **O4.** Публичные эндпоинты вне `/auth` исключены из idempotency-кэша: accept одноразовый по CAS токена; повтор с новым ключом получает `INVITATION_ALREADY_USED`.
- **O5.** Сброс пароля гасит refresh-сессии, действующие access-токены (стоп-лист #333) и открытые WebSocket-соединения (gateway рвёт сокеты по событию и проверяет стоп-лист на хендшейке): доступ закрывается сразу, включая реалтайм. Авто-вход после принятия ссылки выпускает токен позже маркера; если вход случился в первые секунды запаса, SPA чинится штатным прозрачным refresh. При появлении MFA пересмотреть.
- **O6.** Сырой токен идёт путём URL — маскирование в логах/аудите, `no-referrer`, троттлинг по хешу токена; при #991 тот же путь.

## Последствия

- Новый статус расширяет `UserStatus`; чтения, которые раньше делили «active | deactivated», обязаны явно решать про `invited` (пикеры/поиск/структура уже фильтруют `active`).
- `password_hash NULL` — backward-compatible: старый код читал только `active`, а теперь проверяет NULL до verify.
- Миграции expand-only: `ALTER TYPE … ADD VALUE` отдельной миграцией, затем nullable-колонки и `user_tokens`.
