# ADR-0036. Прод портала из готовых образов: сборка по тегу, прод-каталог без исходников

- **Статус:** Принят
- **Дата:** 2026-11-02
- **Контекст:** инциденты #560 (молча пропала раздача десктопа) и #561 (api перестал видеть конвертер). Оба — один класс: прод собран из рабочего дерева `../nodus-rel`, конфиг разъехался с основным деревом, «что сейчас на проде» определялось каталогом, из которого случайно запустили `docker compose`. ADR-0004 уже фиксирует целевое: прод обновляется по тегу через `pull`; этот ADR описывает реализацию для нашего хоста.

## Контекст

Прод обслуживался так: `git switch --detach vX.Y.Z` в отдельном worktree → `docker compose up -d --build`. Следствия:

- конфиг прода (`.env`, смонтированные каталоги, профили) живёт в git-дереве и дрейфует между worktree;
- сборка на хосте занимает минуты и зависит от состояния рабочего дерева;
- откат = пересборка предыдущего тега (те же минуты + риск, что сборка не повторится);
- любая команда `docker compose` из другого каталога создаёт контейнеры с другим `working_dir` — так 28.10 конвертер выпал из сети api, а 27.10 раздача десктопа указала в пустую папку.

Требование владельца (02.11): прод не должен зависеть от того, из какого каталога его запустили; откат — быстро; десктоп и портал раздаются с нашего сервера; клиентские коробки остаются zero-cloud.

## Решение

1. **CI собирает образы один раз по тегу** (`.github/workflows/images.yml`): `ghcr.io/passat-project/nodus-{web,api,gateway}:X.Y.Z` + `:sha-<short>`. Повторная публикация той же версии запрещена (`docker manifest inspect` перед push), digest пишется в summary прогона. Web собирается с `VITE_API_MOCK=false`.
2. **Прод-каталог `D:\NodusProd` — единственный источник прода на хосте:** `.env` (боевой), `kit/v<версия>/` (compose-файлы из тега), `desktop/` (раздача оболочки), `backup/`, `deployments.log`. Исходников и `.git` нет.
3. **Прод-оверлей `compose.prod.yaml`** поверх базового compose: `build: !reset null`, `image: …:${NODUS_VERSION}`, `pull_policy: missing`; для web — `volumes: !override` с обязательным абсолютным `NODUS_DESKTOP_DIR`. Прод без переменных не поднимается (громкий отказ вместо молчаливого дефолта).
4. **Выкатка и откат — только `scripts/prod-deploy.mjs`:** kit из тега через `git show` (рабочее дерево не трогается), запись `NODUS_VERSION`, `config --quiet` → `pull` → `up -d`, ожидание healthy (≤180 с), обязательный `scripts/prod-smoke.mjs`, строка в `deployments.log` с digest. Откат — та же команда с предыдущей версией, без пересборки. `--current` поднимает текущую версию после перезагрузки хоста.
5. **Смок каждой выкатки** (`prod-smoke.mjs`) проверяет главную, health api, манифест оболочки и скачивание установщика: тихая пропажа `/desktop/` больше не проходит незамеченной.

## Отклонённые альтернативы

- **Сборка на хосте из worktree** — текущая схема; источник #560/#561. Отклонена.
- **Деплой по digest (`@sha256:…`) в `.env`** — строже тега, но оператору нечитаемо, а риск закрыт запретом перезаписи тега в CI + записью digest в журнал. Пересмотреть при появлении второго прода.
- **Свой registry на хосте** — лишний сервис на одного потребителя; GHCR бесплатен для публичного репозитория (ADR-0023). I11 ограничивает рантайм, а `pull` при выкатке — не рантайм.
- **Симлинки `current → releases/<v>`** — заменены переменной `NODUS_VERSION` в `.env`: на Windows симлинки требуют прав, а версия и так видна в журнале.

## Последствия

- Плюсы: прод не зависит от рабочего дерева; выкатка — `pull`+`up` (минуты, без сборки); откат — переключение версии; «что на проде» = строка в `.env` и `deployments.log`.
- Минусы: нужен доступ к GHCR при выкатке (при недоступности `pull` падает до `up` — прод остаётся на прежней версии); первый переход пересоздаёт web/api/gateway (тома именованные, данные не теряются; перед переходом — бэкап БД).
- Worktree `../nodus-rel` после перехода не нужен: удаляется отдельным решением владельца после недели стабильной работы.

## Сервер компании без интернета

Схема та же, но образы доставляются офлайн: `docker save` трёх образов версии + kit + артефакт десктопа в один архив, на сервере — `docker load` и `prod-deploy --from-bundle` (режим добавляется в issue-заготовке «обновление сервера компании», триггер — назначение сервера). На сервере компании `NODUS_DESKTOP_DIR=/srv/nodus/desktop`.
