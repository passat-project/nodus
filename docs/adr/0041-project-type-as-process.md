# ADR-0041. Тип проекта как процесс: статусы проекта, ветки по полям, издания схемы, «что здесь можно создавать»

- **Статус:** Принят
- **Дата:** 2026-11-15
- **Контекст:** решения владельца 15.11.2026 (три круга разбора на бизнес-кейсах), обсуждения 08–10.11.2026 (четыре комментария-примерки в #38), интервью ГИПа и главспеца (саммари — `docs/product/interviews/`, локально у владельца). Дополняет ADR-0024, ADR-0037; уточняет ADR-0030 п.6 и п.8. Простое изложение модели — `docs/product/unified-model.md`.

## Контекст

ADR-0037 описал схему проекта одной строкой: «наглядный редактор правил типа проекта по видам папок». При разборе выяснилось, что этого мало и что агенты читают описание по-разному:

- нет ответа, чем являются этапы договора («получены исходные данные», «экспертиза», «сдан») и кто их закрывает;
- нет ответа, как один тип «Договор» обслуживает разные договоры (только технология, без смет, полный состав) без отдельной схемы на каждый случай;
- любой тип задачи можно создать в любом проекте — в теме «Обучение персонала» предлагается «Разработка комплекта»;
- настройка разнесена по двум вкладкам («Процессы» и «Схемы проектов»), хотя это одна картина;
- ADR-0030 п.8 говорит «экземпляр схемы копируется в проект» — после этого правка схемы типа не доходит до идущих проектов;
- в примерке 10.11 появился тезис «ни одна запись не создаётся без проекта», противоречащий решению владельца 21–23.10 («задача без проекта — нормальный сценарий»).

## Решение

1. **Тип проекта — корень настройки процесса.** Он состоит из формы проекта, допустимых видов папок, списка разрешённых типов задач и писем, маршрута проекта, веток, вкладок по умолчанию и доступа. Тип задачи описывает одну работу; тип проекта — какие работы бывают и что за чем появляется.
2. **Маршрут проекта — третья категория движка «Процессы»** (`project` рядом с `task` и `letter`, ADR-0024 п.2–3): статусы с этапом и итогом, кнопки-переходы и кнопки-действия, окна, проверки, шаги, «кто жмёт», общий журнал переходов. Модуль проектов регистрирует адаптер своей категории. Этапы договора — статусы проекта, а не задачи и не папки. Системные состояния проекта (действует / завершён / в архиве) выводятся из этапа статуса. Переход — кнопкой руководства проекта или правилом.
3. **Ветка — правило с областью «тип проекта»** (#448): событие (папка появилась, статус работы достигнут, статус проекта сменился, Изм. создано) → условия по полям папки и проекта (#635) → шаги (#634, #436). Привязка ветки — к значениям обычных атрибутов (марка папки, признак договора), а не к отдельной сущности. Нет папок с такой маркой — ветка не срабатывает и ничего не ждёт.
4. **Контрольный штамп — окно кнопки проекта:** элемент окна «таблица строк» и шаг «создать папки и работы по строкам». Отдельного экрана-мастера нет (уточняет ADR-0030 п.6). Дерево проекта остаётся источником правды о составе.
5. **«Ждать всех» — проверка на кнопке** в момент нажатия по живому составу проекта (#635). Снимков состава, токенов и отдельного узла слияния нет.
6. **Экземпляр — издание плюс локальные правки** (отменяет в ADR-0030 п.8 «экземпляр копируется в проект»). Схема типа (маршрут проекта и ветки) живёт черновиком и изданиями. Проект хранит ссылку на издание и свои правки (ветка отключена для папки, разовый шаг). Сработавшее пишется в журнал; ключ идемпотентности — ветка × папка × Изм.
7. **Публикация издания:** перед публикацией — предпросмотр затронутых проектов и числа ещё не сработавших шагов. После: сработавшее не меняется; не сработавшее в проектах без локальных правок переходит на новое издание; локально правленое остаётся с пометкой «отличается от нового издания». Проверки при публикации: недостижимый статус, кнопка без цели, ветка на событие, которого нет в маршруте типа работы, две ветки с одинаковым событием и пересекающимися условиями, ссылка на удалённый атрибут.
8. **Отступления:** руководитель проекта и помощники в своём проекте проходят проверку с причиной, отключают ветку для папки, добавляют разовый шаг — с записью в историю. Ответственный за комплект добавляет только внеплановую задачу. Схему типа меняет обладатель права настройки проектов.
9. **Применимость типов:** связь «тип проекта × тип задачи или письма» хранится один раз и показывается с двух сторон («что здесь можно создавать» / «где создаётся»). Отдельная строка «Без проекта» — список типов, разрешённых без проекта. Сервер проверяет применимость при создании, смене типа, переносе и в шагах, создающих записи. Запись без проекта допустима; автоматизации схемы у неё нет.
10. **Письмо** регистрируется без проекта; проект обязателен к моменту, когда расписаны поручения; поручения создаются в проекте письма. Отдельного справочника рубрик нет — вместо него проекты-темы.
11. **Единый вход настройки** — «Автоматизация → Процессы»: типы проектов, строка «Без проекта», библиотека типов задач и писем. Вкладка «Схемы проектов» снимается (уточняет раскладку ADR-0030 «Реализация (#556)»).
12. **Данные процесса** — атрибуты проекта, папок и задач и поля окон. Отдельного хранилища переменных нет.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
| --- | --- | --- |
| Этапы договора — задачи-вехи у ГИПа | Владелец 15.11: ГИПу не нужны задачи по ведению проекта; статус проекта нужен руководству колонкой | — |
| Этапы — рамки на холсте или папки дерева | Вторая сущность с собственным жизненным циклом рядом с маршрутом | — |
| Второй движок с токенами (BPMN) для схемы проекта | Дублирует семантику движка «Процессы»; ADR-0037 уже отклонил | — |
| Полная копия схемы в проекте | Исправление схемы не доходит до идущих проектов; владелец 15.11 выбрал издания | — |
| Идущие проекты доживают по старому изданию (как Camunda по умолчанию, Битрикс24) | Ошибка в схеме остаётся в идущих договорах на месяцы | Понадобится жёсткая неизменность договора |
| Отдельный тип проекта на каждый вариант («без смет», «только ТХ») | Одно изменение вносится во все типы; владелец 15.11 выбрал правила по полям | Варианты разойдутся настолько, что общая схема перестанет читаться |
| Обязательный проект у каждой записи | Владелец 15.11: записи без проекта бывают; служебный проект-свалка хуже | — |
| Флаг «один проект этого типа» | Дубли ограничивает право «кто создаёт проекты типа»; флаг — лишний механизм | Появятся реальные дубли служебных проектов |
| Мастер создания проекта отдельным экраном | Штамп — окно кнопки проекта; один механизм окон | — |
| Хранилище переменных процесса | Данные уже живут в атрибутах и окнах | Появится значение, которое негде хранить |

## Последствия

**Проще:** один редактор и один движок для задач, писем и проектов; новый вид договора — настройка; руководство видит статус проекта и причину остановки; агент-исполнитель получает одну картину вместо четырёх комментариев-примерок.

**Сложнее:** адаптер категории `project` и перенос состояний существующих проектов; элемент окна «таблица строк»; предпросмотр издания по идущим проектам; новая нижняя полоса кнопок в карточке проекта; проверка применимости во всех точках создания записей.

**Риски и меры:** пересекающиеся ветки — проверка при публикации; рост числа правил на большом штампе — обработка пачками и журнал (#448); утечка через шаги — выполнение в пределах настройки и `security-reviewer` на каждом issue; путаница терминов — глоссарий и единая модель обновляются тем же коммитом.

## Обоснование (research)

Проверено поиском 08–10.11.2026, ссылки — в комментариях #38:

- **Pega / case management:** основные и альтернативные стадии, пропуск стадии по условию, «переходить автоматически или остаться вручную» — статусы проекта с кнопкой или правилом.
- **Provop, C-EPC (конфигурируемые процессы):** базовый процесс как надмножество вариантов, конфигурация только отключением неактивных фрагментов — ветки по полям.
- **Camunda:** версии определений, миграция идущих экземпляров с предпросмотром; пересекающиеся условия дают непредсказуемую ветку — проверка пересечений при публикации.
- **Битрикс24 (новый конструктор):** черновик и публикация, идущие экземпляры остаются на старой версии, несоединённый выход молча обрывае
- **Jira:** типы работ и схемы типов по проектам — «что здесь можно создавать» как связь типа проекта и типа задачи.
