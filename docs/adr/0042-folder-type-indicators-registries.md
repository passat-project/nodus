# ADR-0042. Тип папки как документ: действия и показатели; единый справочник типов; списки и реестры; видимость по типу задачи

- **Статус:** Принят
- **Дата:** 2026-11-16
- **Контекст:** решения владельца 16.11.2026 (разбор эпика #377 перед исполнением: комплект и его статус, переработки, книга изменений, раскладка настройки), проверка модели на десяти случаях вне проектирования. Дополняет ADR-0037 и ADR-0041; уточняет ADR-0030 («Дополнение (05.11)» — состояние комплекта и возможности видов папок), ADR-0025 (кнопку жмут несколько), ADR-0024 «Дополнение (#432)» (доступ к типу). Простое изложение — `docs/product/unified-model.md` §5, §11, §12.

## Контекст

При подготовке эпика #377 к исполнению нашлись места, где канон отвечал словами, но не правилом:

- статус комплекта: ADR-0030 и ADR-0037 говорили «формулы по работам папки», но не говорили, какая работа главная. В коде у вида папки есть переключатели «Документ», «Пульс», «Схема» без поведения, отметки «точка выпуска» нет, формулы берут у последней задачи папки значение атрибута, но не её статус;
- «Внести изменения» записано как действие «на папке-комплекте или в карточке выпущенной работы», при этом кнопки есть только у задач, писем и проектов;
- «реестр переработок» называл реестром список задач; книга изменений дублировала в строке данные карточки изменения;
- реестры «по всей компании» открывались во вкладке, доступной только настройщику;
- вид папки настраивался внутри типа проекта в узкой панели на четыре экрана, хотя в данных вид один на портал;
- в открытом проекте задачи видны всем: заявки на переработку видел бы каждый.

## Решение

1. **Папка — документ без своих статусов.** Всё, что папка показывает, считается из записей внутри неё. Статусов и кнопок смены статуса у папки нет. Запись, которой нужен собственный жизненный путь с решениями людей, — задача или проект своего типа.
2. **Действия у типа папки.** Тип папки может иметь кнопки-действия (ADR-0037 п.5) — тот же механизм, что действие задачи: окно, проверки, шаги, запись в истории. «Внести изменения» и «Передать по накладной» — действия папки-комплекта (уточняет ADR-0030 «Изменения»: в карточке выпущенной работы — ссылка на комплект, второй кнопки нет).
3. **Показатели типа папки** — вместо «формул по работам» без правила и вместо переключателя «Документ»: **указатель** (одна задача папки по правилу: типы, «в работе» или «выдана», порядок) и **сводка** (сколько, все ли, сумма по задачам или строкам реестра с условием). Показатели считает и пересчитывает система; руками и шагами они не пишутся; работают колонками, фильтрами и сортировкой списков. Сводка по вложенным папкам не делается.
4. **«Результат выдан»** — отметка статуса маршрута (ею становится «точка выпуска» ADR-0030): с этого статуса результат работы считается выданным. Без отметок «выдана» значит «закрыта успешно».
5. **Главная работа комплекта** (заготовка посева #557): работа «в работе» (самая новая), иначе последняя выданная; отменённые не считаются. Статус комплекта — статус главной работы; «комплект выдан» — есть действующий выпуск и ничего не в работе.
6. **Привязка типа задачи к типу папки:** создание и перенос такой задачи мимо папки этого типа запрещены (расширяет применимость ADR-0041 п.9 на уровень папки).
7. **Единый справочник типов.** «Автоматизация → Процессы» — четыре группы: Проекты (и строка «Без проекта»), Задачи, Письма, Папки (уточняет ADR-0041 п.11: вместо «типы проектов / Без проекта / библиотека типов»). Тип папки один на портал и настраивается отдельным экраном; тип проекта отмечает галочками, какие папки в нём бывают. Термин — **«тип папки»** (вместо «вид папки»); «вид» остаётся только за сохранённой настройкой списка. В боковой панели настройки — не больше одного уровня вложенности.
8. **Список и реестр.** Запись, с которой кто-то работает, — задача; факт без карточки — строка реестра. Список задач, писем или папок — «список» (вкладка-список, #435), не реестр. Строка реестра не копирует карточку: хранит ссылку, остальное показывается по ней. Реестр любого размера; импорт — вместе с поиском (#272).
9. **Реестры — для всех с доступом.** «Автоматизация → Реестры»: список реестров → строки → настройка шестерёнкой. Вкладку видит каждый с доступом хотя бы к одному реестру; права у реестра свои (видит / добавляет / правит и аннулирует). Отдельного пункта в левом меню нет (уточняет ADR-0037 п.9).
10. **Книга изменений.** Номер «NN-ГГ» рождается в строке реестра; задача «Изменение» показывает номер своей строки; каждый сотрудник берёт номер сам, нормоконтроль правит и аннулирует.
11. **Видимость задач по типу.** У типа задачи — настройка «кто видит задачи этого типа»: все, кто видит проект (как сейчас), либо только участники задачи, их руководители, решающие и выбранные роли. Действует и в открытом проекте (дополняет ADR-0024 «Дополнение (#432)»: доступ к типу сейчас скрывает тип в списках типов, но не задачи).
12. **Повторное нажатие.** Кнопка, создавшая записи, не срабатывает снова, пока созданное ею не закрыто; в режиме «по одной на каждое отмеченное» уже выданные отмечены и недоступны. Готовая проверка включена по умолчанию, настройщик может её снять. Кнопки, которые только записывают данные, не ограничиваются (уточняет решение 15.11 по #633).
13. **Архив проекта** — системная кнопка завершённого проекта, а не статус маршрута (уточняет ADR-0041 п.2: из этапа статуса выводятся «действует» и «завершён»; «в архиве» — отдельный признак).
14. **Кнопку жмут несколько** (дополняет ADR-0025): отметка последнего участника сохраняется, даже если проверка кнопки не прошла, — ответственному уходит «все сдали, мешает: …», кнопка становится обычной; возврат в статус сбора спрашивает, кому вернуть, отметки остальных сохраняются; уволенный участник снимается сам с причиной; первая версия — задачи, письма подключаются в #463 и #464.
15. **Правила:** ручного тест-запуска нет (пробный прогон — #860); правил, не привязанных к типу, в первой версии нет.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
| --- | --- | --- |
| Собственные статусы и маршрут у папки-комплекта | Второй источник правды рядом со статусами работ, который пришлось бы держать в согласии вручную; маршрут ходил бы назад на каждом изменении (отклонено ещё ADR-0030 02.11) | — |
| Состояние комплекта пишут шаги кнопок работ | Расходится при возврате, отмене, переносе и параллельных изменениях; каждая новая кнопка должна помнить о записи | — |
| Одно фиксированное правило «главная работа» на папку | Проверка на десяти случаях: не описывает папку со многими равноправными задачами, двумя показателями, строками реестра, выбором по ближайшему сроку | — |
| «Внести изменения» — кнопка выпущенной работы | Работа закрыта и не оживает; с хранением файлов кнопку пришлось бы переносить на документ | — |
| Закрытый (секретный) проект «Переработки» | В секретном проекте задачи создают только участники — заявку было бы не подать | — |
| Реестр переработок со своими строками | Дублирует карточку заявки | — |
| Пункт «Реестры» в левом меню | Реестры наполняют кнопки, смотрят вкладкой в проекте; раздел слишком мелок для главного меню (владелец 16.11) | Появится ежедневная ручная работа с реестрами |
| Типы папок внутри типа проекта | Вид один на портал; панель в четыре экрана; кажется, что папка принадлежит типу проекта | — |
| Сводка по вложенным папкам | Нет случая, который не закрывает группировка списка | Появится показатель у здания или стадии, нужный вне списка |
| Библиотека шаблонов задач отдельным списком | Пятый список рядом с четырьмя группами; шаблон — заготовка полей своего типа | Шаблон понадобится сразу нескольким типам |

## Последствия

**Проще:** статус комплекта определён одним правилом и не расходится с работами; новые типы папок вне проектирования собираются настройкой; настройка всех типов в одном месте; заявки и подобные записи закрываются от чужих глаз без секретного проекта.

**Сложнее:** пересчёт показателей при изменении задач и настройки; видимость через показатели и списки; действия у записи без маршрута; перенос настройки видов папок на отдельный экран и переименование строк интерфейса.

**Риски и меры:** утечка через показатель или список — правило «видимость одна» (`unified-model.md` §7) и `security-reviewer` на каждом issue; расхождение показателя с задачами — показатель только вычисляется, тест на каждое событие задач; путаница слов — глоссарий и единая модель обновлены тем же коммитом.

## Обоснование (research)

- **ISO 19650.** У информационного контейнера есть статус и ревизия: статус — «текущее положение в процессе», ревизия — история изменений; состояния контейнера — Work in progress / Shared / Published / Archive ([CDBB, National Annex Guidance](https://www.cdbb.cam.ac.uk/files/national_annex_guidance.pdf); [UK BIM Framework, Guidance Part C](https://ukbimframework.org/wp-content/uploads/2021/02/Guidance-Part-C_Facilitating-the-common-data-environment-workflow-and-technical-solutions_Edition-2.pdf)). Комплект — контейнер, работа — его ревизия, статус комплекта — статус текущей ревизии. Читались руководства к стандарту, не его текст.
- **Autodesk Docs.** Проверка запускается по версиям файлов; статус документа обновляется автоматически, когда проверка завершена ([Create and Edit Approval Workflows](https://help.autodesk.com/cloudhelp/ENU/BIM360D-Document-Management/files/About-Reviews/GUID-C9632B31-2B76-4F3F-B883-45C38C29C280.html)) — статус документа выводится из процесса над его версией.
- **Битрикс24, универсальные списки.** «Автоматизация → Списки», просмотр элементов и настройка в одном месте, права у каждого списка, создаёт администратор ([справка](https://helpdesk.bitrix24.ru/open/25651148/)).
- **Кадровые системы.** Заявку на отсутствие или переработку по умолчанию видят заявитель, его руководители, согласующие и кадры ([PurelyHR](https://support.purelyhr.com/calendar-view-restrictions), [NCompass](https://kb.findesolutions.com/books/hr-module-aH0/page/overtime/export/pdf)); два примера, не обзор рынка.
- **Проверка модели 16.11.2026** на десяти случаях: комплект, том на экспертизе, авторский надзор, обучение, исходные данные, внедрение IT, накладные и замечания экспертизы, задача мимо папки, тендер, здание — итог в `unified-model.md` §11. Проверка выполнена одним агентом, без независимых проверяющих.
