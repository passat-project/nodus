# ADR-0053. Руководитель сотрудника — производное поле структуры

- **Статус:** Принят
- **Дата:** 2026-11-17
- **Контекст:** карточка профиля (#923) и оргструктура (M2): `users.manager_id` был свободной ссылкой клиента (кейс «помощник ГИПа»), из-за чего руководитель в карточке расходился с деревом подразделений, а правка вручную требовала валидации циклов и роняла связь при увольнении главы.

## Контекст

До #923 `managerId` сотрудника назначался вручную администратором (и мог указывать на любого активного сотрудника). Параллельно существовал `departments.headId` — глава подразделения, из которого задачи и маршруты уже выводили «ближайшего руководителя» цепочкой вверх (ADR-0025, `OrgStructureReader.managerChainOf`). Два источника истины давали расхождения: карточка показывала один «руководитель», решающие маршруты — другой; при увольнении главы `headId` оставался висячей ссылкой.

Владелец (17.11.2026, #923) решил: руководитель — **вычисляемое** свойство структуры, ручное назначение убирается. Риск принят осознанно: кейс «помощник ГИПа» при главе-не-из-отдела получит руководителем главу отдела; если понадобится исключение — отдельное решение.

## Решение

1. `users.manager_id` — **производное кэшируемое поле**: ближайший активный глава (`departments.head_id`) вверх по дереву **управленческих** подразделений. Глава своего отдела; если сотрудник сам глава — глава родительского (и так выше); сам себя не назначаем; уволенный глава пропускается. Нет главы выше — `null`.
2. **Клиент значение не присылает**: `createUserSchema`/`updateUserSchema` не содержат `managerId`; `userCardSchema`/`userListItemSchema` отдают вычисленное.
3. **Пересчёт транзакционный** (`ManagerDerivationService`, один рекурсивный CTE по departments, глубина ≤ 32): создание/перевод сотрудника, смена `headId`/`parentId`/архивация подразделения, деактивация. Пишутся только реально изменившиеся строки (`IS DISTINCT FROM`).
4. **Увольнение**: `headId`/`deputyId` очищаются во ВСЕХ подразделениях, где сотрудник руководитель/зам, подчинённые пересчитываются на ближайшего главу выше, `directory.department.updated` — на каждый затронутый узел. **Перевод** в другое подразделение (или без подразделения) снимает роль ТОЛЬКО в старом узле — один сотрудник занимает одно место в управленческой структуре, а руководитель/зам — роль своего отдела, не второе место; отдельной кнопки «Перевести» нет (это поле «Подразделение»), юридическая структура (`legal*`) — формальные поля и в переводе не участвует. Глава/зам при назначении не обязан входить в состав подразделения (например, BIM-группой руководит глава из другого узла) — проверки членства нет.
5. **Бэкфилл**: миграция `20261128090000_derive_user_manager` перезаписывает старые ручные значения (включая «помощника ГИПа»).
6. Решающие маршруты (ADR-0025) и «Подчинённые» карточки читают тот же `manager_id` — второй источник истины удалён.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Вычислять руководителя только на чтение (CTE в каждом запросе) | ~40 мест UI и решающие маршруты читают `managerId` из DTO; сквозной вычисляемый join в списках и JWT-подобных проекциях дороже и размазан по модулям | Если появится второй тип иерархии (матричная организация) — вычисление на чтение с явным «каким путём» |
| Оставить ручное поле, добавить «derived» fallback | Два источника истины сохраняются; расхождения карточки и маршрутов остаются | Никогда — расхождение данных не лечится приоритетом |
| Closure table / materialized path | Для штата ~170 глубина дерева ≤ 32, пересчёт поддерева одним CTE — миллисекунды; closure-таблица усложняет инвариант ценой преждевременной оптимизации | При росте штата на порядки или частых переносах больших поддеревьев |
| Периодический refresh (как Oracle HCM flatten) | Нужна согласованность в той же транзакции с правкой структуры; лаг между правкой и карточкой недопустим | Если пересчёт станет дорогим и допустим лаг |

## Последствия

- Проще: один источник истины «кто мой руководитель» — дерево; карточка и решающие маршруты не расходятся; исчезли проверки циклов и advisory-лок графа `nodus:users:manager-graph`; увольнение главы больше не оставляет висячих `head_id`.
- Сложнее: любая структурная правка (глава, родитель, архив, деактивация, перевод) обязана идти через пересчёт — это новый инвариант для будущих фич структуры; тесты обязаны покрывать пересчёт.
- Потеря: ручная подчинённость вне дерева («помощник ГИПа») не выражается. Обходной путь — назначить главу отдела или создать подразделение; исключения — отдельным решением владельца.
- Уволенный глава: подразделение остаётся без главы (`headId = null`) до назначения нового — это видно в структуре и требует действия администратора. Переведённый глава/зам оставляет свой прежний узел без руководителя по тому же правилу.

## Обоснование (research)

- Oracle HCM использует денормализованную таблицу «flattened supervisor hierarchy» именно ради быстрых выборок руководителя и подчинённых, но обновляет её периодическим процессом; наш масштаб (~170) и требование согласованности позволяют пересчитывать в той же транзакции, а не по расписанию (Hodson, «HCM Flattened Supervisor Hierarchy Table», 2020).
- AppMaster, «Model org charts in PostgreSQL: adjacency lists vs closure» (2024): adjacency list (`manager_id`) — минимальное число движущихся частей; closure-таблица окупается только при регулярных обходах больших поддеревьев и иерархических правах. Для штата компании и глубины ≤ 32 рекурсивный CTE достаточен.
- Microsoft Azure Table Storage design guide: денормализация «отдел в сотруднике» дешевле на чтении, но требует обновления всех затронутых записей при смене руководителя — у нас это делает один SQL-проход по затронутому поддереву в транзакции.
