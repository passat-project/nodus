# ADR-0051. Eval каталога инструментов ассистента: золотой набор, детерминированный скорер, гейт и горячая полка

- **Статус:** Принят
- **Дата:** 2026-11-18
- **Контекст:** эпик #926 (паритет действий ассистента), ADR-0043 (каталог), ADR-0048 (карточки), ADR-0049 (контракт каталога), I2 (API-first), I8 (RBAC), I12 (устаревшая документация = баг).

## Контекст

Каталог ассистента вырос с 41 до 88 инструментов за одну смену: партии #927–#932
добавили 47 операций (создание проектов, дневные действия задач, чатов, писем,
проектов, контрагентов, справочников, уведомлений). Владелец поставил цель
40–60 инструментов и требование «каждая партия не ухудшает выбор».

Проблема: «стало ли модели удобнее» до этой смены измерялось мнением. При росте
каталога модель начинает путать соседние операции (создать письмо ↔ пригласить
участника, задача ↔ подзадача), а живой прогон LLM дорог, недетерминирован и
требует ключа провайдера, которого в ночной смене нет. Нужен измеритель, который:

1. гоняется в CI на каждом коммите и не флакает;
2. объясняет промахи (какой инструмент спутали и с чем);
3. не даёт добавить инструмент «на глаз», без стандарта описания;
4. отвечает на вопрос о размере горячей полки числами, а не вкусом.

## Решение

1. **Золотой набор — данные, а не код** (`apps/api/src/modules/assistant/eval/golden/`).
   150 обезличенных запросов четырёх ролей (ГИП, секретарь, администратор, рядовой),
   по 2–3 формулировки на интент: официальная, разговорная, с опечаткой. У кейса —
   `expectedTools`, `forbiddenTools` (правдоподобно неверный выбор), признаки
   `noToolCase` (операции нет — нужен отказ) и `shouldClarify` (нужно уточнение).
   Ограничения проверяются тестом: 100–150 кейсов, ≥ 30 на роль, все формы у роли,
   ≥ 15 отказов, ≥ 4 уточнения, id инструментов существуют, каталог покрыт целиком,
   нет реальных почт/телефонов (публичный репозиторий).
2. **Детерминированный скорер** (`tools/retrieval-lang.ts`, `retrieval-rank.ts`,
   `retrieval-lexicon.ts`): нормализация и основы русских слов (ё→е, опечатки домена,
   отсечение окончаний, 4-буквенные ключи), лексика модулей/объектов/классов действия,
   понимание запроса (имя человека, номер сущности, «мой», кавычки, объект создания),
   потолок возможности (`hasCapability`: нельзя выбрать инструмент, натягивающий
   несуществующую операцию) и структурные фильтры (просьба «покажи» не предлагает
   запись). Лексика вынесена в данные: новый синоним не требует правок алгоритма.
3. **Две траектории.** `tools.search` — лексическая полка кандидатов (top-7);
   **симулятор диспетчера** — прокси LLM-диспетчера #917: тот же скорер, но с
   порогом, проверкой возможности операции и приоритетом объекта. Гейт по неверному
   инструменту/отказу — на симуляторе; `tools.search` меряется на recall (его
   кандидатов отсекает модель).
4. **Метрики и пороги** (`eval/eval-runner.ts`, `eval/eval-gate.test.ts`):
   `recall@7` ≥ 90%, **неверный инструмент = запрещённый выбран ПЕРВЫМ** < 5%,
   корректный отказ ≥ 95%, безопасное уточнение ≥ 90%; справочно — `allExpected@7`,
   попадание запрещённого в полку top-7, `top1`. Dev/holdout делится детерминированно
   по хешу id (75/25) — расхождение чисел сигнализирует о подгонке описаний.
5. **Стандарт описания + линтер** (`tools/definitions/meta/*.meta.ts`,
   `tools/tool-standard.test.ts`): `why`, `whenToUse`, `whenNotToUse`, `subject`,
   `alsoSubjects`, `effect`, `example` (валидируется zod-схемой инструмента),
   `returns`, `nextStep`, `intent`; длины, уникальность названий, соответствие
   эффекта виду, отсутствие двух инструментов с одинаковым смыслом без явного
   разграничения. Новый инструмент без стандарта не мержится.
6. **Конвейер «добавление инструмента = данные»**: определение описывает операцию
   API (метод, путь, zod-схема, проекция); карта поверхностей
   (`assistant-surface.md`) и стандарт (`assistant-tool-standard.md`) генерируются
   из каталога и проверяются на свежесть в CI; тест маршрутов сверяет каждую
   `api`-операцию с реальными маршрутами Fastify.
7. **Горячая полка — 18–30 инструментов, сейчас 26.** Замер на золотом наборе:
   полка из 12 самых частых покрывает 41.6% ожидаемых инструментов и 24.8% кейсов
   полностью, 15 — 46.3%/29.5%, 18 — 51.1%/33.3%, 30 — 64.7%/51.9%; текущие 26
   (набор #889) — 50.5%/35.7%. Вариант 12–15 **отклонён**: полка — это весь набор
   инструментов в режиме без диспетчера (свежая установка, выключенная модель-
   диспетчер), и сокращение теряет 4–9 п.п. покрытия в обмен на выигрыш внимания,
   который детерминированный замер не измеряет. Верхняя граница 30 совпадает с
   порогом деградации выбора 30–50 инструментов (Anthropic). Переход на частотные
   30 (64.7%/51.9%) — отдельное изменение данных после живого замера внимания модели.
8. **Партия, ухудшившая метрики, не мержится**: откат, фиксация в отчёте; вторая
   неудача партии — метка `blocked`.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
| --- | --- | --- |
| Только живой eval LLM | Нет ключа провайдера в ночной смене; недетерминизм и стоимость не позволяют держать CI-гейт; промахи невоспроизводимы | Появится ключ и бюджет: живой прогон 30–50 задач как второй слой |
| Эмбеддинги/BGE-реранкер сразу | Инфраструктура локальной модели и задержка на каждом вызове; при 88 инструментах лексика с фильтрами даёт recall@7 100% на наборе | Каталог 150+, или лексика перестанет держать recall на живых формулировках |
| Малый набор «на глаз» (30–40 кейсов) | Не статистика: одна правка описания меняет проценты; не покрывает все инструменты | Никогда |
| Неверный инструмент считать по попаданию в top-7 | Полка — кандидаты для модели; запрет в полке ≠ неверное действие, порог 5% был бы недостижим без ослабления запретов | Решение принимает модель по одному инструменту — метрика остаётся top-1 |
| Горячая полка 12–15 | Теряет 4–9 п.п. покрытия fallback-режима без измеренного выигрыша внимания | Живой замер покажет деградацию выбора при 26 |
| Частотная полка 30 сразу | +14 п.п. покрытия, но смена 30 флагов `hot` без живого замера внимания — риск для основного пути свежей установки | После живого eval внимания модели |

## Последствия

**Проще:** добавление инструмента стало конвейером (определение → стандарт → кейс →
доки), а не ручной работой; регрессия выбора ловится в CI за секунды; промахи
объяснимы (отчёт печатает кейс, запрос, ожидание и фактическую полку); горячая
полка обоснована числами.

**Сложнее:** каждый новый инструмент требует кейса в золотом наборе (иначе тест
покрытия красный) и стандарта описания; при росте каталога промпт диспетчера
упирается в бюджет 16k — строка каталога уже сжата (id, название, модуль, вид,
«зачем» ≤ 48 знаков, 3 ключа ≤ 30 знаков), при следующем росте потребуется
иерархическая выдача.

**Риски и меры:** лексический скорер ≠ LLM — сложные перифразы ловятся живым
прогоном, который вне гейта; золотой набор написан агентами — пополняется
формулировками владельца/сотрудников; опечатки покрыты словарём и 4-буквенными
ключами, не полноценной морфологией; детерминированный `wrongToolRate` не заменяет
измерение задержки/стоимости диспетчера (событие `tools.routed`).

## Обоснование (research)

- Anthropic, Tool search tool: «Claude's ability to pick the right tool degrades
  once you exceed 30–50 available tools»; рекомендация держать 3–5 самых частых
  инструментов всегда загруженными, остальные — по запросу; поиск по именам и
  описаниям, поэтому описания с живыми словами пользователей важнее краткости.
  <https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool>,
  <https://www.anthropic.com/research/advanced-tool-use>
- MCP Client Best Practices: progressive discovery, стратегии поиска — keyword
  (BM25/regex), embeddings, subagent-based routing; для серверов с десятками
  инструментов рекомендовано не грузить все определения в контекст.
  <https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices>
- Контекст MCP-масштаба: типовой мультисерверный набор (GitHub, Slack, Sentry,
  Grafana, Splunk) — ~55K токенов определений до первого запроса; отсюда бюджет
  промпта диспетчера и компактная строка каталога.
- Внутренние замеры смены: `docs/architecture/assistant-eval-report.md` —
  baseline `main@04b6dbd0` (41 инструмент, 100 кейсов) против текущего каталога
  (88 инструментов, 150 кейсов): recall@7 диспетчера 90.1% → 100%, все ожидаемые
  86.1% → 100%, неверный первый 3.8% → 1.3%, уточнение 83.3% → 100% (тот же срез);
  полный набор — неверный 1.6%, отказ 100%.
