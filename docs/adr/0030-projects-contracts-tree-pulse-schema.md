# ADR-0030. Проекты: договор, портфель, дерево узлов, пульс, мастер, схема проекта

- **Статус:** Принят; частично отменён ADR-0037 (шифр и код — атрибуты, возможности видов папок — заготовки настроек, пульс — виды, схема — правила)
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 23–25.10 (master-plan §8; ответы 68–76; «проект — всегда договор, портфель — один заказчик одного большого объекта с десятками договоров» — 25.10; «чаты узлов — после декабря» — 25.10), интервью Вашурова, Куралени, Шайдеровой, `docs/mvp/process-model-plan-2026-10-25.md` §4.5, #427. Отменяет «узлы = структурные задачи» (09.10/21.10) и флаг `TaskType.structural`.

## Контекст

Сегодня структура проекта вводится трижды (контрольный штамп → папки в Пилоте → задачи в Битриксе); статусы комплектов ГИПы ведут в своих таблицах, руководство сводит их вручную; задания смежникам забывают выдавать. Бэкенда проектов нет (только моки веба).

## Решение

1. **Модуль `projects`.** Проект = договор (на этап или на весь объект): шифр (необязателен — «темы» без шифра: «Тендер», «Внедрение IT»), название, тип проекта, портфель, заказчик (контрагент, ADR-0033), **руководитель проекта** (по умолчанию — создатель, передаётся) и **помощники** (несколько; системные поля, вердикт 29.10), видимость `open | secret` (умолчание для новых — настройка администратора в «Настройках портала»), статус (действует / завершён — метка / в архиве — заморозка: создание задач в проекте запрещено, возврат — руководителем), даты, кастомные поля, канал проекта (создаётся автоматически). Создаёт любой сотрудник (право `project.create` у всех ролей). Админы по умолчанию НЕ видят секретные (осознанное отклонение от Jira/Linear: модель Битрикс-суперадмина — спец-право `project.view_secret` выдаётся роли «Системный надзор» для учётки Системного Администратора).
2. **Портфель** (`project_groups`, плоский список) — один заказчик одного большого объекта с десятками договоров; фильтр «по портфелю» в реестрах (переработки, письма).
3. **Участие — двухрежимное** (вердикты 29.10). Открытый проект: состав живёт из задач (постановщик, ответственный, соисполнители; наблюдатель задачи участником НЕ становится) + руководство + вступившие своей кнопкой; руками состав не редактируется. Секретный проект: видят только участники; состав прописывается вручную руководством (участник — может получать задачи, наблюдатель — только просмотр); задачи состав не расширяют: в задачу секретного проекта нельзя добавить никого (даже наблюдателем), кто не состоит в проекте. Создатель, назначивший руководство другим, — наблюдатель. Состав канала проекта = участники.
4. **Руководство проекта:** системные поля Руководитель + Помощники (несколько) с правами уровня постановщика на все задачи проекта (закрывать забытые, удалять ненужные, менять поля проекта); каталог ролей проекта отменён (вердикт 29.10). Дополнительные роли — атрибуты области `project`; подсказки (ГИП в резолюции) и источник решающих «роль в проекте» (#433, ADR-0025) подключаются к полям Руководитель/Помощник.
5. **Дерево:** каталог видов уровней (стадия, очередь, пусковой комплекс, здание по генплану, раздел, этап — значок, цвет; создаются в визарде); тип проекта задаёт шаблон уровней, проект — свой порядок. Узел (`project_nodes`: проект, родитель, вид уровня, название, код, порядок, архив) — **папка-агрегат без полей, ответственного, срока и (в декабре) без чата**. Листья — задачи: `tasks.node_id` (plain UUID; принадлежность проекту проверяется read-портом структуры проектов). Часы, срок и прогресс узла — агрегаты с листьев. Комплект — задача типа «Комплект», изм. N — задача типа «Изменение» (подзадача комплекта). Узлы видны только в модуле «Проекты».
6. **Мастер создания:** основа (тип, шифр, название, заказчик, портфель, видимость) → структура (уровни, пакетное создание узлов) → контрольный штамп (вставка таблицы из Excel/Word: марка, шифр комплекта, название, узел, ориентировочный срок, главспец) → схема → создание (узлы, задачи-комплекты, экземпляр схемы, канал).
7. **Пульс:** задачи типов с флагом «в пульсе» (ADR-0024) по дереву — комплекты и их изм. N; статус цветом, исполнитель, срок, часы, процент маршрута (позиция статуса), колонки-поля («№ накладной», «Дата передачи»), сводка по статусам. Данные — API задач по проекту, дерево — API проектов (композиция на вебе, I3).
8. **Схема проекта (декабрь):** шаблон у типа проекта (холст `shared/flow`, ADR-0022): заглушки «будущая задача» (тип, название, дисциплина/узел, правило исполнителя, поля для окна) и стрелки «после статуса S задачи A → заглушка B». Экземпляр копируется в проект при создании и правится в проекте. «Запустить схему» — системное создание стартовых задач; когда задача заглушки достигает статуса-сигнала, нажавший получает окно генерации, задача создаётся механизмом ADR-0025 п.6 (шаблон — из заглушки через read-порт проектов). Прогресс схемы — в пульсе. Заглушки — не задачи и не спящие черновики.
9. **Чаты узлов и пространство проекта в мессенджере** (окно поверх списка чатов: канал, чат проекта, ленивые чаты узлов) — после декабря, отдельным решением.

## Дополнение (#467, вердикты владельца 30.10)

П.5 «Дерево» уточнён вердиктами владельца 30.10 (issues #467):

- **Свободная вложенность, вид уровня = ярлык** («папки в проводнике, задачи — файлы»): каталог `node_levels` — значок+цвет, узел носит вид как ярлык; вложенность видом не ограничивается. **«Порядок уровней проекта» и «правка с предупреждением» отменены** — шаблон уровней у типа проекта (`levelKindIds`) остаётся только подсказкой дефолтного вида при создании узла.
- **Узлы без архивации**: пустой узел удаляется насовсем; непустой (задачи или дети) — 409. Архивы — только у проекта.
- **Узла нет в карточке задачи**: узел назначается/меняется только в дереве проекта (DnD, «+ задача» пресетом).
- **Агрегаты узлов — на чтении** (расширенный read-порт задач при запросе структуры), а не кэш с пересчётом по событиям: до тысяч узлов материализация не нужна (сверка мировой практикой, Exa 30.10).
- **Реалтайма структуры чужих изменений нет до пилота** (gateway не маршрутизирует `project.*`).
- **Срез узлов структуры без курсорной пагинации** (≤1000 узлов на проект) — легализованное исключение из I7-пагинации.

## Дополнение (02.11, вердикты владельца в сессии планирования)

Отменяет в п.5 «Комплект — задача типа «Комплект», изм. N — задача типа «Изменение» (подзадача комплекта)» и решение 30.10 о связи изменения с комплектом через `changeOfTaskId` (жило только в локальном черновике #467, в git не попадало); уточняет п.2 (портфель), п.7 (пульс), п.8 (схема) и «Дополнение (#467)» («вид уровня = ярлык», «виды узлов живут в «Структуре»»). Issues: #556, #557, #558, #559; переписаны #38, #468, #469, #551; #552 закрыт.

- **Работа ≠ документ.** Комплект — папка структуры вида с возможностью «Документ с изменениями»: шифр — код папки (не меняется никогда, СТБ 2255 п. 7.1), название — имя папки. Работы — задачи внутри папки: «Разработка комплекта» (посеянный тип «Комплект» переименовывается), «Изменение», задания сметчикам и смежникам. Подзадачи — части конкретной работы и блокируют только её закрытие.
- **Состояние комплекта выводится из работ на чтении** (как агрегаты узлов): текущий Изм. — последний выпущенный, «Изм. N в работе», статус и исполнитель текущей работы, актуальный файл (атрибут «Файл» последней выпущенной работы); подпись — «ОВ1.1 · Изм. 2». Ручного «номера Изм. комплекта» и формул нет: выводимое выводит система.
- **Виды папок — настраиваемые типы** (вместо «вид = ярлык»): атрибуты области `node` (резерв ADR-0029 активируется), форма создания (скрыто / по желанию / обязательно), закрытый список возможностей — «Документ с изменениями», «Показывать в пульсе», «Строка схемы». Поведение включают только переключатели — кода под конкретный вид нет; в проекте-«Теме» таких папок просто нет. Настройка — «Автоматизация → Типы проектов → Виды папок»; в «Структуре» остаётся выбор вида. Посев: вид «Комплект» с атрибутами «Марка» (СТБ 2255 прил. А) и «Стадия».
- **Изменения.** Точка выпуска — настройка типа работы (по умолчанию «Выдано в печать»): с неё «Файл» и отмеченные атрибуты только для чтения; правка — «Внести изменения» (на папке-комплекте или в карточке выпущенной работы) → задача «Изменение» в папке. Номера — в транзакции создания: «Изм. N» по папке (не переиспользуется) + сквозной номер из серии «Изменения» (механизм серий ADR-0024; заменяет Excel-таблицу нормоконтроля, где номер «берёт» сам проектировщик: номер, объект, кто взял, причина), номер выдаётся и без комплекта (объекты вне Nodus). Причина — справочник («Наша ошибка», «Требование заказчика сверх ТЗ»). Реестр изменений — реестр типа «Изменение» (#435), отдельной сущности нет.
- **Закрытие работ.** Работа закрывается по своему маршруту и не оживает; подзадачи в закрытую работу не добавляются. Когда изменение проходит точку выпуска, прежние выпущенные, но не закрытые работы комплекта (ждут накладную, госорганы, забыты) закрываются правилом с итогом «Заменена Изм. N» (успех, журнал переходов — от правила); невыпущенные и с открытыми подзадачами — подсветка ГИПу.
- **Схема (п.8).** Шаблон у типа проекта — карточки видов работ и правила по видам папок и их атрибутам («каждый «Комплект» с маркой ОВ…»), отметка «повторять на каждый Изм.», порождение из промежуточных статусов. Экземпляр строится из папок дерева с возможностью «Строка схемы» — нарисован каждый комплект; раскладка строками по узлам; штамп живой (схема следует за деревом); одна заглушка экземпляра = одна будущая задача комплекта (× Изм.). Вкладка «Типы проектов» — холст схемы + форма проекта + доступ, одним куском (#38); `levelKindIds` и мост `code_field` удаляются. Порядок: #436 → #38 → #468.
- **Пульс (п.7).** Строки — папки видов с возможностью «Показывать в пульсе»; раскрытие — работы папки.
- **Портфель (п.2).** Папка в журнале «Проекты» (#559); сводная страница (договоры, общий пульс, письма, структура с раскрытием) — после загрузки большого объекта (#551), без собственного состава и прав: строки — по правам договоров.
- **Отложено:** внутренние редакции внутри одного Изм. (фиксация в момент передачи файла + «отпечаток» файла в десктопе; содержимое — будущий файловый модуль), одно изменение на несколько комплектов (общее разрешение, СТБ 2255 п. 7.4.3), повтор по периоду в схеме.
- **Отклонено:** «изменение правит сам комплект» (теряется история выдач — кейс «Гвардейская», маршрут ходит назад, часы смешиваются, параллельные изменения невыразимы); «исходная задача как лицо комплекта» (двойная роль задачи); отдельная сущность «Комплект» рядом с деревом (вторая структура, +3–5 агент-дней); «портфель как проект проектов» (вторая модель прав поверх проектов — риск утечек, ср. #541; дерево «100 договоров × узлы × задачи» нечитаемо).
- **Обоснование:** СТБ 2255-2012 разд. 7, прил. А и К (обозначение не меняется; порядковый номер изменения документа; разрешение «NN-ГГ» по книге регистрации; копии изменённых листов — всем прежним получателям; коды причин табл. К.1); ГОСТ Р 21.101-2020 п. 7.1.2, 7.2, 7.3.1; ISO 19650-2 UK National Annex и UK BIM Framework Guidance Part 2 (ID контейнера неизменен; ревизия P/C и статус — метаданные); Pilot-ICE (новая версия не замещает файл, причина при публикации, прежняя — «Аннулирован»); Asana Portfolios (портфель — витрина над проектами).

## Последствия

**Проще:** штамп вводится один раз; пульс заменяет таблицы ГИПов; генерация не даёт забыть задания. **Сложнее:** проверка `node_id` через read-порт; агрегаты дерева (кэш с пересчётом по событиям задач); схема — самая неопределённая часть, делается последней в треке проектов.

## Дополнение (05.11, ADR-0037) — проекты на ядре

- **Шифр проекта и код папки — атрибуты**, дубли не проверяются. Шифр может быть формулой и меняться при переносе комплекта (владелец 03.11); правило «шифр не меняется никогда» перестаёт быть поведением системы, закрепляют значение вводом руками.
- **Возможности видов папок** («Документ с изменениями», «Показывать в пульсе», «Строка схемы») становятся готовыми заготовками настроек ядра. «Внести изменения» — кнопка-действие с шагами: создать «Изменение», выдать Изм. N из счётчика папки и номер книги, записать строку реестра. Точка выпуска — состояние полей по статусу. «Заменена Изм. N» — правило.
- **Состояние комплекта** (текущий Изм., статус текущей работы, актуальный файл) — формулы по работам папки.
- **Книга изменений** — реестр: номер «NN-ГГ» (счётчик по году), коды причин 1–5 (ГОСТ 21.1101 табл. Л.1, СТБ 2255), основание — необязательная ссылка на письмо. Номер для объекта вне Nodus — строка со ссылкой на проект; старые договоры грузятся завершёнными проектами (И-007). **Накладные** — реестр с номером по объекту.
- **Пульс** — виды проекта: по умолчанию от типа проекта, ГИП правит для своего проекта, каждый сохраняет свои.
- **Схема проекта** — редактор правил типа проекта; экземпляр в проекте правится без публикации типа, включая ещё не сработавшие узлы.
- **Задания смежникам и сметчикам** — посев настроек (интервью 05.11): задача на пару «кто → кому» — подзадача работы; получатель по умолчанию — ответственный текущей работы комплекта-получателя; «Принять» = ознакомился и взял в работу; номер версии — при принятии; реестр «Выдачи заданий»; на каждый Изм. — новые задания тем, кого отметил разработчик; сметчикам — всегда.
