# ADR-0048. Действия агента: карточка подтверждения, байпас, идемпотентность и аудит «через ИИ»

- **Статус:** Принят
- **Дата:** 2026-11-27
- **Контекст:** решение владельца 17.11.2026 (ночной бриф, эпик #889, Ф2/#899); ADR-0043 (каталог инструментов), ADR-0047 (MCP-серверы равнозначны); I7 (идемпотентность и аудит), I8 (права на API), I2 (действие воспроизводимо).

## Контекст

Ф1 сделала ассистента читающим: инструмент — операция API портала, исполняемая от имени сотрудника через Fastify `inject` с его `Authorization`. Ф2 «Делать» добавляет записи. Две крайности недопустимы: (а) модель молча меняет данные портала — недопустимо для корпоративной системы; (б) каждая запись требует модального окна сотрудника — медленно и раздражает. Владелец задал точную модель: **по умолчанию подтверждение каждого создания/изменения, байпас — долгим нажатием на иконку в композере**.

## Решение

1. **Запись не исполняется из агентного цикла.** Инструмент `kind: write` вызывает не API, а `AssistantActionsService.propose`: валидирует аргументы zod-схемой инструмента, собирает карточку (заголовок, сводка, поля-столбиком, последствия, обратимость) и создаёт строку `assistant_actions` в состоянии `proposed`. Модель получает результат «действие подготовлено, ждёт подтверждения» и НЕ утверждает, что оно выполнено. Строка вызова инструмента для записи не создаётся — карточка и есть элемент ленты (без дубля).
2. **Три состояния решения:** `POST /assistant/actions/:id/execute` — выполнить, `…/cancel` — отклонить (записей в портале нет), `…/undo` — отменить выполненное там, где API позволяет (удаление созданного). Исполнение идёт от имени сотрудника: его `Authorization` из текущего HTTP-запроса, те же guard-ы, валидация и фильтры видимости API. Токен не хранится в БД.
3. **Байпас — единственный обход подтверждения.** Включается только долгим нажатием (≥ 400 мс) на иконку в композере; активное состояние видно иконкой и пометкой над полем; выключается повторным долгим нажатием, сбрасывается при смене диалога и закрытии окна. Состояние передаётся в `POST …/messages` флагом `bypass`, фиксируется на прогоне (`assistant_runs.auto_execute`) — снимок на отправку, следующий вопрос снова спрашивает. При байпасе карточка создаётся и исполняется сразу, с пометкой «выполнено автоматически» — прозрачность и аудит не теряются.
4. **Жёсткий предохранитель — код, а не промпт.** `ToolExecutorService.execute` отклоняет `kind: write` (`ASSISTANT_WRITE_NEEDS_CONFIRMATION`). Прямой путь записи один: `executeWrite`, вызываемый только из `AssistantActionsService` после захвата карточки. Каталог не регистрирует запись без `card` (тест). Модель физически не может выполнить запись без карточки.
5. **Идемпотентность.** `Idempotency-Key` внутреннего запроса = **id карточки** (I7, ADR-0005): повторный клик «Выполнить» и сетевой ретрай не создают дубль. Захват карточки — атомарный `updateMany` `state IN (proposed, failed) → executing`; второй параллельный клик получает уже выполненную карточку или 409. Зависший `executing` (> 60 с, перезапуск API) перезахватывается. `cancel` возможен только для `proposed/failed`; `undo` — только для `executed` и только при `undoable`.
6. **Аудит «через ИИ».** Каждое исполнение (и кнопкой, и байпасом) пишет `audit_logs`: `assistant.action_execute` / `assistant.action_failed` с `actorId` сотрудника, `entityId` карточки и `details { viaAi: true, toolId, automatic, runId }`. Доменная мутация дополнительно аудируется своим API (`task.create`, `chat.message_send`, …) — карточка связывает обе записи. Отказ/отмена — `assistant.action_cancel`, отмена выполненного — `assistant.action_undo` (интерсептор аудита контроллера).
7. **События ленты.** К журналу прогона добавлены `action.proposed/executed/cancelled/failed/undone` с полным DTO карточки; клиент обновляет живой буфер по SSE, а после решения перечитывает историю диалога (состояние — из БД).
8. **Состав действий Ф2 (только существующие маршруты API, без новых endpoint-ов):** `tasks.create`, `tasks.update` (поля, исполнитель, срок, стадия), `chat.send` (+ чтение `chat.task_conversation` для чата задачи), `letters.transition` (резолюция/регистрация/шаги маршрута), `projects.update`, `projects.add_member`, `projects.add_node`. Удаление сущностей и админские операции с ролями/правами портала, публикация и архив процессов, формулы, смена типа — вне скоупа. Комментарий к задаче — сообщение в её чат (портал не имеет отдельного API комментариев).

    **Расширение #926 (18.11.2026):** состав Ф2 вырос партиями #927–#932 до 88 инструментов (создание проектов и групп, дневные действия задач/чатов/писем/проектов, контрагенты, варианты справочников, настройки уведомлений; групповые беседы — `chat.create_conversation`). Правила карточки и идемпотентности те же; **байпас не исполняет инструменты с `effect: irreversible`** — они всегда ждут подтверждения человека (п. 3 действует для обратимых действий). Каталог и права — `docs/architecture/assistant-surface.md`, методика — ADR-0051.
9. **Откат.** Карточка объявляет `undoable`; инструмент даёт запрос отмены (`card.undo`): `tasks.create` → `DELETE /tasks/:id`, `chat.send` → `DELETE` сообщения, `projects.add_node` → `DELETE` узла. Upsert/toggle-операции (`projects.add_member`, `tasks.add_participant`, `tasks.add_relation`, `chat.pin_message`, `chat.react`) **без undo**: удаление сняло бы предсуществующее состояние, поэтому карточка честно говорит «автоматической отмены нет», а `effect` — `irreversible` (байпас их не исполняет). Для необратимых (переходы писем, правки полей) карточка честно говорит об этом. Выполненная отмена помечается `undone`.
10. **Продолжение после решения (#916).** Карточка — вопрос с последствиями: одобрение сразу пишет в портал, поэтому продолжение запускается **отдельным прогоном**, а не висящим SSE (окно можно закрыть — ответ сохранится в истории). Прогон-продолжение идёт с **fresh `Authorization`** из запроса решения; контекст — та же сессия; состояния карточек прошлых сообщений попадают в историю блоком ДАННЫХ `<data tool="assistant_actions">` в роли `user`, а не словами модели и не `system`: строки сводки — названия сущностей и превью результатов портала, которыми управляют другие сотрудники и внешние письма, и роль `system` дала бы им авторитет инструкций выше данных инструментов (security-ревью 18.11.2026); маркеры `<data`/`</data>` внутри строк нейтрализуются тем же `asToolData`, что и результаты инструментов.
    - **Пачка = карточки одного сообщения агента** (`assistant_action_batches`, `message_id` уникален; состояния `open` → `continued` → `closed`). Автопродолжение — только когда решены ВСЕ карточки пачки: иначе лента уезжает вниз, а неодобренные карточки теряются из виду (решение владельца 18.11.2026). Одно продолжение на пачку; `failed` считается решённой карточкой (агент объясняет ошибку); таймеров нет — карточки живут в ленте сколько нужно.
    - **Частичное решение:** автопродолжения нет; над композером липкая строка «Решено N из M · К карточкам · Продолжить сейчас». «Продолжить сейчас» закрывает пачку для автопродолжения (карточки остаются рабочими) и запускает прогон, который упоминает ожидающие; повторный клик идемпотентен (тот же `runId`), после закрытия — 409. Новое сообщение сотрудника = «Продолжить сейчас» (старые карточки не теряются).
    - **Решение пришло, пока исходный прогон печатает:** прогон-продолжение РЕЗЕРВИРУЕТСЯ (строка `queued`, пачка атомарно переходит в `continued` с `continuationRunId`) и стартует по сигналу завершения активного прогона; клиент получает runId сразу, но подписывается на поток только после конца текущего (иначе оборвался бы печатающийся ответ и затёрся буфер). «Стоп» отменяет и текущий прогон, и резерв (пачка возвращается в `open` — «Продолжить сейчас» снова доступен). Перезапуск API в окне резерва закрывает осиротевшие `queued` как `interrupted` и возвращает пачки в `open` (`onModuleInit`), чтобы «Продолжить сейчас» не вёл в мёртвый прогон. Захват пачки атомарный, параллельное решение не создаёт второй прогон; проверка «сессия свободна» и старт прогона сериализованы общим per-session гейтом `runExclusive` для всех входов (`sendMessage`, `afterDecision`, `continueNow`, отложенный резерв) — иначе сообщение в окне проверки давало бы два параллельных прогона.
    - **Маршруты:** `POST /assistant/messages/:id/actions/execute-all|cancel-all` (конверт `{actions, continuationRunId}`), `POST …/continue` (`{runId}`, 202); одиночные решения возвращают `{action, continuationRunId}`. «Отменить все» аудируется `assistant.batch_cancel` (интерсептор контроллера), как и одиночные решения.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
| --- | --- | --- |
| Модель сама решает, спрашивать ли | Поведение непредсказуемо; владелец явно отклонил «модель принятия решений» | Никогда |
| Подтверждение только для «опасных» операций | Классификация опасности субъективна; пропуск важного хуже лишнего клика | Появятся роли с доверенным агентом |
| Тумблер-переключатель байпаса | Случайное включение «без вопросов» одним кликом — риск; длинное нажатие осознанно | Мобильный жест подтверждён приёмкой |
| Модальное окно подтверждения | Выбивает из диалога, ломает ленточную модель | Никогда |
| Хранить токен сотрудника для позднего выполнения | Секрет в БД; токен живёт 15 минут | Никогда |
| Выполнение записи прямо в цикле с пост-аудитом | Нет точки подтверждения; нарушает решение владельца | Никогда |

## Последствия

**Проще:** агент реально помогает («создай задачу…» → карточка → задача), при этом ни одна запись не случается без решения человека; права и аудит — существующие, второго контура нет; повторные клики безопасны.

**Сложнее:** у записи два шага (карточка → выполнение) и два места аудита; карточки живут в БД (новая таблица); для чата задачи нужен id беседы (добавлен read-инструмент, портал создаёт чат при первом открытии).

**Риски и меры:** модель может предложить лишнее — лимит 5 карточек на прогон и правило промпта «не предлагай без просьбы»; неправильные имена в карточке — имена дочитываются с API (`ctx.read`), а не из слов модели; «выполнено автоматически» без ведома сотрудника — активная пометка в композере и сброс на смену диалога/закрытие; сбой после записи до фиксации состояния — идемпотентность по id карточки и перечитывание.
