# ADR-0052. Поиск как способность платформы: проекция, провайдеры источников, видимость pre-filter, FTS-first

- **Статус:** Принят
- **Дата:** 2026-11-18
- **Контекст:** #952 (поиск по порталу), #272 (KB/КСР и векторы — потребитель), ADR-0010 (интерфейсы с первым потребителем), ADR-0012 (кросс-модульные read-порты), ADR-0032 (облачный контур смыслового поиска — исключение I11), I3/I6 (изоляция модулей), I10 (фичефлаги), I14 (данные — актив аналитики).

## Контекст

Портал искал фрагментарно: палитра Ctrl+K искала задачи и письма двумя запросами
`contains`, проекты/чаты/люди фильтровались на клиенте, сниппетов и ранжирования
не было; сообщения чатов не искались вовсе. Модуль `search` уже объявлен ядром
(`docs/architecture/modules.md`), `tech-stack.md` заявлял FTS, которого не было.

Ключевые силы:

1. **Права — часть поиска, а не фильтр после.** У задач пять ветвей видимости
   (участие, подчинённые, проекты, решающий, сбор отметок) плюс конфиденциальные
   «только участникам»; у писем — «Новые» и конфиденциальность; у сообщений —
   членство ∪ решающий. Post-filter после лимита даёт «пустую выдачу при
   непустом индексе» и утечки через total/фасеты.
2. **Модули изолированы.** Ядро поиска не имеет права читать таблицы задач,
   писем, чата, проектов, справочника (I3/I6) и не может импортировать их
   сервисы.
3. **История поиска — аналитический актив** (I14): без него нельзя настраивать
   ранжирование, но текст запроса персонально чувствителен.
4. **Первая версия — без смысловых векторов** (ответы владельца Д3/Д4): FTS
   `russian` + `pg_trgm`, векторы/реранк — #272 через `SearchProvider`.

## Решение

1. **Единая проекция `search_documents` вместо федеративного поиска в реальном
   времени.** Одна строка = один источник (`task|letter|message|project|employee`),
   PK `(source_type, source_id)`; текст (title/body/keywords), контексты
   (`project_id`, `conversation_id`, `counterparty_id`, `author_id`,
   `participant_ids`), флаги (`confidential`, `registered`), `acl_kind`,
   `payload` (номер/рег. номер/шифр/seq), даты источника. Вложения не отдельный
   тип: имя файла индексируется в тексте письма/сообщения (ответ В3).
2. **Провайдеры источников — владельцы данных.** Модуль реализует
   `SearchSourceProvider` (load/scan/tombstone), объявляет маркер
   `searchSourceType` и регистрирует провайдером Nest; реестр собирает их
   `DiscoveryService` по маркеру (ADR-0010). Индексация — обработчики outbox
   (`task.*`, `chat.message_*`, `correspondence.letter_*`, `project.*`,
   `directory.*`) с идемпотентным upsert по `source_updated_at`.
3. **Видимость — pre-filter портами.** Наборы видимости отдают владельцы:
   `TASK_VIEWER_READER` (те же ветви, что `visibleTasksWhere`),
   `PROJECT_READER.viewScopeFor`, `CHAT_MEMBERSHIP_READER.readableConversationIds`
   (членство без hidden ∪ чаты задач, где пользователь — решающий; гейтованный
   `TASK_CHAT_READER.deciderTaskIds`). Формула письма повторяет `canViewLetter`
   на полях проекции. Golden-матрица (`search.integration.test.ts`) сверяет SQL
   с каноническими функциями модулей — дрейф валит CI.
4. **FTS-first: три ноги + бусты, окно топ-100.** Точное совпадение/префикс +
   `websearch_to_tsquery('russian')` (`ts_rank_cd`) + триграммы для опечаток
   («похоже на», без автозамены). Векторы, эмбеддинги и реранк — после #272 за
   `SearchProvider`/`EmbeddingProvider` (ADR-0032 остаётся для облачного контура).
5. **tsvector — SQL-функция `search_tsv(...)` + expression-GIN,** не
   generated-колонка: Prisma не управляет generated-колонками, и `migrate diff`
   начинает дрейфовать. Запрос обязан вызывать ту же функцию.
6. **Имена — при выдаче, в индексе только id** (порты `USER_PROFILE_READER`,
   `PROJECT_READER`, `COUNTERPARTY_READER`, `CHAT_MEMBERSHIP_READER`) —
   переименование не требует переиндексации. Подпись «чат задачи ПП-123» берёт
   номер из СВОЕЙ проекции, не из таблиц задач.
7. **Аналитика — своя таблица `search_queries`,** запись best-effort после
   ответа; клики не пишутся (нужен `queryId`+мутация — отдельная задача).
8. **Тяжёлый запрос ограничен:** `statement_timeout` 3 с и порог триграмм —
   `SET LOCAL` в транзакции (глобальный `SET` на pooled-соединении изменил бы
   поведение подсказки контрагентов), таймаут → `SEARCH_TIMEOUT` (504).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Федеративный поиск (запрос в каждый модуль на лету) | Каждый модуль обязан реализовать ранжирование и пагинацию; общий порядок и total невозможны; N запросов на ввод символа; права всё равно надо сводить. Glean пришёл к единому permission-aware индексу по той же причине | Никогда для портала; для внешних систем — через провайдер источника |
| Post-filter прав после ранжирования и лимита | «Пустая страница при непустом индексе», утечки через total/фасеты, непредсказуемое листание | Никогда: видимость — данные запроса |
| Generated-колонка `search_vector` | Prisma её не описывает → `migrate diff` дрейфует; триггер-колонка — fallback, если expression-индекс не примет `migrate diff` | При смене ORM/переходе на нативный SQL-слой |
| `similarity(a,b) > x` для триграмм | Индекс `pg_trgm` не используется (Seq Scan), фильтр-функция не индексируется | Никогда; только `%`/`<%` |
| Векторы/реранк сразу | Дорого, требует эмбеддингов и живого корпуса; владелец отложил (#272) | После пилота и накопления кликов/оценок |
| Postgres FTS вместо Meilisearch | 200k строк и p95 < 150 мс достижимы; zero-cloud (I11), одна БД, транзакционная согласованность проекции | При млн+ документов и требовании морфологии/синонимов — внешний движок за `SearchProvider` |

## Последствия

- **Проще:** новый источник = провайдер + обработчик событий; права наследуются
  от владельца данных; аналитика и эксплуатация (бэкфилл CLI) в одном месте;
  #272 и ассистент получают `GET /search` и готовую проекцию.
- **Сложнее:** текст источника дублируется (проекция) — нужна дисциплина
  обработчиков (пропущенное событие = устаревшая строка; лечится `search:reindex`,
  сторож — poison-лог диспетчера). Формула видимости письма повторяется в SQL —
  закрыта golden-матрицей. Объём индекса растёт с сообщениями — при миллионах
  строк `REINDEX CONCURRENTLY` и отдельный issue.
- **Риски:** дрейф видимости (golden + security-reviewer), тяжёлые общие слова
  (`statement_timeout`, кап total), приватность аналитики (нет UI, 90 дней,
  чистка по README). Осознанно приняты (security-аудит #952, заготовка #954):
  потеря outbox-события оставляет в
  проекции старые права/текст до `search:reindex` (направление отказа —
  раскрытие участнику, которого уже убрали; сторож — poison-лог диспетчера,
  периодический reindex — #954); удаление строки во время бэкфилла может
  воскресить её (tombstone физический; окно — только обслуживание, лечится
  повторным reindex; tombstone-строки — #954); per-user лимита
  на `/search` нет (глобальный 3000/мин по IP общий за NAT — #954).

## Обоснование (research)

- Glean — единый permission-aware индекс против федеративного поиска:
  `glean.com/blog/federated-indexed-enterprise-ai` (сверка #272, «права доступа
  в поиске»).
- PostgreSQL 12 (Full Text Search): `to_tsvector`/`ts_rank_cd`, expression-GIN
  требует совпадения выражения; `ts_headline` — сниппеты с маркерами.
- PostgreSQL `pg_trgm`: индекс используют `%`/`<%`/`similarity`-операторы,
  порог — `pg_trgm.word_similarity_threshold` (SET LOCAL).
- Пагинация поиска — курсор, не offset; float в курсоре — дрейф сравнения
  (the-main-thread.com «cursor pagination in search», turion.ai про RRF/бусты).
- ADR-0012 (порты), ADR-0010 (интерфейс с первым потребителем), ADR-0032
  (векторный контур — отдельно).

## Дополнение (19.11.2026, #956)

- **Поиск внутри открытого чата** реализован через `GET /search?conversationId=`
  (pre-filter `doc.conversation_id` во всех ногах/фасетах): панель беседы
  ищет по ВСЕМ сообщениям с FTS-ранжированием и сниппетами, «Избранное»
  сохраняет собственный режим записей/закладок. Видимость — тот же
  pre-filter членства: чужая беседа даёт пустую выдачу, не 403.
- **Поиск списка бесед** — серверный (`/chat/conversations?search=`).
  Названия чатов задач/писем в БД `null` (собираются из сущности), поэтому
  chat спрашивает id у владельцев портами (`TaskChatReader.searchIds` →
  фильтр СВОИХ `task_id`; `LetterChatReader.searchIds` → `letter_id`) —
  кросс-модульных чтений таблиц нет.
- **Мини-поиски задач** переведены на серверный `?search=` (журнал, канбан,
  карточки проекта/сотрудника/контрагента): клиентский фильтр по курсорной
  пагинации видел только загруженные страницы. Локальными остались
  фильтры-атрибуты и полные малые справочники (сотрудники, проекты).
