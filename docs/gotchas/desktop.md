# Десктоп (Tauri, apps/desktop)
- **Avest CSP роняет оболочку на первом TLS через Schannel — никакого `native-tls`/Schannel в процессе оболочки** (#586, стенд владельца 04.11): установщик Avest PKI прописывает `AppInit_DLLs = AvCNG.dll` (`LoadAppInit_DLLs = 1`, HKLM и WOW6432Node). Windows грузит его в КАЖДЫЙ GUI-процесс с user32 — только при выключенном Secure Boot (при включённом Windows игнорирует AppInit_DLLs; на стенде Secure Boot = 0 — вероятное объяснение «у части машин с Avest работает», не подтверждено на рабочих машинах). AvCNG подтягивает `AvSSPc.dll` и ставит inline-хуки (`jmp`) на `SSPICLI!InitializeSecurityContextW`/`AcquireCredentialsHandleW`/`EncryptMessage`. Хук 6.1.3.1715 падает с 0xc0000005 на `avsspc+0x1207b` (`cmp dword ptr [rcx+4],2`, rcx=8 — разыменование NULL+8) прямо в первом вызове `InitializeSecurityContextW` из `schannel`-крейта (стек cdb: `nodus_desktop → avsspc!InitializeProcess+0x5ec7 → … → avsspc+0x1207b`). Вызов шёл из `fetch_config` (reqwest `native-tls`) при автоподключении к сохранённому адресу — отсюда «падает через 1–2 с без ввода». Обновление CSP до 6.3 не лечит. Тот же класс — Codex (openai/codex#42058), Skype, Word, Касперский. Штатный обход вендора — дописать exe в файл `C:\Program Files\Common Files\Avest\Avest CSP\process` (и в `(x86)`): нужны права админа, при переустановке CSP перезаписывается. Канон: весь HTTP оболочки — `reqwest` + `rustls` (ring, platform-verifier по хранилищу Windows), как у `tauri-plugin-updater`; `cargo tree -i schannel` обязан быть пуст. WebView2 (BoringSSL) не затронут. Диагностика: `cdb` из WinDbg (`winget install Microsoft.WinDbg`), `sxe -c "kn 30" av`, запуск exe под отладчиком — прав админа не нужно.
- **`GetCursorPos` отказывает вне input desktop — раскладка попапов молча падала на системный каскад** (#588): `layout.rs` брал монитор только по курсору (`cursor_position` → `monitor_from_point`), а при заблокированной сессии, экране входа, смене пользователя и RDP `GetCursorPos` возвращает FALSE/ERROR_ACCESS_DENIED (Microsoft Learn, GetCursorPos: «The input desktop must be the current desktop»; тот же класс — Wails PR #5789). Уведомления, пришедшие в этот момент (автостарт на логоне, пробуждение с локскрином), рождались на `CW_USEDEFAULT` — лесенкой от левого верхнего угла — и переезжали только после клика, когда сессия уже разблокирована. Канон: якорь раскладки с резервной цепочкой курсор → монитор главного окна → первичный монитор (эти API input desktop не требуют), позиция попапа задаётся сразу в билдере окна, а после возврата сессии тикер переставляет стек на монитор курсора. Проверка: `cargo test` в `apps/desktop/src-tauri` (якорная геометрия) + живой старт с залоченной сессией.
- **Кнопка «Скачать приложение» fail-safe: нет манифеста — в браузере кнопки нет, в оболочке она есть, но автообновление мертво, и ошибки нигде нет** (apps/web/src/app/shell/download-app-button.tsx:43). Относительный `NODUS_DESKTOP_DIR` резолвится от каталога compose-проекта: прод, поднятый из worktree `../nodus-rel`, искал артефакты в пустой `nodus-rel/infra/desktop-dist`, `/desktop/latest.json` отдавал 404 — кнопка в браузере и обновления установленных оболочек пропали молча (инцидент 02.11, #560). Канон: абсолютный путь вне git-деревьев (`D:/NodusProd/desktop`) + `scripts/prod-smoke.mjs` в каждой выкатке проверяет манифест и скачивание установщика.
- **Выключение монитора по DisplayPort = физическое УДАЛЕНИЕ устройства, а tao не пробрасывает `WM_DISPLAYCHANGE` — попапы остаются в координатах временного стола** (#763): рабочий стол переезжает на оставшийся дисплей (1280×720), попап создаётся в его координатах, а после возврата монитора никто не переставляет окно — «слева и выше» вместо правого нижнего угла. Механизм подтверждён исходниками tao 0.37.1 (`WM_SETTINGCHANGE` обновляет только тему, `ScaleFactorChanged` — только на `WM_DPICHANGED`; DPI обоих экранов 96 → событий нет) и журналами Windows (PnP 1010 «DELD12C удалён»), тот же класс у ноутбуков в док-станциях и RDP. Канон: пока стек попапов не пуст, тикер 500 мс сравнивает подпись ТОПОЛОГИИ (позиции, размеры, scale и рабочие области всех мониторов, отсортированные) и переставляет стек при изменении; движение курсора между мониторами перестановку не вызывает. Индустриальный аналог — скрытое окно под `WM_DISPLAYCHANGE` (крейт `display-config`, `WindowsDisplayObserver`). Проверка: `cargo test` (`reanchor`) + живой сценарий «выключить монитор → попап → включить».
- **PowerShell 5.1 читает `.ps1` без UTF-8 BOM как ANSI — кириллица в скрипте роняет парсер** (#820, воспроизведено 13.11: `Write-Output "Привет — проверка"` без BOM → `ParserError: В строке отсутствует завершающий символ: "`; тот же файл с BOM печатает текст). Механизм: байты UTF-8 декодируются системной кодовой страницей, многобайтные последовательности превращаются в мусор, часть байт — в кавычки/скобки, из-за чего строка обрывается. Канон: скрипты `scripts/*.ps1` — ASCII-only (сообщения по-английски), русские подсказки печатает вызывающий `.mjs`/README; BOM — не закладываем (лишний невидимый байт в первой строке). Проверка: запуск скрипта через `powershell.exe -NoProfile -File …` — текст без мусора, код выхода 0/2.
- **Панель задач Windows берёт значок приложения из РЕСУРСОВ exe (bundle.icon), а не из рантайм-`set_icon`** — перекрас иконки окна кодом (и даже отложенный повтор после старта) не меняет то, что видно на таскбаре и ярлыке: они слушаются только картинки, вшитой в установщик; рантайм-перекрас меняет лишь иконку заголовка окна. Решение — единый статичный значок (плитка + белый знак), правки только перегенерацией `tauri icon` (воспроизведено живой приёмкой 09.10 #263: два раунда рантайм-перекраса не тронули таскбар).
- **Кэш иконок Explorer переживает замену exe: после смене иконки приложения ярлык и панель задач показывают СТАРУЮ, хотя exe уже несёт новую** (подтверждено: иконка установленного exe — новая, 93% непрозрачных пикселей; ярлык — старый). Гарантированного программного сброса нет — известная боль инсталляторов (Cendio bugzilla 7970: SHCNE_ASSOCCHANGED из NSIS не чинит закреплённый таскбар; MS Learn forums: `WM_SETICON`-манипуляции мимо). Рабочие сбросы: свойства ярлыка → сменить значок (вердикт владельца 09.10 «обновил в свойствах — всё изменилось»), `ie4uinit.exe -show`, перезапуск explorer с удалением iconcache*. Правило: смена иконки = редкое событие, сопровождать инструкцией (runbook desktop-deploy).
- **WiX-шаблон Tauri v2 УЖЕ создаёт ярлык рабочего стола** (`ApplicationDesktopShortcut` → компонент в `ShortcutsFeature`, просматривается в таблицах собранного MSI через COM `WindowsInstaller.Installer`) — свой WiX-фрагмент с `DirectoryRef Id="DesktopFolder"` (как в гайдах для v1) даёт ДУБЛЬ ярлыка; кастомный фрагмент нужен только для того, чего в шаблоне нет (подтверждено таблицами MSI 1.0.0/1.0.1, #263). UpgradeCode дефолтно выводится из `productName` (UUID v5, tauri-utils config.rs) — фиксировать значением, извлечённым из Property-таблицы собранного MSI, иначе переименование продукта = «второе приложение» у установленных машин.
- **tauri-plugin-updater: `platforms.*.url` парсится как АБСОЛЮТНЫЙ URL** (serde `Url` — относительный путь = ошибка парсинга манифеста), а target-ключ манифеста ищется по типу СВОЕЙ установки: `windows-x86_64-nsis` / `-msi`, затем fallback `windows-x86_64` (`get_urls`, 2.13.2) — манифест может нести оба канала без кросс-прыжков; `install()` делает `std::process::exit(0)`, `restart_after_install` по умолчанию `true` (NSIS `/R` сам возвращает приложение); http-эндпоинты отвергаются `validate_endpoints` без `dangerousInsecureTransportProtocol` (локальный http-цикл автообновления не проверить). Подтверждено исходниками плагина 2.13.2 (#263).
- **Ручная подпись апдейтер-артефактов БЕЗ `--app-version` = «тихие» необновляемые релизы** (инцидент 16.10: 1.0.7/1.0.8 не прилетали никому): обновлятор с `requireSignedVersion` отвергает подпись, в trusted-комментарии которой нет `version:<semver>` — «The update signature does not specify the version it was signed for» — а ошибка видна ТОЛЬКО в логе оболочки (`%LOCALAPPDATA%\by.nodus.desktop\logs\nodus-desktop.log`), трей «Проверить обновления» при этом молчит. Механизм по CLI-докам (`tauri signer sign --help`): `tauri build` встраивает версию сам, ручная подпись — только явным `--app-version <версия>`; без флага подпись валидна криптографически, но отвергается на этапе скачивания. Диагностика подобных «тихих» отказов — читать лог оболочки, не гадать по раздаче: манифест/URL/подписи могут быть безупречны. **В CI-выпуске (`.github/workflows/desktop-release.yml`) версию в trusted comment встраивает сам `tauri build`** — ручной `--app-version` там не нужен и не передаётся; `scripts/desktop-publish.mjs` отвергает подпись без `version:` ещё при выкладке, поэтому класс инцидента не проходит дальше прогона (#562).
- **Свой `SW_SHOWNOACTIVATE` на окне Tauri ломает рендер попапа** — Windows рисует системную рамку с заголовком на непрозрачном чёрном фоне (вид «попап в попапе», живой вердикт 08.10 #254). Показ — штатный `win.show()`.
- **Попап не должен отбирать КЛАВИАТУРУ: `focusable(false)` закрывает только системный foreground, а клавиатурный фокус забирает кросс-процессный webview-ребёнок** (#709, два слоя, 10–12.11). Слой 1: ручной `WS_EX_NOACTIVATE` живёт только до первого `win.show()` — `show()` → tao `apply_diff` пересобирает ex-style с нуля и пишет его ЦЕЛИКОМ (`SetWindowLongW(GWL_EXSTYLE, …)`, tao 0.37.1 `window_state.rs:412-431`); `WS_EX_NOACTIVATE` вычисляется только из флага `focusable` (`:293-295`), поэтому ручной бит стирается, а следующий `ShowWindow(SW_SHOW)` (`:459-466`) активирует topmost-попап поверх чужой программы (`MARKER_DONT_FOCUS` от `focused(false)` к моменту показа уже снят — `window.rs:1415-1420`). Канон слоя 1: неактивируемость задаёт билдер `.focusable(false)` (tao удерживает бит сам), ручной `WS_EX_NOACTIVATE` не ставить — аварийный ремонт в `popups.rs` остаётся только страховкой от регрессии tao. Слой 2 (живой рецидив на 1.0.16/1.0.17): `WS_EX_NOACTIVATE` запрещает лишь ПОЛЬЗОВАТЕЛЬСКУЮ активацию — программно окно активируется (Raymond Chen, «My window has WS_EX_NOACTIVATE, but it got activated anyway», 19.09.2024), а `SetFocus` по документации MS «activates either the window that receives the focus or the parent of the window that receives the focus». WebView2 живёт в отдельном процессе `msedgewebview2.exe`, его `Chrome_WidgetWin_1` — кросс-процессный ребёнок контейнера попапа и забирает клавиатуру сам (WebView2Feedback #2487; winit #4345 «webview child pulls focus … parent remains foreground»; uno #23481 «spurious Deactivated when the WebView2 renderer HWND gains focus»). Симптом: клавиши не доходят вовсе, каретка мертва, возвращается ТОЛЬКО кликом по полю. Показ попапа при этом реально уводит foreground в попап (измерено снаружи по кадрам 250 мс: `fg=попап active=попап`, и после закрытия окна — `focus=0 active=0`), поэтому сигналом служит `GetGUIThreadInfo().hwndFocus`, а не `GetForegroundWindow()`. Почему не видел #709: его проверка `GetForegroundWindow() == popup` стояла в ветке аварийного ремонта ex-style (`has_noactivate(&win) != Some(false)` → `return`) и в обычном пути не выполнялась вовсе; к тому же одной проверки в момент `show()` мало — кража приходит и позже (первый кадр, навигация мини-UI), а `main.set_focus()` — no-op, когда окно уже foreground (`window.rs:139-150`). Диагноз — `GetGUIThreadInfo().hwndFocus` (top-level предок окна с фокусом = попап), ремонт — `SetFocus` в главное окно (или в открытое поле ответа — там печатают, новый попап не имеет права уводить набор; цель выбирается по foreground ДО показа, потому что флаг «поле открыто» не значит «человек печатает там»), а если foreground украли у чужой программы — вернуть его ей (`SetForegroundWindow`, клавиатуру в чужую очередь без `AttachThreadInput` не поставить) ТОЛЬКО с главного потока («the window must be attached to the calling thread's message queue»; успех судить по `GetGUIThreadInfo` после вызова — `SetFocus` возвращает NULL и при успехе, если прежний фокус был вне очереди потока): wry на `WM_SETFOCUS` родителя сам зовёт `MoveFocus(PROGRAMMATIC)` в главный webview (`wry-0.57.0/src/webview2/mod.rs:1325-1328`, сабкласс ставится при `!is_child` — дефолт Tauri без фичи `unstable`), и Chromium возвращает каретку в поле, не терявшее DOM-фокус. Канон слоя 2: гвард `focus.rs` на создание/показ/закрытие попапа + сторож 2 с после показа (кража асинхронна — создание контроллера WebView2, первый кадр, навигация мини-UI); лимит 8 возвратов за 3 с против петли (в tauri#15624 наивный app-side ремонт давал 140–200 Гц); уничтожение окна может оставить очередь ввода вообще без фокуса (winit #4345) — `focus = 0` при нашем foreground тоже чинится. Проверка: в логе оболочки `попап popup-N (показ): main=… fg=… active=… focus=…(class) root=…`, при краже — `фокус ушёл из портала: … → возвращён`. Оговорка: включённая в Windows настройка «активировать окно наведением» активирует и NOACTIVATE-окно (Raymond Chen, Old New Thing) — стилем не лечится.
- **WebView2 при `win.hide()` НЕ меняет `document.hidden`, а при минимизации может сохранять и `visibilityState='visible'`, и `document.hasFocus()`** — сигналы страницы о «смотрит/не смотрит» в оболочке недостоверны: скрытие в трей шлётся событием `shell-visibility`, фокус/свёрнутость — `shell-focus` (`WindowEvent::Focused`/`Resized` + `is_minimized()`, lib.rs), и только модель внимания (`shared/attention/attention-store.ts`, ADR-0038) решает, что человек видит. Без этого ушедший домой пользователь «читал» всю переписку из трея («зомби-бейдж» #254, ложное «прочитано» #770; механизм подтверждён кодом моста и приёмкой владельца 08.10/11.11).
- **Попап-окно, показанное ДО первого кадра WebView2, composite-ится ЧЁРНЫМ, а гонка двух каналов темы красила его тёмными токенами в светлой теме портала** (#305, репро владельца: «первое уведомление чёрное, остальные белые»): `win.show()` сразу после билда обгоняет загрузку страницы — прозрачное непрогретое окно Windows рисует чёрным до первого composite (tauri #6775: «web render engine has warmed up» — первое окно худшее; WebView2Feedback #4834; wry-док `no_redirection_bitmap`: «flash before the webview content is rendered»), а `eval` темы из `UI_THEME` во время навигации теряется — и inline-скрипт окна (читает `localStorage` сетап-тумблера, где может лежать устаревший `dark`) побеждает. Канон: окно создаётся скрытым; данные+тема приезжают ОДНИМ payload (pull `popup_get_data`); мини-UI применяет тему до рендера и зовёт `popup_ready` после первого кадра (двойной rAF) — только тогда `win.show()`; fallback-таймер ~1.2 с страхует потерянные уведомления (`mark_shown` — show ровно один раз).

- Создание `WebviewWindow` в СИНХРОННОЙ tauri-команде дедлокит WebView2 — окно висит на `about:blank` и держит foreground Windows (пользователь не может активировать другие окна!): команды, создающие окна, — только `async fn` (docs.rs WebviewWindowBuilder «Known issues», tauri #13963/#13092; подтверждено живым репро 08.10 #254).
- Наличие каталога `src-tauri/permissions/` включает строгий AppManifest-режим: КАЖДАЯ команда приложения (включая локальный мини-UI) требует явной capability — «command not allowed. Command not found» даже для локальных страниц (tauri 7a2672f; репро #254).
- `tauri::generate_context!` вшивает ассеты `frontendDist` ПРИ КОМПИЛЯЦИИ: после `vite build` обязателен `cargo build`, иначе работает старый бандл; запущенный exe блокирует линковку (`os error 5`) — убивать процесс ДО cargo build (репро #254).
- Попап-окно с CSS-скруглением требует `transparent(true) + shadow(false)` билдера: непрозрачный фон окна вылезает из-за углов карточки, а системная тень тянется по прямоугольнику окна (репро #254).
- Payload в свежесозданное окно — pull-моделью (окно само инvoke'ает `popup_get_data`): push-событие из Rust прилетает раньше монтирования React-слушателя и теряется (репро #254).
- Альфа-смешивание пикселей в u16 переполняется (255·255·255 > 65535, паника debug-сборки «attempt to multiply with overflow» в бейдже) — считать в u32 (репро #254).
- Битовые глифы пиксельного шрифта со сдвигом `row*3+col` читаются СНИЗУ вверх — цифры бейджа зеркалились по вертикали; строковые глифы row-major без битовой математики (репро #254, вердикт владельца «перевёрнутая цифра»).
- **`overflow: hidden` — это scroll-контейнер: фокус поля внутри прокручивает его программно** (scroll-into-view), даже если пользователь скроллить не может. Контент уезжает за верхнюю границу вместе с абсолютным крестиком — попап «зависает» (закрыть нечем), потому что `replying` держит паузу угасания. Лечение: `overflow: clip` — не создаёт scroll-контейнер и запрещает программный скролл (MDN overflow: «the element box is not a scroll container … programmatic scrolling is not supported»; подтверждено живым репро #406: scrollTop 4–58 px до фикса, 0 после). Оговорка MDN: клипнутый focusable-контент фокус получает, но НЕ прокручивается в вид — поэтому высоту окна надо подгонять под контент, а не надеяться на скролл.
- **Геометрия попапа не хардкодится в Rust-константах: мини-UI живёт на `--ui-scale`** — `packages/ui/src/styles/globals.css` задаёт `html { font-size: calc(100% * var(--ui-scale)) }` с дефолтом 1.25, поэтому rem-утилиты (padding, line-height, size) на 25% больше дизайн-px базы 16. - **Каретка мерцает/пропадает при печати во ВСЕХ полях оболочки, возвращается от движения мыши** (#309, две сессии ложных следов): функция Chromium 152+ `HideCursorWhileTyping` (системная настройка Windows «Скрывать указатель во время ввода», включена по умолчанию) в HWND-хостинге WebView2 гасит и каретку (WebView2Feedback #5687/#5708). - **webview молча сохраняет скачивание: файл тихо падает в «Загрузки» без UI и без события** (#647): wry 0.57 по умолчанию ставит `download_started_handler = Some(|_, _| true)` и `download_completed_handler = None` (wry-0.57 `src/lib.rs:868-869`), а WebView2 при `SetHandled(true)` + `SetResultFilePath(путь по умолчанию)` не показывает свою панель загрузок — пользователь не видит ни подтверждения, ни пути. Лечение: `WebviewWindowBuilder::on_download` главного окна (tauri 2.12.1 `webview/mod.rs`, `DownloadEvent::{Requested,Finished}`), на `Finished` — попап оболочки; окно попапа создаётся ТОЛЬКО из async-контекста (`async_runtime::spawn`), потому что синхронный обработчик события дедлокит WebView2 (соседняя ловушка выше). Проверено: `cargo check`/`cargo test` (5 тестов гварда пути); живая цепочка скачивание → карточка → reveal — после сборки/релиза оболочки. Источник механизма — исходники wry и tauri, не догадка.
- **Tauri подменяет drop-обработчик WebView2 — HTML5 drag&drop файлов в оболочке молча не работает** (#716): `WebviewWindowBuilder` по умолчанию ставит свой drag-drop хендлер (генерация `DragDropEvent`), и на Windows нативные DOM-события дропа до страницы не доходят — файл из Проводника в ленту чата не прикрепляется, хотя в браузере тот же экран работает (приёмка владельца). Лечение: `.disable_drag_drop_handler()` на билдере главного окна (`apps/desktop/src-tauri/src/lib.rs`); док-комментарий tauri 2.12.1 (`webview/webview_window.rs:1094-1099`) дословно: «required to use HTML5 drag and drop APIs on the frontend on Windows since we replace the drag drop handler of WebView2». Обратная сторона: JS-события `DragDropEvent` не приходят вовсе — понадобится путь файла в Rust, хендлер придётся вернуть осознанно. Вторая сторона: внешний drop включает нативную навигацию WebView2 на `file://`-URL брошенного файла — гвард `navigation_allowed` обязан проверять СХЕМУ до host (`file://tauri.localhost/…` иначе проходит как «локальный UI» и грузит сторонний HTML в окно с внедрённым мостом; security-ревью #716).
- **Веб-манифест `/desktop/latest.json` в долгоживущем окне портала СТАРЕЕТ: авторитет по версии обновления — мост, не манифест** (#739): попап кнопки обновления брал целевую версию и «что нового» из манифеста, а SPA оболочки живёт часами — фетч один на загрузку страницы (`staleTime` 10 мин, `refetchOnWindowFocus:false`, фоновых рефетчей нет), поэтому попап показывал «1.0.15 → 1.0.15» и текст ПРЕДЫДУЩЕГО выпуска, хотя апдейтер уже скачал 1.0.16 и кнопка ставила именно её. Канон: pending-версия и решение «есть обновление» — из `updateState` моста (`status:available`, опрос 15 с + событие); манифест — только источник ТЕКСТОВ, и заметки/дату показываем лишь когда `manifest.version === targetVersion` (иначе лучше без текста, чем чужой); при рассинхроне — один рефетч манифеста на версию (`refreshedFor`-guard) догоняет текст. Воспроизведено живой приёмкой 10.11 (1.0.15 → 1.0.16).
