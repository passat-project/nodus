# Docker и инфраструктура

- На dev-хосте крутятся чужие Docker-проекты: контейнеры/сети/тома Nodus — только с префиксом `nodus_`, порты — через `.env`, перед `docker compose up` проверяй занятые порты (`docker ps`).
- **Прод — `D:\NodusProd`, а не git-дерево** (ADR-0036): `.env`, `kit/v<версия>/`, `desktop/`, `backup/`, `deployments.log`; образы по тегу собирает CI, выкатка/откат — только `scripts/prod-deploy.mjs` (runbook `prod-update.md`). Каталог не удалять и не чистить — это прод-данные, а не остатки сессий. **Сервисы прода не поднимать `docker compose` из основного дерева или из worktree**: так 28.10 конвертер `gotenberg` пересоздали из другого дерева, он оказался в чужой сети, и api перестал его видеть (#561). Worktree `../nodus-rel` — устаревшая точка сборки: живёт до перехода на образы, удаляется отдельным решением владельца. Соседние `nodus-*` — остатки агентных сессий: пустой скелет (0 файлов, только каталоги) снимать можно; перед удалением любой соседней папки проверяй label живых контейнеров — `docker inspect nodus_web --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'` (подтверждено воспроизведением 29.10: label показал `nodus-rel` на живом проде).
- **Переменные из `.env` НЕ попадают в контейнер сами**: compose подставляет их только в файл (интерполяция), а в процесс сервиса уходит лишь то, что перечислено в `environment:`/`env_file:` (docs.docker.com/compose/how-tos/environment-variables/variable-interpolation). Новая подсистема, читающая новый ключ из `.env`, молча спит на проде, если ключ не проведён в `environment:` сервиса — `docker compose config` этого не ловит, он показывает подстановку в файле, а не env контейнера (репро 03.11, #577: приём почты на проде без единой строки в логе). Лечение: явный список ключей в `environment:` (не `env_file` — путь резолвится от каталога kit, а `.env` живёт в прод-каталоге) и warn в лог при старте, если подсистема не вооружена.
- **Пустая env-переменная из compose — это не «не задана»** (#580): `${VAR:-}` подставляет пустую строку, а `z.string().optional()` пропускает только `undefined` — `min(32)` падает на `''`, и выключенная подсистема роняет старт. Валидация env обязана трактовать пустую строку как отсутствие (`z.preprocess`), иначе `docker compose up` из `.env.example` не поднимается. (Docker Compose docs, variable interpolation: `${VAR:-default}` — значение `VAR`, если задано и непусто, иначе default; Zod docs, Optionals: `.optional()` допускает только `undefined`.)
- В alpine-контейнерах `localhost` резолвится в ::1 (musl предпочитает AAAA), а наши сервисы слушают IPv4 (`0.0.0.0`) — healthcheck'и docker-compose ходят на `127.0.0.1`, не `localhost`.
- Образ `postgres:18+` ждёт данные в `/var/lib/postgresql`, а не `/var/lib/postgresql/data` — со старым путём контейнер не стартует («unused mount/volume»); новый путь заодно даёт мажорные апгрейды через `pg_upgrade --link`.
- **В runner-стадии Dockerfile глобальных CLI нет** (pnpm ставится только в builder): CMD и seed-скрипты вызывают бинарники из `node_modules/.bin/` пакета (`./node_modules/.bin/prisma migrate deploy`), иначе контейнер рестартит с «pnpm: not found» (подтверждено воспроизведением в issue #3).
- **`prisma db seed` в контейнере не находит tsx на PATH** (pnpm-бины не экспортированы): seed-команда — `node --import tsx prisma/seed.ts`, кроссплатформенно (Windows-хост и alpine-контейнер; подтверждено воспроизведением в issue #3).
- **ONLYOFFICE DS (#138, все — официальные доки API DS + репро 28.09):**
  - `window.DocsAPI` — ОБЪЕКТ с конструктором `DocsAPI.DocEditor`, не сам конструктор (`new DocsAPI(...)` → TypeError; api.onlyoffice.com/docs/docs-api/usage-api/doceditor).
  - Алфавит `document.key` — `0-9-.a-zA-Z_=`: двоеточие в `${id}:v1` молча валит канал ко-эдитинга (`io.on connection unexpected key use key pattern` в логах docservice, в UI — ошибка -23).
  - DS строит абсолютные ссылки (Editor.bin в /cache, колбэки) от УВИДЕННОГО Host: прокси обязан слать браузерный `Host`/`X-Forwarded-Host` С ПОРТОМ (nginx `$http_host`, не `$host`; vite-прокси — БЕЗ changeOrigin) — подменённый хост = кросс-origin ERR_FAILED.
  - **cloudflared НЕ ставит `X-Forwarded-Proto`**: nginx за туннелем видит `$scheme` = всегда http — DS строит `http://`-ссылки на свой кэш, а HTTPS-браузер режет их как Mixed Content («Редактор недоступен», errorCode -1; репро nodus.by 29.09). Схему оригинала берём из `CF-Visitor` (edge всегда шлёт): map `$http_cf_visitor → $nodus_proto` → `X-Forwarded-Proto` (web.conf); Edge Cloudflare инжектит и beacon cloudflareinsights.com в HTML iframe — CORS-шум в консоли, продукт не трогает, выключается в панели CF.
  - DS 302-редиректит статику на версионный префикс `/<версия>-<хэш>/web-apps/...` — прокси должен покрывать и его (regexp `^/(web-apps|...|[0-9]+\.[0-9]+\.[0-9]+-[0-9a-f]+)`).
  - SSRF-фильтр DS (`request-filtering-agent`) по умолчанию режет приватные адреса — скачивание `document.url` из compose-сети требует env `ALLOW_PRIVATE_IP_ADDRESS=true`.
  - Callback-токен приходит Bearer-заголовком с payload-обёрткой `{payload:{...тело}}` (`JWT_IN_BODY=false` по умолчанию; api.onlyoffice.com signature/request).
  - **DS считает ошибкой ЛЮБОЙ не-200 ответ колбэка** (включая семантически успешный Nest-дефолт 201 для `@Post`): в логах docservice `postData error: statusCode:201`, в UI «Не удается сохранить документ», повторные доставки → `storeForgotten` — на колбэке обязателен `@HttpCode(200)` (репро 29.09, вердикт владельца #138; доки DS callback handler: response 200 + `{"error":0}`).
  - **Встраивание DS корневыми путями = коллизия со своими публичными ассетами**: `/fonts/*` приложения перехватывается DS-прокси ДО статики (vite proxy и nginx) → 404 из documentserver; свои публичные файлы держать вне DS-путей (`/app-fonts/` вместо `/fonts/`, репро 29.09 #138).
  - **DS не автоопределяет кодировку txt/csv/tsv**: показывает диалог «Выбрать параметры TXT/CSV» (конфигом НЕ отключается — официальный ответ ONLYOFFICE, community 9910; feature request открыт годами). UTF-8 **с BOM** открывается без диалога (проверено живьём 29.09) — API отдаёт текст DS через `office=1`-нормализацию (UTF-8/1251→BOM). CSV всё равно спрашивает РАЗДЕЛИТЕЛЬ (предзаполняется автодетектом). **Кэш конвертаций привязан к document key**: сменив отдаваемые байты без смены ключа (наш office=1), чисти `/var/lib/onlyoffice/documentserver/App_Data/cache+forgotten` — иначе DS вечно отвечает старым «спросить кодировку» (репро 29.09).
- **NestJS `@Global()`-модуль глобализирует ТОЛЬКО `exports`**: провайдер без попадания в exports невидим другим модулям, а `@Optional()` на инжекте маскирует провал пустым дефолтом — баг молчит до живой проверки (репро 29.09 #138: multi-порт FILE_ACCESS_CONTRIBUTORS без exports → доступ «только владелец», участник беседы получал 404; docs.nestjs.com/modules «global scope + exports»; замок — probe-потребитель без @Optional, компиляция падает при регрессе).
- Cloudflare Tunnel после пересоздания web-контейнера теряет origin («connection refused» до переподключения): `docker restart nodus_cloudflared`; проверяй демо curl'ом, а не Invoke-WebRequest (тот капризничает с таймаутами на этой машине).
- **`VITE_*`-переменные — build-time**: `.env` хоста не попадает в docker-сборку, режим демо задаётся `ARG`/build-args в compose (`NODUS_WEB_MOCK` → `VITE_API_MOCK`); сменил режим — пересобирай образ (`docker compose up -d --build web`), рестарта контейнера мало.
- **turbo-кэш build не видит env — и не только «не пересобирает», но и ЗАТИРАЕТ чужую сборку**: ручная non-mock сборка web (`VITE_API_MOCK=false vite build`) была перезаписана кэшированной задачей последующего `pnpm build` (в кэше лежал бандл с .env-значением флага) — на вердикт-стек уехал полумок-бандл с активным MSW (репро #57: владелец получил «Не удалось загрузить файл»). Лечение: `turbo.json` → `tasks.build.env: ["VITE_API_MOCK"]` — env входит в хэш задачи, смена значения = гарантированный промах кэша.
- **Порты сервисов опубликованы на `127.0.0.1`** (postgres/redis/minio/api/gateway; у gotenberg опубликованного порта нет вовсе): k6 и dev с хоста ходят через localhost, из LAN сервисы не видны — это осознанно (аудит #123), «чинить» обратно на `0.0.0.0` не нужно. После ребута хоста `docker compose up -d` БЕЗ `--profile tunnel` не поднимает cloudflared — nodus.by лежит до `--profile tunnel up -d` (runbook `host-reboot.md`).
- **SILO (клиент mcli И СЕРВЕР) отвергает `_` в hostname**: `alias set http://nodus_minio:9000` — «invalid hostname» на клиенте; Host с подчёркиванием — 400 InvalidRequest на КАЖДЫЙ запрос к серверу (репро пересборки прода 28.09: api падал на ensureBucket). Всё, что ходит в SILO — по алиасу через дефис (`aliases: [nodus-minio]`, `STORAGE_ENDPOINT: nodus-minio`) (подтверждено воспроизведением, #57).
- **Статический `proxy_pass http://service` резолвит имя при загрузке конфига** — nginx падает в рестарт-цикл (`host not found in upstream`), если сервис выключен профилем (DS живёт под профилем `office`): для опциональных апстримов `resolver 127.0.0.11 valid=30s ipv6=off;` + `set $up http://service; proxy_pass $up;` — без DS офисные пути дают 502, остальной портал живёт (#579; подтверждено `nginx -t` в контейнере: до фикса `emerg` на `nodus_documentserver`, после — `syntax is ok`).
- **Дефолт nginx `client_max_body_size` — 1 МБ**: любой аплоад через прокси-локацию /api молча срезается 413 до api; при добавлении загрузок поднимай лимит в локации (`infra/nginx/web.conf`, #57 — 200m + таймауты 300s на медленные каналы; поведение дефолта — документация nginx).
- **Cloudflare режет тело проксированного запроса по тарифу** (Free/Pro 100 МБ, Business 200, Enterprise 500; не отключается): любой upload через туннель nodus.by >100 МБ падает на edge независимо от нашего кода — «серые облака»/VPS или прямой presigned в фазу 2 (подтверждено: developer docs Cloudflare «Limits», #57/ADR-0013).

- **Docker публикует порты только на `127.0.0.1`, а Node 17+ резолвит `localhost` в `::1`** — vite-прокси/node-fetch получают ECONNREFUSED → «502 Bad Gateway» при зелёном curl (curl фолбэчится на IPv4): таргеты прокси и серверных фетчей — явный `127.0.0.1` (репро #378: живой auth через dev-прокси).
- **SPA без явного `Cache-Control` живёт на эвристике «10% от возраста Last-Modified»** — WebView2/браузер держат старый `index.html` бесконечно: деплой «не доезжает» до оболочки (#263). Канон nginx: `index.html`/SPA-фолбэк — `no-cache`, `/assets/*` (vite-хэши) — `immutable`; свои `add_header` в location отменяют наследование серверного security-набора — повторять HSTS/nosniff. Закэшированную копию серверный no-cache не лечит: embedded-вью грузят документ с одноразовым `_nd=<millis>`; доставку деплоя проверять grep маркера в ассетах контейнера.
- **Compose-сеть `internal: true` — Docker МОЛЧА игнорирует опубликованные порты и не пускает хост** (#56, воспроизведено): контейнер только во internal-сети с `ports: 127.0.0.1:…` не получает published-порт (`docker port` пуст), прямые IP контейнера с хоста тоже недоступны (timeout) — «выставлю порт на internal-сети для локальных нужд» не работает. Исход: egress-изоляция Gotenberg (Р10). Канон: прод-сервис без портов только во internal-сети; хостовому потребителю (песочница live-stack) — отдельный эфемерный контейнер профиля compose на обычной сети с loopback-портом.
- **Хранилище: файл > 64 МиБ идёт multipart-путём и требует права на СПИСОК загрузок** (#713, 10.11.2026): minio-js режет загрузку по `partSize = 64 * 1024 * 1024` — до 64 МиБ `putObject` буферизует и делает один PUT, больше — `uploadStream`, а он ДО данных вызывает `ListMultipartUploads` (`findUploadId`, поиск незавершённой загрузки для продолжения) и при продолжении `ListParts`. Политика сервисной учётки (`docker-compose.yml`, `minio-init`) с одними `PutObject/ListBucket` даёт `Access Denied` ровно на пороге: 67 108 864 байт — 201, 67 108 865 — 400 `FILE_SIZE_MISMATCH` (в хранилище уходит ~65 КБ). Лимит приложения при этом 100 МБ — «лимит» ни при чём. Канон: в политике обязаны быть `s3:ListBucketMultipartUploads` и `s3:ListMultipartUploadParts`; страж — `scripts/lib/storage-policy.test.mjs` в always-run шаге `pnpm test:scripts` (turbo-тесты пакетов идут affected-only и compose-only правку пропустили бы); брошенные части при обрыве убирает `MinioStorageDriver.put` (`removeIncompleteUpload` в catch), жёсткий kill/OOM закрывает уборка #715 — ILM-правила на незавершённые загрузки в SILO `RELEASE.2026-09-16` НЕТ (`mcli ilm rule add --help` без флага, не искать); подтверждение — исходник minio 8.0.7 (`client.js`: `partSize = 64 * 1024 * 1024`, `uploadStream → findUploadId`) и доки S3 Actions (`ListBucketMultipartUploads` — отдельное действие от `ListBucket`). Попутно: `mcli admin policy update` в SILO-форке удалён («Deprecated command»), а `policy create` — апсерт (перезаписывает существующую политику), поэтому fallback `create || update` в init ломал бы рестарт.
