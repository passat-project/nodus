# Единая модель Nodus: тип проекта, проект и работы

Читать: **перед любой работой над issue ядра автоматизации, проектов, задач и корреспонденции** — до тела issue. Здесь простым языком описано, как устроен продукт целиком; каждый issue описывает один кусок этой картины и начинается ссылкой сюда. Если issue, ADR или код расходятся с этой страницей — это находка: остановись и сообщи, не выбирай сам.

Источник: решения владельца 15.11.2026 (три круга разбора на бизнес-кейсах) поверх ADR-0024, ADR-0030, ADR-0037. Архитектурное решение — ADR-0041.

## 1. Главная мысль

- **Тип задачи** (и тип письма) знает, как течёт **одна** работа: статусы, кнопки, окна, проверки.
- **Тип проекта** знает, **какие работы в проекте бывают и что за чем появляется**. Это шаблон всего процесса.
- **Проект** — живой экземпляр своего типа: дерево папок, работы, письма, люди, статус.

Слова владельца: «тип проекта — это некая абстракция, схема поведения всех остальных сущностей и процессов, которые у нас будут создаваться»; «проект — аккумуляция всех этих процессов».

## 2. Из чего состоит тип проекта

Всё настраивается в интерфейсе, в коде нет ни одного слова предметной области («комплект», «смета», «КЖ»).

| Часть | Что это | Пример у «Договора на проектирование» | Issue |
| --- | --- | --- | --- |
| Форма проекта | Поля проекта, включая признаки договора | шифр, заказчик, «Сметная документация: да / нет» | сделано (#631, #496) |
| Виды папок | Что бывает в дереве проекта | здание, комплект с полем «Марка» | сделано (#556) |
| Что здесь можно создавать | Типы задач и писем из общей библиотеки, разрешённые в проектах этого типа | «Разработка комплекта», «Изменение», «Задание смежнику», входящее письмо | #665 |
| Статусы и кнопки проекта | Маршрут проекта: статусы, кнопки с окнами, проверки — как у задачи | «Подготовка → Проектирование → Экспертиза → Сдан» | #856 |
| Ветки | Правила «для каждой папки такого-то вида с такими-то полями: когда случилось A — сделать B» | «у каждого комплекта с маркой ОВ после „Костяк готов“ — окно „Кому выдать задания“» | #38 |
| Вкладки по умолчанию и доступ | Какие списки видит ГИП в карточке проекта; кто создаёт проекты типа | вкладка «Пульс» | #469, #637 |

## 3. Сквозной пример: договор «Школа»

1. ГИП создаёт договор короткой формой: название, шифр, заказчик, «Сметная документация: да». Проект в статусе «Подготовка».
2. В карточке проекта жмёт кнопку «Начать проектирование». Открывается окно с таблицей «Контрольный штамп»: в строке — марка (из списка), шифр, название, здание, главспец, срок; таблицу можно вставить из Excel. После подтверждения система создаёт папки-комплекты и в каждой — работу «Разработка комплекта» у главспеца. Проект переходит в «Проектирование». Отдельного мастера создания проекта нет: штамп — это окно кнопки.
3. Главспец ведёт ОВ1.1 по маршруту «Разработки комплекта». На статусе «Костяк готов» срабатывает ветка для марки ОВ: окно «Кому выдать задания», по задаче «Задание смежнику» на каждого отмеченного.
4. Кнопка «Выдано в печать» не пускает, пока задания не приняты, и перечисляет, какие. После выдачи срабатывает сметная ветка: у договора «Сметная документация: да» — появляется «Задание сметчикам».
5. Заказчик прислал замечания → «Внести изменения» → работа «Изменение» (Изм. 1) в той же папке. Ветки повторяются для каждого Изм.
6. Комплектов с маркой КЖ в штампе нет — ветка КЖ молчит, её никто не ждёт. В договоре без смет молчит сметная ветка. ГИП ничего не отключает руками.
7. Кнопка проекта «Сдать заказчику» не пускает, пока есть невыданные комплекты, и показывает их; руководитель проекта может пройти с причиной. Переход статуса может быть и автоматическим — правилом («все комплекты выданы»).
8. Руководство видит статус проекта колонкой в списке проектов; зайдя в проект — что мешает перейти дальше.

## 4. Другие случаи на той же модели

- **Тема** («Обучение персонала», «Внедрение IT») — тип проекта с одним статусом «Действует», без веток; разрешены простые задачи и письма. Темы — способ группировать письма и задачи не по договору. Слова «рубрика» в продукте нет.
- **Переработки** — тип проекта, в котором разрешён один тип задачи «Переработка». Проект такого типа один, поэтому при создании заявки он подставляется сам. «Проект, где отработано» — поле заявки. Часы по подразделениям — вкладка-список в карточке проекта «Переработки» (#435).
- **Без проекта** — лёгкие внутренние задачи («Стандартная», «Быстрая») можно создавать без проекта. У них нет автоматизации схемы проекта, и это нормально. В настройке «Без проекта» — строка рядом с типами проектов со своим списком разрешённых типов.
- **Письмо** регистрируется без проекта (секретарь не обязан знать договор). Проект — договор или тему — указывает тот, кто накладывает резолюцию, или ГИП; без проекта поручения не расписать. Поручения создаются в проекте письма (#463).

## 5. Где это настраивают и где с этим работают

- **Настройка — «Автоматизация → Процессы»** (один вход). Слева: типы проектов, строка «Без проекта», «Библиотека типов» — общий справочник типов задач и писем (тип один на весь портал). В типе проекта — холст со статусами проекта и ветками и панель «Что здесь можно создавать»: галочки из библиотеки. Двойной клик по типу задачи открывает его маршрут — тот же, что открывается из библиотеки. Новый тип проекта создаётся копией существующего (#857).
- **Работа — карточка проекта**, рабочее место ГИПа: вкладки (задачи, структура, списки и реестры, письма проекта, чат, канал) и нижняя полоса с кнопками статусов проекта — всегда на всю ширину карточки, как бы пользователь ни разложил вкладки по областям; кнопки слева, как у задачи и письма. Проектировщик работает кнопками в карточке задачи.

## 6. Отступления и новые издания схемы

- **Руководство проекта** (руководитель и помощники) в своём проекте: проходит проверку с причиной, отключает ветку для конкретного комплекта, добавляет разовый шаг. Всё пишется в историю проекта с фамилией и причиной.
- **Главспец** в своём комплекте может только добавить внеплановую задачу.
- **Схему типа** меняет настройщик (отдельное право). Схема живёт черновиком и изданиями. Перед публикацией издания настройщик видит, какие идущие проекты и сколько ещё не сработавших шагов это затронет. После публикации: пройденное и созданное не меняется никогда; ещё не сработавшее в проектах без ручных правок переходит на новое издание само; там, где ГИП правил руками, его правка остаётся с пометкой «отличается от нового издания».

## 7. Один движок (для исполнителей)

- Движок один — «Процессы» (ADR-0024). Маршрут проекта — третья категория сущностей движка рядом с задачами и письмами: те же статусы, кнопки (переходы и действия), окна, проверки, журнал.
- Ветка — правило «когда → если → сделать» (#448) с областью «тип проекта»: событие (папка появилась, статус работы достигнут, статус проекта сменился, Изм. создано) → условия по полям папки и проекта (#635) → шаги (#634, #436).
- Панель кнопок карточки (задача, письмо, проект) — три слота: главная, второстепенные, действия; меню «⋯» в ней нет. Несколько кнопок в слоте — первая нажимается сразу, остальные в списке по стрелке вверх, редкие — в конце списка. Кнопка, которую жмут несколько, в список не прячется (решение владельца 16.11.2026).
- Кнопка «из любого статуса» в завершённой или отменённой записи не показывается: переход — только если ведёт обратно в работу, действие (#633) — никогда. Нужно действие в закрытой записи — его ставят на этот статус явно (решение владельца 16.11.2026; у Jira и Яндекс Трекера «любой» включает закрытые, ограничение там — ручным условием).
- «Ждать всех» — проверка на кнопке в момент нажатия по живому составу проекта. Снимков состава, токенов и второго движка нет.
- Проект хранит ссылку на издание схемы и свои локальные правки, а не копию схемы. Сработавшее пишется в журнал: одна ветка для одной папки и одного Изм. срабатывает один раз.
- Данные процесса — атрибуты проекта, папок и задач и поля окон. Отдельного хранилища переменных нет.

## 8. Чего в модели нет

Ошибки, которые уже случались или напрашиваются, — так делать нельзя:

- отдельный движок бизнес-процессов, токены, BPMN-редактор рядом с «Процессами»;
- отдельный экран «мастер создания проекта» — штамп вводится в окне кнопки проекта;
- обязательный проект у каждой записи — записи без проекта допустимы;
- слово «рубрика» и отдельный справочник рубрик — вместо него проекты-темы;
- копия схемы в каждом проекте без связи с типом;
- рисование каждой задачи на холсте типа — рисуются статусы проекта и ветки;
- зашитые в код марки, стадии, «сметы», «комплекты»;
- «виды» как отдельный раздел или выпадающий список в журнале задач — вид это вкладка-список в карточке проекта (#435);
- задачи «по ведению проекта» для ГИПа как обязательный элемент — этапы проекта это его статусы.

Не входит в первую версию, заведено заготовками: вкладка «Схема» в карточке проекта (#858), напоминания по срокам и расписание (#859), пробный прогон схемы (#860), Гант со сроками (#861), внешние события (#862).

## 9. Порядок работ (зависимости, без сроков)

Ядро: действие (#633) → шаги (#634) → «создать задачи» (#436) → проверки (#635) → правила (#448); параллельно — списки (#435), реестры (#636), вкладки (#637), «кнопку жмут несколько» (#434).
Схема: «что здесь можно создавать» (#665) → статусы и кнопки проекта (#856) → окно-штамп (#468) → ветки, издания, отступления (#38) → единый вход (#857).
Посев процессов проектирования: комплект (#557) → задания смежникам и сметчикам (#638) → пульс (#469).

## 10. Как писать issue по этой модели

Каждый issue ядра, проектов и корреспонденции имеет один каркас: **Картина** (что видит человек) → **Где это живёт** → **Где этого не должно быть** → **Сквозной пример** → **Слова владельца** → **Что проверить на приёмке** → зависимости и гейты. Технический план исполнитель добавляет ниже, каркас не трогает.
