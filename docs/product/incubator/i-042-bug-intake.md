# И-042 · Приём обратной связи о багах через ассистента

**Дата:** 2026-11-18

**Суть:** сотрудник жалуется ассистенту на баг или неудобство; агент задаёт вопросы, собирает обязательные поля (что делал, что ожидал, что получил, где, когда, скриншот), проверяет, нет ли уже такого бага, и только после подтверждения записывает обращение. Записи без описания и подтверждения не создаются. Отдельно агент показывает список уже известных багов — по метке `type:bug`, а не по всем 141 открытым issue (сейчас багов 13), чтобы не тонуть в контексте.

**Разбор:** за — единая точка входа, меньше потерянных жалоб, дедупликация до создания; против — нужен реестр/права/триаж, риск спама и «мусорных» записей; риск — публичный GitHub: тексты жалоб могут содержать внутренние данные, поэтому писать напрямую в issues опасно. Варианты: (а) внутренний реестр портала + админ-триаж + отдельная выгрузка в GitHub; (б) GitHub read-only для поиска багов + создание issue только после триажа админом; (в) отдельный инструмент `bugs.report` с карточкой подтверждения и без прямого GitHub-доступа. Массовые комментарии не делаем (решение 18.11.2026).

**Открытые вопросы:** куда пишем — внутренний реестр или GitHub? Кто подтверждает и триажит? Какие поля обязательны и как проверять полноту? Нужна ли связь с GitHub и какой токен/права? Как отличать баг от пожелания (инкубатор) и дедуплицировать?

**Связи:** #889/#926 (ассистент), #938 (курсор списков), GitHub-метка `type:bug`.

**Статус:** обсуждается.
